## 1. 범위와 근거 인벤토리

매뉴얼은 제품 소개가 아니라 특정 독자가 실제 업무를 수행하는 운영 산출물이다. 먼저 다음 표를 만든다.

| 항목 | 확인 내용 |
| --- | --- |
| 독자 | 역할, 경험 수준, 권한, 사용하는 용어 |
| 시작 | 요청, 문서, 상태, 일정, 경고처럼 업무를 시작시키는 조건 |
| 입력 | 필수 값, 선행 문서, 계정, 권한, 기준 데이터 |
| 변화 | 저장·제출·승인 후 바뀌는 상태와 부작용 |
| 성공 | 독자가 화면·보고서·로그에서 다시 읽을 수 있는 결과 |
| 위험 | 결제, 청구, 재고, 삭제, 권한, 개인정보, 규제 판단 |
| 근거 | 공식 문서, 저장소, UI, 런타임, 운영자 확인, 추론 |

근거 등급:

- `source`: 공식 문서, 코드, 설정, 버전 고정 저장소
- `ui`: 실제 제품 화면·캡처·표시 값
- `runtime`: API, 로그, 상태, 데이터베이스 readback
- `operator-confirmed`: 책임 있는 운영자의 명시적 확인
- `inference`: 앞 근거에서 합리적으로 추론했지만 직접 확인하지 못함

근거가 없는 동작을 일반적인 제품 관행으로 채우지 않는다. UI나 런타임을 확인하지 못한 절차는 `provisional`로 제한한다.

## 2. 업무 흐름 설계

화면·메뉴 목록부터 쓰지 않는다. 각 흐름을 다음으로 표현한다.

```text
trigger → 준비/기준 데이터 → 실행 → 검토/승인 → 결과/감사
```

각 흐름에는 다음이 있어야 한다.

- 업무 목표와 시작 조건
- 참여 역할과 책임 교대
- 실행 순서와 건너뛰기·분기 조건
- 상태·문서·데이터 변화
- 성공을 증명하는 최종 readback
- 실패·되돌리기·에스컬레이션 경계

한 화면에서 여러 업무를 처리한다면 화면 단위로 lesson을 합치지 말고 결과가 다른 업무 단위로 나눈다. 반대로 한 업무가 여러 화면을 거치면 하나의 흐름으로 묶는다.

## 3. 초보자 시스템 개요

`overview.html`은 내부 아키텍처 덤프가 아니다. 상세 lesson 전에 필요한 정신 모형을 제공한다.

- 제품/시스템을 한 문장으로 정의
- 사용자 역할과 책임
- 주요 구성요소와 보이는 화면의 관계
- 요청·문서·데이터 생명주기
- 처음 접하는 사람이 자주 하는 오해와 올바른 판단
- 어떤 흐름부터 읽을지 안내

정신 모형은 일상 비유를 사용할 수 있지만 실제 상태 변화와 충돌하면 안 된다. 구성요소·생명주기는 CSS 다이어그램, 흐름도, 실제 화면 중 하나로 시각화한다.

## 4. 독립 lesson 깊이

lesson은 index 카드보다 깊어야 한다. 다음 구획을 고정한다.

1. 이 작업의 목적
2. 언제 사용하는가
3. 시작 전 준비
4. 안전 경계
5. 실행 단계
6. 화면·매체 증거
7. 주의할 점
8. 흔한 실수
9. 완료 확인
10. 근거
11. 다음 분기

각 단계는 세 칸으로 작성한다.

| 필드 | 질문 |
| --- | --- |
| `operation` | 이 단계가 읽기 전용(`read`)인가, 상태 변경(`write`)인가 |
| `action` | 독자가 무엇을 읽고 입력하거나 선택하는가 |
| `evidence` | 어떤 화면·문서·값이 그 행동과 현재 상태를 증명하는가 |
| `success` | 어떤 가시적 결과가 단계 완료를 증명하는가 |
| `readback` | `write` 후 어떤 ID·상태·부작용을 다시 읽어 변경 결과를 증명하는가 |

“확인한다”, “처리한다”처럼 목적어와 판정 기준이 없는 문장은 실패다. 버튼 이름만 나열하지 말고 행동 전 조건과 행동 후 결과를 연결한다.

## 5. 상태 변경과 전문 영역

상태 변경은 읽기 전용 조사보다 높은 권한을 요구한다.

- 위험도 `none/low/medium`: 실제 영향을 검토하고 필요한 경우 승인 경계를 둔다.
- 위험도 `high/critical`: `approval_required: true`와 안전 fixture가 필수다.
- 모든 단계는 `operation: read|write`를 선언한다. `write`는 high/critical 위험도, 승인, 안전 fixture, `readback`이 모두 없으면 빌드하지 않는다.
- 테스트 데이터는 고유 식별자를 사용하고 실행 전후 상태를 기록한다.
- 취소·되돌리기 가능 여부와 데이터 잔존 여부를 확인한다.
- 결제·원장·재고·권한 등 간접 부작용을 별도로 readback한다.

회계·세무·법률·의료·보안 영역은 UI 조작이 규정 준수 판정을 대신하지 않는다고 밝히고 전문 검토가 필요한 부분을 분리한다.

## 6. 상태와 인계

사용자 화면에는 제작 과정 용어를 노출하지 않는다. 검증 제한과 미완료 범위는 `STATUS.md`, 실행·판본·검증 위치는 `HANDOFF.md`에 기록한다.

상태 정의:

- `draft`: 구조·근거를 수집 중이며 배포하지 않음
- `provisional`: 자동 검증은 가능하지만 UI/런타임/시각 중 일부가 미확인
- `final`: 핵심 흐름 근거, 기술·내용 검증, 시각·사용성 범위가 모두 기록됨

`final` 표시는 소유자 승인이나 도구 실행을 암시하지 않는다. 실제로 수행한 검증만 적는다.
