## CHAPTER 15 · 구글 드라이브 설계

### 들어가며
구글 드라이브는 사용자가 다양한 기기에서 파일을 저장하고, 접근하고, 공유할 수 있게 하는 클라우드 기반 파일 저장·동기화 서비스다. 이 장에서는 다음 기능을 갖춘 확장 가능한 시스템 설계를 다룬다:
- **파일 업로드와 다운로드**
- **기기 간 파일 동기화**
- **파일 공유**
- **파일 수정 이력**
- **수정·삭제·공유 알림**

### 1단계: 문제 이해

#### 핵심 요구사항
#### 기능 요구사항:
- 파일을 업로드하고 다운로드한다.
- 여러 기기에 걸쳐 파일을 동기화한다.
- 파일 수정 이력을 관리한다.
- 권한과 함께 파일 공유를 가능하게 한다.
- 파일 수정·삭제·공유 시 알림을 보낸다.

#### 비기능 요구사항:
- **신뢰성:** 데이터 유실은 용납되지 않는다.
- **빠른 동기화 속도:** 동기화 지연으로 사용자가 답답해하지 않게 한다.
- **대역폭 효율:** 불필요한 데이터 사용을 최소화한다.
- **확장성:** 일일 활성 사용자(DAU) 10 million 명을 처리한다.
- **고가용성:** 서버 장애나 네트워크 문제 중에도 끊김 없이 동작한다.

#### 제약과 가정
- 사용자에게는 **10 GB 무료 공간**이 주어진다.
- 최대 파일 크기: **10 GB**.
- 평균 파일 업로드 크기: **500 KB**.
- 업로드 빈도: **사용자당 하루 2개 파일**.
- 필요한 총 저장소: **500 PB**.

### 2단계: 개략적 설계
#### 단일 서버 구성
기본 구성은 다음을 포함한다:
1. **웹 서버:** 업로드와 다운로드를 처리한다.
2. **메타데이터 데이터베이스:** 사용자 데이터, 로그인 정보, 파일 정보 같은 메타데이터를 관리한다.
3. **저장 디렉터리:** 네임스페이스별로 정리된 파일을 보관한다.

![](images/namespaces.png)

- 웹 서버와, 업로드된 파일을 저장하는 루트 디렉터리 역할을 하는 drive/라는 디렉터리를 둔다.
- drive/ 디렉터리 아래에는 네임스페이스라 부르는 디렉터리 목록이 있다.
- 각 네임스페이스는 해당 사용자가 업로드한 모든 파일을 담는다.
- 각 파일이나 폴더는 네임스페이스와 상대 경로를 합쳐 고유하게 식별할 수 있다.

이 설계는 출발점이 되지만 확장에는 부적합하다.

#### API
1. **구글 드라이브에 파일 업로드:** 두 가지 업로드 방식을 지원한다
    - 단순 업로드: 파일 크기가 작을 때 사용한다.
    - 이어 올리기(resumable upload):
        - 엔드포인트: https://api.example.com/files/upload?uploadType=resumable
        - 최초 요청을 보내 이어 올리기 URL을 받는다.
        - 데이터를 업로드하고 업로드 상태를 추적한다
        - 업로드가 중단되면 이어서 올린다.
2. **구글 드라이브에서 파일 다운로드:** 파일을 내려받으려면
    -  엔드포인트: https://api.example.com/files/download
3. **파일 수정 이력 조회:**
    - 엔드포인트: https://api.example.com/files/list_revisions

#### 분산 시스템으로 전환

#### 개선 사항:
1. **샤딩:** `user_id` 기준으로 저장소를 여러 서버에 나눈다.
2. **Amazon S3:** 리전 간 복제로 확장 가능하고 중복성 있는 파일 저장을 위해 S3를 사용한다.

    ![](images/replication.png)

3. **로드밸런서:** 트래픽을 여러 웹 서버에 분산한다.
4. **메타데이터 데이터베이스 복제:** 데이터베이스 샤딩과 복제로 가용성을 보장한다.

#### 동기화 충돌:
구글 드라이브 같은 대규모 저장 시스템에서는 동기화 충돌이 종종 발생한다.
두 사용자가 같은 파일이나 폴더를 동시에 수정하면 충돌이 일어난다.

![](images/sync-conflicts.png)

- 이 예에서 사용자 1과 사용자 2가 같은 파일을 동시에 갱신하려 하지만, 시스템은 사용자 1의 파일을 먼저 처리한다.
- 사용자 1의 갱신 연산은 통과하지만, 사용자 2는 동기화 충돌을 겪는다.
- 시스템은 같은 파일의 두 사본, 즉 사용자 2의 로컬 사본과 서버의 최신 버전을 함께 보여준다.
- 사용자 2는 두 파일을 병합하거나 한쪽 버전으로 다른 쪽을 덮어쓸 수 있다.

#### 개선된 설계

![](images/high-level-design.png)

1. **사용자 상호작용:** 사용자는 브라우저나 모바일 앱으로 애플리케이션에 접근한다.

2. **블록 서버:**
   - 파일은 **4 MB 블록**(최대 크기)으로 나뉘고 고유한 해시 값이 할당된다.
   - 블록은 클라우드 저장소(예: Amazon S3)에 독립적으로 저장된다.
   - 파일 복원은 블록을 정해진 순서로 이어 붙이는 방식으로 이루어진다.

3. **클라우드 저장소:** 확장성과 중복성을 위해 블록을 클라우드 저장소에 저장한다.

4. **콜드 스토리지:** 비활성 파일은 비용을 줄이기 위해 콜드 스토리지로 옮긴다.

5. **로드밸런서:** 요청을 API 서버들에 고르게 분배해 효율적 운영을 보장한다.

6. **API 서버:**
   - 사용자 인증, 프로필 관리, 파일 메타데이터 갱신을 처리한다.
   - 업로드 외의 모든 워크플로를 관리한다.

7. **메타데이터 데이터베이스와 캐시:**
   - 사용자, 파일, 블록, 버전의 메타데이터를 저장한다.
   - 자주 접근하는 메타데이터는 빠른 조회를 위해 캐시한다.

8. **알림 서비스:**
   - 파일 변경(추가, 수정, 삭제)을 클라이언트에 알리는 **발행/구독(pub/sub) 시스템**이다.
   - 클라이언트가 최신 갱신을 가져올 수 있게 보장한다.

9. **오프라인 백업 큐:** 오프라인 클라이언트를 위해 파일 변경 정보를 임시 저장하며, 다시 온라인이 되면 동기화한다.

### 3단계: 상세 설계

#### 메타데이터 데이터베이스
아래는 크게 단순화한 버전으로, 가장 중요한 테이블과 필드만 담고 있다.
#### 스키마 설계:
- **User 테이블:** 사용자 프로필과 설정을 저장한다.
- **File 테이블:** 파일 메타데이터(예: 크기, 이름, 경로)를 관리한다.
- **Block 테이블:** 파일 복원을 위한 파일 블록을 추적한다.
- **File Version 테이블:** 파일 수정 이력을 저장한다.

![](images/metadata-database.png)

#### 파일 업로드 흐름

1. **파일 업로드:**
   - 파일은 블록 서버에 의해 블록으로 나뉘고 압축·암호화된다.
   - 블록은 블록 서버로 업로드되어 S3에 저장된다.
2. **메타데이터 업로드:**
   - 클라이언트가 API 서버로 메타데이터를 보낸다.
   - 메타데이터는 상태 `pending`으로 데이터베이스에 저장된다.
3. **완료:**
   - S3가 콜백을 발동해 파일 상태를 `uploaded`로 갱신한다.
   - 알림 서비스가 관련 사용자에게 알린다.

![](images/upload-flow.png)

#### 파일 동기화
1. **델타 동기화:** 파일 전체 대신 수정된 블록만 전송한다.

    ![](images/delta-sync.png)

2. **압축:** 블록은 파일 유형에 따라 압축 알고리즘으로 압축된다.
3. **충돌 해결:**
   - 먼저 처리된 버전이 이긴다.
   - 충돌하는 버전은 사용자가 해결할 수 있도록 따로 저장된다.

![](images/file-sync.png)

#### 파일 다운로드 흐름
다운로드 흐름은 파일이 다른 곳에서 추가되거나 수정될 때 촉발된다. 클라이언트가 이를 알 수 있는 방법은 두 가지다:
- 다른 클라이언트가 파일을 변경한 시점에 클라이언트 A가 온라인이면, 알림 서비스가 클라이언트 A에 알린다.
- 다른 클라이언트가 파일을 변경한 시점에 클라이언트 A가 오프라인이면, 데이터가 캐시에 저장된다. 오프라인 클라이언트가 다시 온라인이 되면 최신 변경 사항을 당겨온다.

클라이언트는 파일이 변경된 사실을 알면 먼저 API 서버를 통해 메타데이터를 요청한 뒤, 블록을 내려받아 파일을 만든다.

1. **촉발:** 알림 서비스가 클라이언트에 파일 갱신을 알린다.
2. **메타데이터 조회:** 클라이언트가 API로 갱신된 메타데이터를 가져온다.
3. **블록 다운로드:** 클라이언트가 블록 서버에서 갱신된 블록을 내려받아 파일을 복원한다.

![](images/download-flow.png)

#### 알림 서비스
1. **목적:** 클라이언트가 파일 변경을 최신 상태로 유지하게 한다.
2. **메커니즘:** 비동기 알림을 위해 **롱 폴링(long polling)**을 구현한다.
3. **예시:** 파일이 추가·수정·삭제되면 관련된 모든 클라이언트에 알림이 푸시된다.

#### 저장소 최적화
1. **중복 제거:** 해시 기반 비교로 계정 수준에서 중복 블록을 제거한다.
2. **버전 관리 전략:**
   - 저장하는 수정 버전 수를 제한한다.
   - 자주 수정되는 파일은 최신 버전을 우선한다.
3. **콜드 스토리지:** 거의 접근되지 않는 파일을 더 저렴한 저장소(예: Amazon S3 Glacier)로 옮긴다.

#### 장애 처리
1. **로드밸런서 장애:** 보조 로드밸런서가 활성화된다.
2. **블록 서버 장애:** 대기 중인 작업을 다른 서버에 재할당한다.
3. **메타데이터 데이터베이스 장애:**
   - 슬레이브 노드를 마스터로 승격한다.
   - 트래픽을 나머지 복제본으로 돌린다.
4. **클라우드 저장소 장애:** 리전 간 복제로 사용 불가능한 파일을 가져온다.
5. **알림 서비스 장애:** 클라이언트가 대체 서버에 다시 연결한다.
