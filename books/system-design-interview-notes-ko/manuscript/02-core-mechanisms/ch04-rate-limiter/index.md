## CHAPTER 04 · 처리율 제한 장치 설계

### 들어가며
이 장에서는 처리율 제한 장치(rate limiter)의 설계와 구현을 다룬다. 처리율 제한 장치는 클라이언트나 서비스가 보내는 트래픽의 처리율을 통제하는 시스템 구성 요소다. 처리율 제한 장치는 남용 방지, 비용 절감, 서버 자원의 안정성 보장에 필수적이다. 사용 예로는 게시물 제한, 계정 생성 제한, 보상 수령 제한 등이 있다.

### 처리율 제한의 이점
- **DoS 공격 방지:** 자원 고갈을 피하려고 과도한 호출을 차단한다.
- **비용 절감:** 불필요한 요청을 제한해 서버 비용을 줄인다.
- **과부하 방지:** 과도한 요청을 걸러 내 서버 성능을 안정화한다.

### 1단계: 문제 이해
#### 핵심 기능
- 서버 측 API 처리율 제한 장치.
- 여러 스로틀(throttle) 규칙 지원.
- 분산 환경에서 대규모 시스템 처리.
- 독립 서비스 또는 애플리케이션 수준 코드 선택지.
- 스로틀 시 사용자에게 알림.

#### 요구사항
- 정확한 요청 스로틀링.
- 최소한의 지연 시간.
- 낮은 메모리 사용량.
- 분산 처리 능력.
- 명확한 예외 처리.
- 높은 장애 감내성.

### 2단계: 개략적 설계
#### 배치 옵션

![](images/rate_limiter_architecture.png)

1. **클라이언트 측 구현:** 오용 가능성 때문에 신뢰할 수 없다.
2. **서버 측 구현:** 통제와 신뢰성 면에서 선호된다.
3. **미들웨어(API 게이트웨이):** 통합 처리율 제한을 위한 유연한 선택지.

#### 배치 가이드라인
- 현재 기술 스택을 평가하고 효율적인 선택지를 고른다.
- 비즈니스 요구에 따라 적절한 알고리즘을 선택한다.
- 마이크로서비스를 사용한다면 API 게이트웨이를 사용한다.
- 자원이 부족하다면 상용 솔루션을 선택한다.

### 3단계: 처리율 제한 알고리즘
#### 1. 토큰 버킷(token bucket)

![](images/token-bucket.png)

- **설명:** 고정된 속도로 버킷에 토큰을 추가하며, 요청 하나가 토큰 하나를 소비한다.
- **파라미터:** 버킷 크기와 리필 속도.
- **장점:** 구현이 쉽고, 메모리 효율적이며, 트래픽 버스트를 수용한다.
- **단점:** 파라미터를 신중하게 조율해야 한다.

#### 2. 누출 버킷(leaking bucket)

![](images/leaking-bucket.png)

- **설명:** FIFO 큐를 사용해 고정된 속도로 요청을 처리한다.
- **장점:** 메모리 효율적, 안정적인 유출 속도.
- **단점:** 트래픽 버스트가 최근 요청을 지연시킬 수 있다.

  예시: https://github.com/uber-go/ratelimit

#### 3. 고정 윈도 카운터(fixed window counter)

![](images/fixed-window-counter.png)

- **설명:** 시간을 고정된 간격으로 나누고 카운터를 사용해 요청을 제한한다.
- **장점:** 단순하며 특정 사용 사례에 효율적이다.
- **단점:** 윈도 경계에서 트래픽 급증이 한도를 초과할 수 있다.

- 시간 윈도 경계에서 갑작스러운 트래픽 버스트가 허용된 할당량보다 많은 요청을 통과시킬 수 있다.

![](images/fixed-window-issue.png)

#### 4. 이동 윈도 로그(sliding window log)

![](images/sliding-window-log.png)

- **설명:** 타임스탬프를 추적해 이동하는 시간 윈도를 만든다.
- **장점:** 정확한 처리율 제한.
- **단점:** 높은 메모리 소비.

#### 5. 이동 윈도 카운터(sliding window counter)

![](images/sliding-window-counter.png)

- **설명:** 고정 윈도와 이동 로그 방식을 결합해 급증을 완화한다.
- **장점:** 메모리 효율적, 트래픽 버스트 처리.
- **단점:** 근사치이므로 완벽하게 엄격하지 않을 수 있다.

### 개략적 아키텍처

![](images/architecture.png)

- **데이터 저장소:** 빠른 카운터 연산을 위해 인메모리 캐싱(예: Redis)을 사용한다.
- **단계:**
  1. 클라이언트가 미들웨어로 요청을 보낸다.
  2. 미들웨어가 Redis의 카운터를 확인한다.
  3. 한도에 따라 요청이 처리되거나 거부된다.

### 추가 고려사항
#### 분산 환경
- **과제:** 경쟁 상태(race condition), 동기화 문제.
- **해결책:** Redis에서 락, Lua 스크립트, 정렬된 집합(sorted set)을 사용한다. 동기화를 위해 중앙 집중형 데이터 저장소를 둔다.

#### 성능 최적화
- 지연 시간 감소를 위한 다중 데이터 센터 구성.
- 동기화를 위한 결과적 일관성(eventual consistency) 모델.

#### 모니터링
- 알고리즘의 효과를 확인하고 필요에 따라 규칙을 조정하기 위한 정기적인 분석.
