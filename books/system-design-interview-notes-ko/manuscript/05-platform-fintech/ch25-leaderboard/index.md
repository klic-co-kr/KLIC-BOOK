## CHAPTER 25 · 실시간 게임 리더보드 설계

### 소개

온라인 모바일 게임을 위한 **리더보드(leaderboard)**를 설계한다:

![](images/leaderboard.png)

### 1단계: 문제 이해와 설계 범위 확정

- 지원자: 리더보드 점수는 어떻게 계산하나요?
- 면접관: 사용자가 경기에서 이길 때마다 점수를 얻습니다.
- 지원자: 모든 플레이어가 리더보드에 포함되나요?
- 면접관: 네.
- 지원자: 리더보드에 연결된 시간 구분이 있나요?
- 면접관: 매월 새 토너먼트가 시작되며 새 리더보드가 시작됩니다.
- 지원자: 상위 10명만 신경 쓰면 된다고 가정해도 되나요?
- 면접관: 상위 10명과 특정 사용자의 위치를 보여 주고 싶습니다. 시간이 되면 특정 사용자 주변의 사용자를 리더보드에서 보여 주는 것도 논의할 수 있습니다.
- 지원자: 토너먼트에는 몇 명이 참가하나요?
- 면접관: DAU 500만, MAU 2,500만입니다.
- 지원자: 토너먼트 기간에 평균 몇 경기가 진행되나요?
- 면접관: 플레이어마다 하루 평균 10경기를 합니다.
- 지원자: 두 플레이어의 점수가 같으면 순위는 어떻게 정하나요?
- 면접관: 그 경우 순위는 같습니다. 시간이 되면 동점 처리를 논의할 수 있습니다.
- 지원자: 리더보드는 실시간이어야 하나요?
- 면접관: 네, 실시간 또는 실시간에 최대한 가까운 결과를 제시하고 싶습니다. 배치로 처리한 과거 결과를 보여 주는 것은 안 됩니다.

#### **기능 요구사항**

- 리더보드에 상위 10명의 플레이어를 표시한다.
- 특정 사용자의 순위를 보여 준다.
- 주어진 사용자 기준 위아래 4순위에 있는 사용자를 표시한다(보너스).

#### **비기능 요구사항**

- 점수의 실시간 갱신.
- 점수 갱신이 리더보드에 실시간으로 반영된다.
- 일반적인 규모 확장성, 가용성, 신뢰성.

#### **개략적 규모 추정**

DAU 5,000만 명이고 24시간 동안 플레이어가 고르게 분포한다면, 평균 초당 50명이다.
하지만 분포가 보통 고르지 않으므로, 최대 온라인 사용자는 초당 250명으로 추정할 수 있다.

득점 사용자 QPS - 하루 평균 10경기이므로, 50 users/s * 10 = 500 QPS. 최대 QPS = 2500.

리더보드 상위 10명 조회 QPS - 하루 평균 한 번 연다고 가정하면 QPS는 50이다.

### 2단계: 개략적 설계안 제시 및 동의 얻기

#### **API 설계**

필요한 첫 API는 사용자 점수를 갱신하는 것이다:

```
POST /v1/scores
```

이 API는 두 파라미터를 받는다 - `user_id`와 승리로 얻은 점수 `points`.

이 API는 최종 클라이언트가 아니라 게임 서버만 접근할 수 있어야 한다.

다음은 리더보드 상위 10명을 가져오는 API다:

```
GET /v1/scores
```

응답 예시:

```
{
  "data": [
    {
      "user_id": "user_id1",
      "user_name": "alice",
      "rank": 1,
      "score": 12543
    },
    {
      "user_id": "user_id2",
      "user_name": "bob",
      "rank": 2,
      "score": 11500
    }
  ],
  ...
  "total": 10
}
```

특정 사용자의 점수를 가져올 수도 있다:

```
GET /v1/scores/{:user_id}
```

응답 예시:

```
{
    "user_info": {
        "user_id": "user5",
        "score": 1000,
        "rank": 6,
    }
}
```

#### **개략적 아키텍처**

![](images/high-level-architecture.png)

- 플레이어가 경기에서 이기면 클라이언트가 게임 서비스로 요청을 보낸다.
- 게임 서비스는 승리가 유효한지 검증하고 리더보드 서비스를 호출해 플레이어 점수를 갱신한다.
- 리더보드 서비스는 리더보드 저장소의 사용자 점수를 갱신한다.
- 플레이어는 리더보드 서비스를 호출해 리더보드 데이터(예: 상위 10명과 해당 플레이어의 순위)를 가져온다.

검토한 대안 설계는 클라이언트가 리더보드 서비스에서 자기 점수를 직접 갱신하는 것이다:

![](images/alternative-design.png)

이 선택지는 중간자(man-in-the-middle) 공격에 취약해 안전하지 않다. 플레이어가 프록시를 두고 마음껏 점수를 바꿀 수 있다.

한 가지 추가 유의점은, 게임 로직을 서버가 관리하는 게임에서는 클라이언트가 승리를 기록하려고 서버를 명시적으로 호출할 필요가 없다는 것이다.
서버가 게임 로직에 따라 자동으로 처리한다.

또 하나의 고려사항은 게임 서버와 리더보드 서비스 사이에 메시지 큐를 둘지다. 다른 서비스가 게임 결과에 관심이 있다면 유용하겠지만, 지금까지 면접에서 명시적 요구사항은 아니므로 설계에 포함하지 않았다:

![](images/message-queue-based-comm.png)

#### **데이터 모델**

리더보드 데이터 저장 옵션을 논의해 보자 - 관계형 DB, Redis, NoSQL.

NoSQL 해법은 상세 설계 섹션에서 다룬다.

#### 관계형 데이터베이스 해법

규모가 중요하지 않고 사용자가 그리 많지 않다면 관계형 DB로도 충분하다.

간단한 리더보드 테이블에서 시작할 수 있다. 매월 하나씩 만든다(개인적 소감 - 이건 말이 안 된다. `month` 컬럼 하나만 추가하면 매달 새 테이블을 관리하는 골칫거리를 피할 수 있다):

![](images/leaderboard-table.png)

추가로 넣을 데이터가 더 있지만, 실행할 질의와 무관하므로 생략했다.

사용자가 득점하면 무슨 일이 일어날까?

![](images/user-wins-point.png)

테이블에 사용자가 아직 없다면 먼저 삽입해야 한다:

```
INSERT INTO leaderboard (user_id, score) VALUES ('mary1934', 1);
```

이후 호출에서는 점수만 갱신하면 된다:

```
UPDATE leaderboard set score=score + 1 where user_id='mary1934';
```

리더보드의 상위 플레이어는 어떻게 찾을까?

![](images/find-leaderboard-position.png)

다음 질의를 실행할 수 있다:

```
SELECT (@rownum := @rownum + 1) AS rank, user_id, score
FROM leaderboard
ORDER BY score DESC;
```

하지만 데이터베이스 테이블의 모든 레코드를 정렬하려고 테이블 스캔을 하므로 성능이 좋지 않다.

`score`에 인덱스를 추가하고 `LIMIT` 연산을 써서 전체 스캔을 피하도록 최적화할 수 있다:

```
SELECT (@rownum := @rownum + 1) AS rank, user_id, score
FROM leaderboard
ORDER BY score DESC
LIMIT 10;
```

하지만 이 방식은 사용자가 리더보드 상위권이 아니고 그 순위를 찾으려 할 때는 확장성이 좋지 않다.

#### Redis 해법

수백만 플레이어에게도 잘 동작하면서 복잡한 데이터베이스 질의로 되돌아가지 않아도 되는 해법을 찾고자 한다.

Redis는 메모리 기반 데이터 저장소다. 메모리에서 동작해 빠르고, 우리 필요에 맞는 자료 구조인 정렬된 집합(sorted set)을 제공한다.

정렬된 집합은 프로그래밍 언어의 집합(set)과 비슷한 자료 구조로, 주어진 기준으로 정렬된 상태를 유지할 수 있다.
내부적으로는 키(user_id)와 값(score)의 매핑을 유지하는 해시맵과, 점수를 정렬된 순서로 사용자에 매핑하는 스킵 리스트(skip list)로 구현된다:

![](images/sorted-set.png)

스킵 리스트는 어떻게 동작하나?
- 빠른 탐색이 가능한 연결 리스트다.
- 정렬된 연결 리스트와 다단계 인덱스로 이루어진다.

![](images/skip-list.png)

이 구조는 데이터셋이 충분히 클 때 특정 값을 빠르게 탐색하게 해 준다.
아래 예(64노드)에서 기본 연결 리스트는 해당 값을 찾는 데 62개 노드를 순회해야 하지만, 스킵 리스트에서는 11개 노드면 된다:

![](images/skip-list-performance.png)

정렬된 집합은 데이터가 항상 정렬된 상태로 유지되므로 관계형 데이터베이스보다 성능이 좋다. 추가·탐색 연산에 O(logN)의 비용을 치르는 것이다.

비교를 위해, 관계형 DB에서 특정 사용자의 순위를 찾으려 실행해야 하는 중첩 질의 예시다:

```
SELECT *,(SELECT COUNT(*) FROM leaderboard lb2
WHERE lb2.score >= lb1.score) RANK
FROM leaderboard lb1
WHERE lb1.user_id = {:user_id};
```

Redis에서 리더보드를 운영하려면 어떤 연산이 필요한가?
- **ZADD** - 집합에 사용자가 없으면 삽입한다. 있으면 점수를 갱신한다. 시간 복잡도 O(logN).
- **ZINCRBY** - 사용자 점수를 주어진 양만큼 증가시킨다. 사용자가 없으면 점수는 0에서 시작한다. 시간 복잡도 O(logN).
- **ZRANGE/ZREVRANGE** - 점수로 정렬된 사용자 범위를 가져온다. 순서(ASC/DESC), 오프셋, 결과 크기를 지정할 수 있다. 시간 복잡도 O(logN+M), M은 결과 크기.
- **ZRANK/ZREVRANK** - 주어진 사용자의 위치(순위)를 ASC/DESC 순으로 가져온다. 시간 복잡도 O(logN).

사용자가 득점하면?

```
ZINCRBY leaderboard_feb_2021 1 'mary1934'
```

매월 새 리더보드가 만들어지고 오래된 리더보드는 과거 저장소로 옮겨진다.

사용자가 상위 10명을 가져오면?

```
ZREVRANGE leaderboard_feb_2021 0 9 WITHSCORES
```

결과 예시:

```
[(user2,score2),(user1,score1),(user5,score5)...]
```

사용자가 자기 리더보드 위치를 가져오는 경우는?

![](images/leaderboard-position-of-user.png)

사용자의 리더보드 위치를 안다는 전제 아래, 다음 질의로 쉽게 해결할 수 있다:

```
ZREVRANGE leaderboard_feb_2021 357 365
```

사용자 위치는 `ZREVRANK <user-id>`로 가져올 수 있다.

저장소 요구사항을 살펴보자:
- 한 달간 MAU 2,500만 명 전원이 게임에 참여하는 최악의 시나리오를 가정하면
- ID는 24글자 문자열, 점수는 16비트 정수이므로 26 bytes * 25mil = 약 650MB의 저장소가 필요하다
- 스킵 리스트 오버헤드로 저장 비용이 두 배가 되더라도 현대 Redis 클러스터에는 무리 없이 들어간다

고려할 다른 비기능 요구사항은 초당 2,500회 갱신 지원이다. Redis 서버 한 대의 능력 안에 충분히 든다.

추가 유의점:
- Redis 서버가 크래시할 때 데이터를 잃지 않도록 Redis 복제본을 띄울 수 있다.
- 크래시 시 데이터 손실을 막기 위해 Redis 영속성(persistence)을 활용할 수도 있다.
- 사용자 이름·표시 이름 같은 사용자 상세 정보를 가져오고 사용자가 언제 경기에서 이겼는지 저장하려면 MySQL에 보조 테이블 두 개가 필요하다.
- MySQL의 두 번째 테이블은 인프라 장애 시 리더보드를 재구성하는 데 쓸 수 있다.
- 작은 성능 최적화로, 자주 접근되는 상위 10명의 사용자 상세 정보를 캐시할 수 있다.

### 3단계: 상세 설계

#### **클라우드 제공자를 쓸지 말지**

서비스를 직접 배포·관리하거나, 클라우드 제공자에게 관리를 맡길 수 있다.

직접 관리하기로 하면, 리더보드 데이터에는 Redis를, 사용자 프로필에는 MySQL을 쓰고, 데이터베이스 확장이 필요하면 사용자 프로필 캐시를 추가할 수 있다:

![](images/manage-services-ourselves.png)

대안으로, 클라우드 서비스를 활용해 상당수 서비스의 관리를 맡길 수 있다. 예를 들어 AWS API Gateway로 API 호출을 AWS Lambda 함수로 라우팅할 수 있다:

![](images/api-gateway-mapping.png)

AWS Lambda는 서버를 직접 관리·프로비저닝하지 않고 코드를 실행하게 해 준다. 필요할 때만 실행되고 자동으로 확장된다.

사용자가 득점하는 예시:

![](images/user-scoring-point-lambda.png)

사용자가 리더보드를 가져오는 예시:

![](images/user-retrieve-leaderboard.png)

Lambda는 서버리스 아키텍처의 구현체다. 확장과 환경 설정을 관리할 필요가 없다.

저자는 게임을 처음부터 새로 만든다면 이 접근을 권한다.

#### **Redis 확장**

DAU 500만 명이면 저장소와 QPS 관점 모두에서 Redis 인스턴스 하나로 충분하다.

하지만 사용자가 10배로 늘어 DAU 5억 명이 되면 저장소 65GB가 필요하고 QPS는 250k로 올라간다.

이런 규모에는 샤딩이 필요하다.

한 가지 방법은 데이터를 범위로 분할하는 것이다:

![](images/range-partition.png)

이 예에서는 사용자 점수 기준으로 샤딩한다. user_id와 샤드의 매핑은 애플리케이션 코드에서 유지한다.
매핑 자체는 MySQL이나 다른 캐시로 둘 수 있다.

상위 10명을 가져오려면 가장 높은 점수의 샤드(`[900-1000]`)에 질의하면 된다.

사용자 순위를 가져오려면 해당 사용자 샤드 안의 순위를 계산하고, 다른 샤드에서 더 높은 점수의 사용자를 모두 더해야 한다.
후자는 샤드별 총 레코드 수를 info keyspace 명령으로 빠르게 얻을 수 있어 O(1) 연산이다.

대안으로 Redis Cluster를 통한 해시 파티셔닝을 쓸 수 있다. 안정 해시와 비슷하지만 완전히 같지는 않은 분할 방식으로 Redis 노드에 데이터를 분산하는 프록시다:

![](images/hash-partition.png)

이 구성에서는 상위 10명 계산이 까다롭다. 각 샤드의 상위 10명을 가져와 애플리케이션에서 결과를 병합해야 한다:

![](images/top-10-players-calculation.png)

해시 파티셔닝의 한계:
- 상위 K명을 가져와야 하고 K가 크면, 모든 샤드에서 많은 데이터를 가져와야 해 지연이 커질 수 있다.
- 파티션 수가 늘수록 지연이 커진다.
- 사용자 순위를 정하는 간단한 방법이 없다.

이런 이유로 저자는 이 문제에 고정 파티션 쪽으로 기운다.

그 밖의 유의점:
- 쓰기가 많은 Redis 노드에는 필요량의 두 배 메모리를 할당하는 것이 모범 사례다. 필요 시 스냅샷을 감당하기 위해서다.
- Redis-benchmark 도구로 Redis 구성의 성능을 추적하고 데이터에 기반한 결정을 내릴 수 있다.

#### **대안: NoSQL**

고려할 대안 하나는 다음에 최적화된 적절한 NoSQL 데이터베이스를 쓰는 것이다:
- 무거운 쓰기
- 같은 파티션 안 항목을 점수로 효과적으로 정렬

DynamoDB, Cassandra, MongoDB 모두 잘 맞다.

이 장에서 저자는 DynamoDB를 쓰기로 했다. 완전 관리형 NoSQL 데이터베이스로, 신뢰할 만한 성능과 훌륭한 확장성을 제공한다.
기본 키에 없는 필드로 질의해야 할 때 전역 보조 인덱스(global secondary index)도 쓸 수 있다.

![](images/dynamo-db.png)

체스 게임 리더보드를 저장하는 테이블에서 시작하자:

![](images/chess-game-leaderboard-table-1.png)

잘 동작하지만, 점수로 무엇을 질의해야 하면 확장성이 나쁘다. 그래서 점수를 정렬 키(sort key)로 둘 수 있다:

![](images/chess-game-leaderboard-table-2.png)

이 설계의 또 다른 문제는 월 단위 파티셔닝이다. 최신 월이 다른 달보다 불균형하게 접근되어 핫스팟 파티션이 생긴다.

쓰기 샤딩(write sharding)이라는 기법을 쓸 수 있다. 각 키에 `user_id % num_partitions`로 계산한 파티션 번호를 붙이는 것이다:

![](images/chess-game-leaderboard-table-3.png)

고려할 중요한 트레이드오프는 파티션 수다:
- 파티션이 많을수록 쓰기 확장성이 높아진다.
- 하지만 집계 결과를 모으려 더 많은 파티션에 질의해야 해 읽기 확장성은 나빠진다.

이 접근을 쓰려면 앞서 본 "스캐터-개더(scatter-gather)" 기법이 필요한데, 파티션을 추가할수록 시간 복잡도가 커진다:

![](images/scatter-gather-2.png)

파티션 수를 잘 평가하려면 벤치마킹이 필요하다.

이 NoSQL 접근에도 큰 단점 하나는 남는다 - 사용자의 구체적 순위를 계산하기 어렵다.

샤딩이 필요할 만큼 규모가 크다면, 사용자에게 자기 점수가 몇 "퍼센타일(percentile)"인지 알려 줄 수 있을 것이다.

cron 작업이 주기적으로 점수 분포를 분석하고, 이를 바탕으로 사용자의 퍼센타일을 정한다. 예:

```
10th percentile = score < 100
20th percentile = score < 500
...
90th percentile = score < 6500
```

### 4단계: 마무리

시간이 남으면 논의할 다른 주제:
- **더 빠른 조회** - `user_id -> user object` 매핑을 가진 Redis 해시로 사용자 객체를 캐시할 수 있다. 데이터베이스 질의보다 빠른 조회가 가능해진다.
- **동점 처리** - 두 플레이어의 점수가 같으면, 마지막으로 플레이한 경기를 기준으로 정렬해 동점을 가른다.
- **시스템 장애 복구** - 대규모 Redis 장애 시, MySQL WAL 엔트리를 훑어 임시 스크립트로 리더보드를 재구성할 수 있다.
