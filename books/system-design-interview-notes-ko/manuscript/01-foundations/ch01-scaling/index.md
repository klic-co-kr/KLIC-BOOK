## CHAPTER 01 · 0에서 수백만 사용자로의 확장

### 들어가며
수백만 사용자를 지원하도록 시스템을 확장하는 일은 다듬고 최적화해 나가야 하는 복잡하고 반복적인 여정이다. 이 장에서는 단일 서버 구성으로 시작해 단계별로 아키텍처를 확장하여 수백만 사용자를 처리하는 방법을 개관한다.

### 섹션 1: 단일 서버 구성
처음에는 모든 구성 요소(웹 앱, 데이터베이스, 캐시)가 단일 서버에서 실행된다.

![](images/single-server.png)

#### 요청 흐름
1. 사용자는 도메인 이름(예: `api.mysite.com`)을 통해 애플리케이션에 접근하며, DNS가 이를 IP 주소로 변환한다.
2. 웹 서버의 IP 주소가 브라우저나 모바일 앱으로 반환된다.
3. HTTP 요청이 웹 서버로 전송되면, 웹 서버는 HTML 또는 JSON 응답을 반환한다.

#### 트래픽 출처
1. **웹 애플리케이션:** 비즈니스 로직에는 서버 측 언어(예: Python, Java)를, 화면 표현에는 클라이언트 측 언어(예: JavaScript, HTML)를 사용한다.
2. **모바일 애플리케이션:** HTTP와 JSON을 사용해 웹 서버와 통신하며 가벼운 데이터를 주고받는다.

### 섹션 2: 데이터베이스 분리
사용자층이 커지면 데이터베이스를 전용 서버로 옮겨 웹 계층과 데이터베이스 계층이 각각 독립적으로 확장되게 한다.

![](images/database.png)

#### 데이터베이스 선택

1. **관계형 데이터베이스(SQL):** 구조화된 데이터를 테이블에 저장한다. 예: MySQL, PostgreSQL.
2. **비관계형 데이터베이스(NoSQL):** 비정형 데이터나 낮은 지연 시간 요구사항에 적합하다. 카테고리는 다음과 같다:
   - 키-값 저장소(key-value store)
   - 그래프 데이터베이스
   - 컬럼 저장소
   - 문서 저장소

- 다음의 경우에는 비관계형 데이터베이스가 올바른 선택일 수 있다:
   - 애플리케이션이 아주 낮은 지연 시간을 요구한다.
   - 데이터가 비정형이거나 관계형 데이터가 없다.
   - 데이터를 직렬화·역직렬화하기만 하면 된다(JSON, XML, YAML 등).
   - 방대한 양의 데이터를 저장해야 한다.

### 섹션 3: 수직 확장 vs 수평 확장
#### 수직 확장
- 기존 서버에 더 많은 자원(CPU, RAM)을 추가한다.
- 하드웨어 제약으로 한계가 있으며 중복성이 부족하다.

#### 수평 확장
- 서버 풀에 서버를 더 추가하므로 대규모 시스템에 더 적합하다.
- 서버 간 요청 라우팅을 처리하기 위해 로드밸런서를 사용한다.

### 섹션 4: 로드밸런서

![](images/load-balancer.png)

**로드밸런서**는 여러 서버에 트래픽을 분산한다. 이점은 다음과 같다:
1. 중복성: 서버가 오프라인이 되면 트래픽이 우회된다.
   - 서버 1이 오프라인이 되면 모든 트래픽이 서버 2로 라우팅된다.
2. 확장성: 트래픽 급증에 대응해 서버를 손쉽게 추가한다.
   - 웹사이트 트래픽이 빠르게 늘어나면 서버를 계속 추가해 증가한 트래픽을 처리할 수 있다.

### 섹션 5: 데이터베이스 복제

![](images/database-replication.png)

#### 마스터-슬레이브 모델
- **마스터 데이터베이스:** 쓰기 연산을 처리한다.
   - insert, delete, update 같은 데이터 변경 명령은 모두 마스터 데이터베이스로 보내야 한다.
- **슬레이브 데이터베이스:** 읽기 연산을 처리하여 성능과 신뢰성을 높인다.
   - 대부분의 애플리케이션은 읽기가 쓰기보다 비율이 높기 때문에, 시스템에서 슬레이브 데이터베이스 수가 보통 마스터 데이터베이스 수보다 많다.

#### 이점
1. 병렬 읽기 연산을 통한 성능 향상.
2. 중복화를 통한 높은 가용성과 데이터 신뢰성.

#### 장애 처리
- 슬레이브 데이터베이스가 하나뿐인데 오프라인이 되면, 읽기 연산은 일시적으로 마스터 데이터베이스로 보낸다.
- 슬레이브 데이터베이스가 여러 개라면, 읽기 연산은 다른 정상 슬레이브 데이터베이스로 재전송되고 새 서버가 기존 서버를 대체한다.
- 마스터 데이터베이스가 오프라인이 되면, 슬레이브 데이터베이스 하나가 새 마스터로 승격된다.
- 프로덕션 시스템에서 선택된 슬레이브 데이터베이스가 최신 상태가 아닐 수 있으므로, 데이터 복구 스크립트를 실행해 데이터를 갱신해야 한다(multi-masters나 circular replication 같은 방법이 도움이 될 수 있다).

### 섹션 6: 캐시
**캐시**는 자주 접근되는 데이터를 메모리에 저장해 데이터베이스 부하를 줄인다. 캐시 계층은 임시 데이터 저장 계층으로, 데이터베이스보다 훨씬 빠르다.

![](images/cache.png)

#### 캐시 사용 시 고려사항
1. **사용 사례:** 데이터가 자주 읽히고 자주 변경되지 않는다면 캐시 사용을 고려한다.
2. **만료 정책:** 캐시된 데이터가 만료되면 캐시에서 제거된다. 만료 정책이 없으면 캐시된 데이터가 메모리에 영구히 저장된다.
3. **일관성:** 데이터 저장소와 캐시를 동기화 상태로 유지하는 것을 뜻한다. 데이터 저장소와 캐시에 대한 데이터 변경 연산이 단일 트랜잭션으로 묶여 있지 않기 때문에 불일치가 생길 수 있다.
4. **장애 완화:** 캐시 서버 하나는 잠재적 단일 장애 지점(single point of failure)이므로, SPOF를 피하려면 여러 데이터 센터에 걸쳐 캐시 서버를 여러 대 두는 것이 권장된다.
5. **축출 정책:** 캐시가 가득 차면 메모리를 확보하기 위해 항목을 축출해야 한다. LRU가 가장 널리 쓰이는 캐시 축출 정책이다.

### 섹션 7: 콘텐츠 전송 네트워크(CDN)
**CDN**은 정적 콘텐츠(이미지, CSS, JavaScript)를 지리적으로 분산된 서버에 캐시해 로드 시간을 개선한다.

![](images/cdn.png)

#### 동작 방식
1. 사용자가 가장 가까운 CDN 서버에 콘텐츠를 요청한다.
2. 콘텐츠가 없다면 원본(origin) 서버에서 가져와 캐시한다.

#### CDN 사용 시 고려사항
1. **비용:** CDN은 서드파티 제공자가 운영하며, CDN 안팎의 데이터 전송량만큼 비용을 청구한다.
2. **캐시 만료:** 캐시 만료 시간은 너무 길지도 짧지도 않아야 한다.
3. **CDN 폴백(fallback):** 일시적인 CDN 장애가 발생하면 클라이언트가 문제를 감지하고 원본 서버에서 리소스를 요청할 수 있어야 한다.
4. **파일 무효화:** 파일이 갱신되면 갱신된 파일을 가리키도록 캐시를 무효화해야 한다.

### 섹션 8: 무상태 웹 계층
세션 데이터를 공유 데이터 저장소로 옮기면 웹 서버는 무상태(stateless)가 된다. 이를 통해 다음이 가능하다:
1. 더 쉬운 수평 확장.
2. 트래픽 기반 자동 확장.

![](images/stateless.png)

### 섹션 9: 다중 데이터 센터 구성
여러 데이터 센터에 걸쳐 배포하면 가용성이 높아지고 지연 시간이 줄어든다. 전략은 다음과 같다:

![](images/data-center.png)

1. **GeoDNS 라우팅:** 사용자를 가장 가까운 데이터 센터로 안내한다.
2. **데이터 복제:** 데이터 센터 간에 데이터를 동기화해 불일치를 방지한다.

#### 핵심 고려사항
- **트래픽 재전송:** 트래픽을 올바른 데이터 센터로 보낼 효과적인 도구가 필요하다.
- **데이터 동기화:** 일반적인 전략은 여러 데이터 센터에 데이터를 복제하는 것이다.
- **테스트와 배포:** 자동화된 배포 도구는 모든 데이터 센터에서 서비스를 일관되게 유지하는 데 필수적이다.

### 섹션 10: 메시지 큐
**메시지 큐**는 메모리에 저장되는 내구성 있는 구성 요소로, 비동기 통신을 지원한다. 버퍼 역할을 하며 비동기 요청을 분산한다.

![](images/message-queue.png)

- 생산자(producer)/발행자(publisher)라고 불리는 입력 서비스는 메시지를 만들어 메시지 큐에 발행한다.
- 소비자(consumer)/구독자(subscriber)라고 불리는 다른 서비스는 큐에 연결해 메시지에 정의된 동작을 수행한다.

### 섹션 11: 로그, 메트릭, 자동화

![](images/logging.png)

#### 중요성
1. **로그:** 오류와 시스템 상태를 추적한다.
2. **메트릭:** 성능과 사용자 활동에 대한 통찰을 제공한다.
3. **자동화:** 테스트, 배포, 확장을 간소화한다.

### 섹션 12: 데이터베이스 확장
#### 수직 확장
- 하드웨어 자원을 추가하지만 물리적·비용적 한계가 있다.
- 여러 단점이 있다:
   - 단일 장애 지점 위험이 커진다.
   - 수직 확장의 전체 비용이 높다.

#### 수평 확장(샤딩)

![](images/horizontal-scaling.png)

- 키(예: `user_id`)를 사용해 데이터를 여러 샤드로 나눈다.
   - 샤딩은 큰 데이터베이스를 샤드(shard)라고 불리는 더 작고 관리하기 쉬운 부분으로 나눈다.
   - 각 샤드는 같은 스키마를 공유하지만, 각 샤드에 저장된 실제 데이터는 그 샤드에 고유하다.
- 샤딩 전략을 구현할 때는 샤딩 키가 중요하다. 샤딩 키를 고를 때는 데이터를 고르게 분산할 수 있는 키를 선택하는 것이 중요하다.

#### 도전 과제
1. **리샤딩(resharding) 데이터:** 다음의 경우 리샤딩이 필요하다:
   - 급격한 성장으로 단일 샤드가 더는 데이터를 담을 수 없을 때.
   - 불균일한 데이터 분포 때문에 특정 샤드가 다른 샤드보다 빨리 샤드 고갈을 겪을 수 있을 때.
   - 이 문제를 극복하기 위해 일관성 해시(consistent hashing)를 사용한다.

2. **유명인(celebrity) 문제:** 특정 샤드에 대한 과도한 접근이 서버 과부하를 일으킬 수 있다.
   - 이 문제를 풀려면 유명인마다 샤드를 하나씩 할당해야 할 수 있다.

3. **조인과 비정규화:** 데이터베이스가 여러 서버에 샤딩되고 나면 샤드 간 조인 연산을 수행하기 어렵다.
   - 흔한 회피책은 쿼리를 단일 테이블에서 수행할 수 있도록 데이터베이스를 비정규화하는 것이다.

### 결론
#### 핵심 요약
1. 웹 계층을 무상태로 유지한다.
2. 모든 계층에 중복성을 구축한다.
3. 캐시와 CDN으로 성능을 최적화한다.
4. 샤딩으로 데이터 계층을 확장한다.
5. 유연성을 위해 구성 요소를 분리한다.

이 장은 수백만 사용자를 처리할 수 있는 확장 가능한 시스템을 구축하는 탄탄한 기초를 제공한다.
