# 6장 클러스터 성능·용량·벤치마크

성능 수치는 설계의 출발점이지만, 다른 시험과 단위를 같은 막대에 놓으면 판단을 망친다. FP8 EFlops, TOP500 Rmax·Rpeak, GPU 장수, TOP500 `cores`는 서로 다른 질문에 답한다.

[공식 발표 | SRC-003] NHN은 FP8 기준 27.4 EFlops를 제시했다. [공식 발표 | SRC-003, SRC-005] 7,656 B200 GPU와 4,080 GPU는 별도 발표 범위다. [원자료 | SRC-011] TOP500은 CL-1·CL-2의 Rmax·Rpeak·순위·`#Proc./Cores`를 공개한다. 이 값들은 같은 축에서 비율·합계·우열을 계산하지 않는다.

## Rmax와 Rpeak

[원자료 | SRC-012] TOP500은 Rmax를 LINPACK 시험에서 달성된 성능으로, Rpeak를 시스템의 이론적 최대 성능으로 설명하고 Rmax를 기준으로 목록을 정렬한다. 이 정의는 명확하지만 ‘해당 시스템이 모든 AI 작업에서 이만큼 빠르다’는 뜻은 아니다. LINPACK은 특정 선형대수 시험이고, 실제 학습·추론에는 모델 구조, 정밀도, 통신, 입력·출력, 메모리 용량, 재시도와 큐 대기가 더해진다.

[원자료 | SRC-011] 2026년 6월 목록에서 `NIPA(NHN Cloud)-CL-1`은 20위, Rmax 137.40 PFlop/s, Rpeak 156.48 PFlop/s로 기록됐다. 같은 목록의 `CL-2`는 40위, Rmax 68.42 PFlop/s, Rpeak 77.94 PFlop/s다. 이 네 성능 값은 같은 LINPACK 문맥 안에서 CL-1과 CL-2를 읽을 때만 비교할 수 있다. [설계 해석 | SRC-011, SRC-012] 두 값의 차이는 벤치마크 효율, 구성, 시험 조건을 살필 출발점이지, 특정 LLM 학습 시간 또는 사용자 요청 처리량의 배수로 곧장 바꿀 근거는 아니다.

> 차트 6-1은 LINPACK 지표만 사용한다. FP8 EFlops, GPU 장수, TOP500 `cores`는 데이터나 보조 축으로 넣지 않는다.

## FP8 EFlops의 별도 의미

[공식 발표 | SRC-003] 27.4 EFlops는 NHN이 FactoryX에 대해 FP8 기준으로 제시한 AI 연산 성능이다. ‘E’와 ‘P’는 접두어가 달라 숫자 크기를 환산할 수 있어 보이지만, 환산 가능한 접두어라는 사실은 벤치마크와 정밀도, 연산 정의, 시스템 경계까지 같다는 뜻이 아니다. FP8 AI 연산 성능과 TOP500 LINPACK Rmax·Rpeak는 측정 정밀도와 워크로드가 다르다. [원자료 | SRC-012] TOP500 수치는 LINPACK 정의로 읽어야 한다.

[설계 해석 | SRC-003, SRC-011, SRC-012] FP8 발표값과 CL-1의 LINPACK 수치를 한 그래프·비율로 만들면 다른 시험을 경쟁시키는 오류가 된다. FP8 발표값을 7,656 GPU 또는 4,080 GPU로 나눠 장치당 성능이라고 표현해서도 안 된다. 시스템 경계와 수량의 관계가 공개되지 않았기 때문이다.

[실무 제안] 대시보드는 FP8 발표, TOP500 LINPACK, 학습 완료 시간, 추론 SLO를 별도 카드로 둔다. 카드는 연결해도 공통 순위 축으로 합치지 않는다.

## 학습 성능

학습 성능의 질문은 ‘요구 품질로 언제 끝나는가’다. [설계 해석] `단계 시간 = 연산 + 통신 + 입력 + 대기·재시도`는 계측 항목을 빠뜨리지 않기 위한 운영 모델이며 공식 벤치마크가 아니다. 모델·batch·정밀도·병렬화·checkpoint·혼잡에 따라 각 항의 비중이 달라진다.

[원자료 | SRC-015] NCCL은 토폴로지 인지형 GPU collective를, [원자료 | SRC-016] GDS는 조건부 스토리지–GPU 직접 DMA 경로를 설명한다. [설계 해석 | SRC-015, SRC-016] 둘은 완료 시간 보증이 아니다. 시험에는 데이터셋·모델·드라이버 버전, 분산 방식, 참여 GPU, warm-up, 재시도를 남긴다.

[실무 제안] 학습 계획은 최고 token/s 대신 총 step, 허용 완료 시각, 재시도 예산, checkpoint 복구 시간을 먼저 정한다. 정상·혼잡·부분 장애 세 조건을 반복 측정해 보정한다.

| 학습 측정값 | 단위 예 | 어떤 결정을 돕는가 | 단독 해석의 위험 |
|---|---|---|---|
| step time | s/step | 병목 항목과 완료 시각 추정 | 모델·batch가 바뀌면 직접 비교 불가 |
| 통신 비중 | step 안의 시간 비율 | 병렬화·패브릭 검토 | 낮아도 입력·복구 병목이 남을 수 있음 |
| checkpoint 복구 | min 또는 s | 장애 허용 범위·보존 정책 | 저장 성공만으로 복구 가능성을 보장하지 않음 |
| 품질 도달 시각 | h, epoch, 검증 점수 | 업무 완료 조건 | 성능 수치가 품질을 대체하지 않음 |

## 추론 성능

추론은 평균 처리량만으로 사용자 경험을 설명하기 어렵다. 첫 응답, 토큰 간 지연, 긴 입력의 메모리·큐 압력, 오류·fallback 결과가 함께 보인다. [설계 해석] 배치 처리량을 높이면 지연이, 복제본을 줄이면 대기열이 커질 수 있으므로 학습 완료 시간과 추론 지연·처리량을 하나의 값으로 합치지 않는다.

[실무 제안] 추론 SLO는 첫 응답·생성 지연, 성공률, 품질·안전 통과율, 큐 대기, 요청당 가속기 시간으로 나눈다. 프롬프트·출력 길이, 동시성, 도구·캐시 여부를 함께 기록한다.

[미공개 | SRC-003, SRC-001] FactoryX 공식 공개 자료는 이 장에서 제시한 특정 모델의 추론 지연, token 처리량, 큐 정책, 서비스별 GPU 배치 값을 확인시키지 않는다. [설계 해석 | SRC-001, SRC-003] 공개된 27.4 EFlops를 개별 API의 SLO나 사용자당 처리량으로 환산하지 않는 이유도 여기에 있다.

| 추론 지표 | 측정 경계 | 주된 사용처 | 비교 조건 |
|---|---|---|---|
| 첫 응답 지연 | 요청 수신부터 첫 출력까지 | 대화형 서비스의 체감 응답 | 입력 길이·큐 상태·모델을 같게 둠 |
| 생성 지연 | 출력 토큰 사이의 시간 | 스트리밍 품질 | 출력 길이·배치 정책을 기록 |
| 요청 처리량 | 완료 요청 또는 토큰/시간 | 용량·비용 계획 | 품질·오류·지연 한계를 함께 둠 |
| 성공·품질 통과 | 정책·평가를 통과한 결과 | 업무 가치 확인 | 모델·평가 세트를 고정 |

## 용량 계획식

[설계 해석] 용량 계획은 GPU 장수에서 시작하지 않고 수요·완료 조건·손실 요인을 명시하는 식에서 시작한다. 한 기간의 필요한 GPU-시간을 단순화하면 `예상 작업 수 × 작업당 GPU 수 × 작업당 실행 시간`으로 적을 수 있다. 여기에 재시도, 운영 여유, 계획된 점검, 수요 피크, 예약 단위로 생기는 손실을 별도 항으로 더한다. 이 식은 실측 값이 아니라 가정을 공개하기 위한 틀이다. 숫자를 넣을 때에는 정상 조건과 혼잡·장애 조건을 같은 표에 섞지 않는다.

학습은 장시간 예약·복구 비용을, 추론은 짧은 피크·지연 SLO를 우선한다. [설계 해석 | SRC-011, SRC-015, SRC-016] 패브릭·스토리지 제한은 GPU가 남아도 시작·완료를 막을 수 있으므로 예약률만으로 여유를 정의하지 않는다.

| 계획 입력 | 기록 단위 | 보수적으로 잡아야 할 변수 | 검증 방법 |
|---|---|---|---|
| 수요 | job·request·token·기간 | 피크 집중, 계절성, 신규 모델 | 과거 구간과 제한 배포 재현 |
| 자원 요청 | GPU·GPU-hour·메모리 | GPU 형태, 노드 경계, 예약 최소 단위 | scheduler 요청과 실제 사용 비교 |
| 실행 시간 | s·min·h | 통신, I/O, 재시도, checkpoint | 정상·혼잡·장애 조건 분리 측정 |
| 완료 조건 | 마감·지연·성공률·품질 | p95/p99, 정책 실패, 사람 승인 | 업무 SLO와 기술 지표 연결 |
| 여유 | 비율 또는 절대 자원 | 점검, 장애, 긴급 작업 | 월별 가정 오차 회고 |

[실무 제안] 용량 회의에서는 세 결과를 함께 낸다. 첫째, 약속된 SLO를 충족하는 최소 자원이다. 둘째, 예상 수요에서 정상 운용하는 자원이다. 셋째, 한 rail·노드·스토리지 경로의 성능 저하를 견디는 자원이다. 세 결과 사이의 차이는 낭비가 아니라 장애 허용도와 사업 우선순위가 만든 비용이다.

## 설계 리뷰

| 리뷰 질문 | 필요한 증거 | 통과 판단 | 금지할 결론 |
|---|---|---|---|
| LINPACK 지표의 정의와 시험을 적었는가 | Rmax·Rpeak 정의와 출처 | TOP500 값을 같은 시험 안에서 읽음 | LINPACK을 LLM 처리량으로 번역 |
| FP8 지표를 별도 카드로 두었는가 | FP8·발표 주체·시스템 범위 | 27.4 EFlops의 의미를 보존 | PFlop/s와 공통 축·비율 생성 |
| GPU 수와 cores를 분리했는가 | 수량별 출처·범위·단위 | 발표 수량을 식별 정보로 사용 | 4,080·7,656·cores의 합산·환산 |
| 학습·추론 SLO를 실제로 측정했는가 | 모델·데이터·조건·p95/p99 | 완료 시간과 응답 품질을 확인 | 최고 벤치마크 하나로 용량 확정 |
| 장애 여유를 계획식에 넣었는가 | 정상·혼잡·장애 가정 표 | 가정 오차를 회고 가능 | 평균 사용률만으로 증설 결정 |

[설계 해석 | SRC-003, SRC-011, SRC-012] 좋은 성능 보고서는 하나의 ‘최대’ 수치보다 단위, 시험, 시스템 경계, 업무 완료 조건, 미확인 사항을 함께 남긴다. 그 형식이 있어야 하드웨어 발표와 운영 SLO가 서로를 과장하지 않고 연결된다.

## 핵심 요약

- [원자료 | SRC-012] Rmax는 LINPACK 실측, Rpeak는 이론적 peak이며 TOP500은 Rmax로 정렬한다.
- [원자료 | SRC-011] CL-1과 CL-2의 Rmax·Rpeak는 같은 LINPACK·PFlop/s 문맥에서만 읽는다. TOP500 cores는 GPU 장수나 CPU 물리 코어 수가 아니다.
- [공식 발표 | SRC-003] FactoryX의 27.4 EFlops는 FP8 기준의 별도 AI 연산 성능 발표다. TOP500 Rmax·Rpeak와 같은 축, 비율, 순위로 비교하지 않는다.
- [공식 발표 | SRC-001, SRC-003, SRC-005] 4,080 GPU와 7,656 B200 GPU는 발표 범위가 다른 수량이며 합산하거나 TOP500 시스템의 GPU 수로 추정하지 않는다.
- [실무 제안] 용량 계획은 GPU 수가 아니라 수요, 실행 시간, 통신·I/O, 재시도, SLO, 장애 여유를 명시한 가정과 반복 측정으로 갱신한다.
