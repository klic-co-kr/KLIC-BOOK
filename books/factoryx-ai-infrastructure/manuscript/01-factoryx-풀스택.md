# 1장 FactoryX를 읽는 법

FactoryX를 GPU의 수량표로 읽으면 중요한 질문을 놓친다. GPU는 연산을 담당하지만, 실제 업무 결과는 전력과 냉각의 여유, 노드와 네트워크의 데이터 이동, 자원 배정, 모델 배포, 권한과 감사의 연결 위에서 나온다. 이 장은 NHN이 공개한 FactoryX의 범위를 확인 가능한 사실로 한정하고, 그 사실을 투자·설계·운영 판단으로 번역하는 방법을 다룬다. 신청형 자료의 본문을 채워 넣지 않으며, 제품 내부 구현은 공개 근거가 있을 때만 말한다.

## 공개 자료의 경계

[공식 발표] FactoryX 공식 페이지와 NHN 뉴스룸은 FactoryX를 `Infrastructure–Platform–Service`의 세 레이어로 소개한다. 공식 페이지에는 수랭식 데이터센터·GPU 클러스터·GPU 라인업, GPU Live·AI EasyMaker, ProjectX가 각각의 공개 위치로 제시된다. 이 분류는 제품 전체의 기능 명세가 아니라 공개된 브랜드 구조로 읽어야 한다. `SRC-001`, `SRC-003`

[공식 발표] NHN의 기술 백서 안내 페이지는 GPU 인프라, AI 데이터센터, 클러스터 운영, 플랫폼 아키텍처 등을 주제로 든다. 다만 해당 페이지는 신청형 백서의 안내이며, 이 책이 확인한 범위는 안내 페이지의 공개 정보뿐이다. 페이지에 보이지 않는 구성도, 운영 절차, 실험 결과를 백서에 있었을 것이라고 재구성하는 일은 근거가 아니다. `SRC-002`

[미공개] FactoryX 서울의 상세 랙 배치, 노드 내부 결선, 자원 스케줄러, 스토리지 계층, PUE 실측값, CDU의 온도·유량·압력, 전력 이중화 구성은 이 장의 공개 자료만으로 확인할 수 없다. 따라서 DRA, Kueue, MIG, Slurm 같은 기술을 설명할 때에도 FactoryX의 내부 구현이라고 쓰지 않고, 나중에 검증할 수 있는 업계 설계 대안으로만 취급한다. `SRC-001`, `SRC-002`, `SRC-003`

공개 범위를 표시하는 일은 소극적인 면책이 아니다. 설계 회의에서 알려진 항목과 확인이 필요한 항목을 같은 칸에 넣으면, 이후의 성능 약속과 비용 가정도 출처를 잃는다. 공개된 명제는 출발점이고, 미공개 항목은 구매 전 실증·계약·운영 인수에서 확인해야 할 질문 목록이다.

| 구분 | 공개적으로 확인한 내용 | 이 장에서 하지 않는 해석 | 근거 |
|---|---|---|---|
| 브랜드 구조 | Infrastructure·Platform·Service의 세 레이어 | 각 레이어의 내부 제품 조합 단정 | [공식 발표] `SRC-001`, `SRC-003` |
| 기술 백서 | 공개 안내 페이지의 주제·버전·신청 방식 | 신청형 본문과 도표의 추정 | [공식 발표] `SRC-002` |
| 데이터센터 | B200 기반 AI 인프라와 수랭·고밀도 맥락 | PUE·CDU 조건·전력 계통의 확정 | [공식 발표] `SRC-003`, `SRC-005` |
| 운영 플랫폼 | GPU Live와 AI EasyMaker의 공개 위치 | DRA·Kueue·MIG·Slurm 채택 주장 | [공식 발표] `SRC-001`, `SRC-003` |
| 서비스 | ProjectX의 공개 위치와 계획 방향 | 미공개 기능·가격·출시 후 동작 추정 | [공식 발표] `SRC-001`, `SRC-003` |

## 세 개의 레이어

[공식 발표] Infrastructure 레이어에는 수랭식 데이터센터, GPU 클러스터, GPU 라인업이 공개되어 있다. 이 사실은 물리 자원과 그 수용 환경을 어떤 범주로 제공하는지에 답한다. 반면 실제 랙별 전력, 특정 네트워크 토폴로지, GPU 모델별 할당 정책까지 답하지는 않는다. `SRC-001`, `SRC-003`

[공식 발표] Platform 레이어에는 GPU Live와 AI EasyMaker가 배치된다. NHN은 GPU Live를 학습·추론 워크로드의 분리, 동적 자원 할당, 에너지 효율 기반 스케줄링과 연결해 소개하고, AI EasyMaker를 모델 학습·배포·운영을 지원하는 환경으로 소개한다. 이 설명은 사용자가 요구사항과 운영 수명주기를 검증할 출발점이지, API·큐·장치 분할의 구현 증거는 아니다. `SRC-003`, `SRC-006`, `SRC-007`

[공식 발표] Service 레이어의 ProjectX는 기업 AI 에이전트 실행 환경이라는 방향으로 소개된다. 그러나 기준일 현재 기능 경계와 런타임 정책은 제품 공개 자료로 확정할 수 없는 부분이 있다. 에이전트가 업무 도구를 호출할수록 권한, 승인, 실행 기록, 복구는 모델 품질과 별개의 구매 검증 항목이 된다. `SRC-001`, `SRC-003`

[설계 해석] 세 레이어는 위에서 아래로 흘러가는 조직도가 아니라 서로 되먹임하는 운영 경계다. 예를 들어 서비스의 응답 지연은 모델 또는 도구 호출에서 생길 수 있지만, 큐 대기·GPU 메모리·스토리지·냉각 제한도 같은 사용자 경험으로 나타날 수 있다. 그러므로 인프라팀은 전력·열·용량의 증거를, 플랫폼팀은 배정·관측·롤백의 증거를, 서비스팀은 데이터·권한·업무 결과의 증거를 같은 사고 기록에 남겨야 한다. 이 연결은 공개된 세 레이어를 운용 관점으로 확장한 저자의 해석이다. `SRC-001`, `SRC-003`, `SRC-006`

| 레이어 | 처음 확인할 산출물 | 경계를 넘을 때 남길 증거 | 대표적인 미공개 확인 질문 |
|---|---|---|---|
| Infrastructure | 전력·냉각·네트워크·저장소 요구량 | 부하 조건, 장애 도메인, 계측 지점 | 랙별 전력과 냉각 여유는 어떻게 측정되는가? |
| Platform | 요청·할당·실행·회수 흐름 | 큐 정책, 자원 상태, 작업 계보 | 어떤 장치 분할·스케줄링 구현을 쓰는가? |
| Service | 데이터·도구·승인·감사 경계 | 권한 판정, 실행 이력, 복구 기록 | 에이전트의 도구 호출은 어떻게 통제되는가? |

## 숫자를 읽는 단위

[공식 발표] FactoryX 공식 페이지는 단일 GPU 클러스터 구축 경험을 4,080 GPU로, FP8 기준 연산 규모를 27.4 EFlops로, 운영 경험을 7년 이상으로 제시한다. NHN의 별도 발표는 FactoryX 서울에 B200 GPU 7,656장을 구축했다고 설명한다. 이 수치는 모두 발표 주체와 기준을 붙여 보존해야 한다. `SRC-001`, `SRC-003`, `SRC-005`

[원자료] TOP500의 Rmax·Rpeak는 특정 LINPACK 시험의 실측·이론 성능을 설명하는 지표다. 반면 FactoryX 페이지의 27.4 EFlops는 FP8 기준의 연산 규모다. 정밀도, 시험 방법, 측정 경계가 다르므로 두 숫자를 같은 막대그래프에 놓거나 비율로 바꾸면 안 된다. NHN Cloud 회사 전체 소개에 제시된 별도 인프라 수치 역시 FactoryX 단일 클러스터의 성능으로 합산할 수 없다. `SRC-001`, `SRC-004`, `SRC-011`, `SRC-012`

[설계 해석] 숫자가 설계에 유용해지는 순간은 큰 수를 선택하는 때가 아니라, 해당 숫자가 어떤 결정을 제한하는지 밝힐 때다. GPU 장수는 병렬성·전력·공급 계획을 묻는 입력일 수 있고, FP8 연산 규모는 정밀도와 연산 경로의 맥락을 묻는 입력일 수 있다. 그러나 둘 중 어느 것도 업무 모델의 학습 완료 시간, 토큰 지연, 데이터 준비 시간, 승인 대기 시간을 대신하지 않는다. `SRC-001`, `SRC-003`, `SRC-012`

## 풀스택 의사결정

[설계 해석] 풀스택 의사결정은 구매 품목을 한 번에 확정하는 방식이 아니라, 하나의 업무 가설을 여러 층의 검증 질문으로 번역하는 방식이다. 예컨대 월말 대규모 모델 학습 요구는 학습 완료 시점, 데이터 이동, 체크포인트 복구, 큐 우선순위, 랙 전력, 변경 승인이라는 서로 다른 질문으로 풀린다. 공개된 FactoryX 레이어는 이 질문을 누락 없이 배치하는 틀로 사용할 수 있다. `SRC-001`, `SRC-003`, `SRC-006`

[실무 제안] 첫 설계 리뷰에서는 기능 목록 대신 네 개의 문장을 산출물로 고정한다. 첫째, 업무가 끝난 것으로 보는 상태를 한 문장으로 쓴다. 둘째, 그 상태를 망가뜨리는 실패를 시간·데이터·권한으로 나눈다. 셋째, 각 실패를 감지할 신호와 담당 팀을 배정한다. 넷째, 공개 자료에 없는 값은 제공사 확인 항목으로 분리한다. 이 방법은 AI 데이터센터의 전력·냉각과 워크로드·운영을 통합해 보라는 설계 프레임워크의 취지와도 맞닿아 있다. `SRC-019`, `SRC-021`

[실무 제안] 계약 또는 POC의 통과 조건에는 GPU 할당 사실만 넣지 말고, 요청부터 결과 보존·회수까지의 경로를 넣는다. 학습이라면 데이터 버전·체크포인트·재시작 시간을, 추론이라면 지연·오류·과금 경계를, 에이전트라면 권한 판정·승인·도구 실행·감사 기록을 샘플로 확인한다. 이것은 특정 FactoryX 기능의 단정이 아니라, 공개된 인프라·플랫폼·서비스 경계를 검증 가능한 운영 계약으로 바꾸는 제안이다. `SRC-001`, `SRC-003`, `SRC-006`

| 결정 순서 | 확인할 질문 | 남겨야 할 최소 증거 | 공개 자료와의 관계 |
|---|---|---|---|
| 업무 | 무엇이 완료이고 실패 비용은 무엇인가? | SLO 초안, 예외 처리 기준 | [설계 해석] `SRC-006`, `SRC-019` |
| 물리 | 전력·열·연결·저장소의 제한은 무엇인가? | 부하 가정, 계측 위치, 장애 도메인 | [설계 해석] `SRC-003`, `SRC-019`, `SRC-021` |
| 플랫폼 | 누가 어떤 GPU를 얼마나 오래 쓰는가? | 요청·할당·회수 이력 | [설계 해석] `SRC-003`, `SRC-006` |
| 서비스 | 데이터와 도구 실행을 누가 허용하는가? | 정책, 승인, 감사·복구 절차 | [설계 해석] `SRC-001`, `SRC-003` |

## 핵심 요약

- [공식 발표] FactoryX의 공개 구조는 Infrastructure·Platform·Service 세 레이어다. 이 구조는 제품 내부 명세가 아니라 공개된 분류로 사용한다. `SRC-001`, `SRC-003`
- [공식 발표] 4,080 GPU, 27.4 EFlops(FP8), 7년 이상, 7,656 B200 GPU는 서로 다른 발표 범위와 단위를 가진다. `SRC-001`, `SRC-003`, `SRC-005`
