# 8장 AI EasyMaker와 MLOps 수명주기

모델의 첫 학습은 수명주기의 시작일 뿐이다. 운영에서 다시 써야 할 것은 가중치 파일 하나가 아니라, 어떤 데이터와 코드와 환경에서 만들어졌는지, 어떤 평가를 통과했는지, 어느 엔드포인트에 어떤 방식으로 배포되었는지, 문제가 생기면 무엇으로 돌아갈지를 설명하는 증거 묶음이다. 이 장은 AI EasyMaker의 공개 기능을 출발점으로 삼되, 공개 자료에 없는 feature store·자동 드리프트 감지·승인형 레지스트리 같은 기능을 제품 사실로 확장하지 않는다.

## AI EasyMaker의 공개 기능

[공식 발표] AI EasyMaker 공식 개요는 TensorFlow·PyTorch 기반 Jupyter Notebook 개발 환경, CPU/GPU 인스턴스와 저장공간을 지정하는 학습, 최대 10노드 분산 학습, TensorBoard 기반 결과 분석, 모델 아티팩트 관리와 성능 비교, 엔드포인트 관리의 범위를 안내한다. FactoryX 발표는 AI EasyMaker를 컨테이너 기반 표준 환경에서 학습·배포·운영을 지원하는 Platform 레이어의 제품으로 설명한다. 이 두 출처는 학습부터 운영까지 연결하려는 공개 방향을 뒷받침하지만, 모든 MLOps 기능의 제공을 보증하지는 않는다. [SRC-003, SRC-007]

[공식 발표] AI EasyMaker 릴리스 노트에는 ML Pipeline, 개인 컨테이너 이미지, 배치 추론, RAG, NVIDIA Triton Inference Server, 엔드포인트 리소스 설정, 파인 튜닝 같은 기능 변화가 날짜와 함께 기록되어 있다. 이러한 항목은 현재 기능을 확인할 때 유용하지만, 롤링 릴리스 문서이므로 기준일과 버전을 함께 보아야 한다. [SRC-008]

| 수명주기 영역 | 공개 문서에서 확인한 범위 | 이 장에서 제품 사실로 단정하지 않는 범위 | 근거 |
|---|---|---|---|
| 개발·학습 | Notebook, CPU/GPU 학습, 저장공간, 최대 10노드 분산 학습 | 모든 프레임워크·모든 분산 방식의 지원 | [공식 발표] SRC-007 |
| 실험 | TensorBoard 기반 분석, 반복 실험 비교, 튜닝 관련 기능 | 전사 표준 실험 추적 정책 | [공식 발표] SRC-007·SRC-008 |
| 모델·서빙 | 모델 아티팩트 관리·성능 비교, 엔드포인트 관리 | 승인형 레지스트리·드리프트 자동 판정 | [공식 발표] SRC-007 |
| 파이프라인·확장 기능 | Kubeflow Pipelines SDK, RAG, Triton 관련 공개 안내 | FactoryX 내부 연결 방식과 보존 정책 | [공식 발표] SRC-007·SRC-008 |

[설계 해석] “통합 MLOps”라는 표현은 도구 목록이 아니라 경계의 질문으로 읽어야 한다. 개발 환경에서 생성한 산출물의 식별자가 학습 작업, 평가 결과, 모델 아티팩트, 배포 구성, 운영 사건과 이어질 때만 특정 결과를 다시 만들거나 되돌릴 수 있다. 제품 화면이 여러 단계를 제공해도, 단계 사이에 무엇을 보존하고 누가 승인하는지 정하지 않으면 수명주기는 끊긴다.

## 실험에서 등록까지

[설계 해석] 실험은 “좋아 보이는 모델”을 만드는 활동이 아니라, 다음 판정을 재현할 수 있게 만드는 활동이다. 따라서 실험 기록에는 최소한 코드 리비전, 컨테이너 이미지 식별자, 데이터셋의 버전 또는 조회 조건, 학습 파라미터, 하드웨어·분산 조건, 난수 시드의 처리 방식, 생성된 아티팩트의 해시 또는 불변 식별자를 남긴다. 데이터 원문을 모두 복사하라는 뜻은 아니다. 접근 권한과 보존 정책을 해치지 않는 범위에서 “동일한 입력을 다시 선택할 수 있는 참조”를 남기라는 뜻이다.

[공식 발표] AI EasyMaker는 학습 결과 분석과 반복 실험 비교를 위한 TensorBoard 기반 기능을 안내한다. 이 기능은 실험의 비교 화면에 해당한다. 그러나 어떤 지표가 배포 승인 기준인지, 누가 기준을 변경할 수 있는지, 비교 대상 데이터셋을 언제 동결하는지는 팀의 운영 규칙으로 별도 결정해야 한다. [SRC-007]

| 단계 | 반드시 연결할 입력 | 보존할 산출물 | 재현 질문 |
|---|---|---|---|
| 개발 | 코드 리비전·의존성·컨테이너 | 실행 명령·이미지 식별자 | 같은 환경을 만들 수 있는가 |
| 학습 | 데이터 참조·파라미터·자원 조건 | 로그·체크포인트·모델 아티팩트 | 같은 입력에서 차이를 설명할 수 있는가 |
| 평가 | 평가 데이터셋·지표 정의·임계값 | 점수·오류 표본·판정자 | 같은 기준으로 통과 여부를 재판정할 수 있는가 |
| 등록 | 승인된 모델 식별자·부모 실험 | 계보 링크·변경 사유 | 배포 대상이 어느 실험에서 왔는가 |

[실무 제안] 등록은 파일을 한 폴더로 옮기는 행위가 아니라, 배포 후보를 가리키는 불변 참조를 만드는 단계로 설계한다. 사람 친화적인 별칭은 바뀔 수 있지만, 운영 배포가 참조한 모델·평가·구성 조합은 나중에 변하면 안 된다. 등록을 허용하는 사람과 평가를 만든 사람이 같아도 되는지, 비상 배포에서 어떤 사후 승인이 필요한지는 조직의 위험도에 맞춰 결정한다.

[설계 해석] 비교의 단위도 명확히 해야 한다. 하나의 모델이 점수에서 앞서더라도 응답 지연, 메모리 사용, 안전성 오류, 실패 요청의 재시도 비용이 달라질 수 있다. 그러므로 “새 버전이 더 좋다”라는 결론은 지표, 평가 데이터 범위, 측정 시각, 비교 대상, 허용 오차를 함께 기록한 판정문이어야 한다. 외부 벤치마크 순위나 단일 평균 점수만으로 업무 배포를 승인하지 않는 이유가 여기에 있다.

## 배포와 단계 전환

[공식 발표] AI EasyMaker 문서는 엔드포인트 관리, 이중화, 테스트 스테이지와 기본 도메인 전환을 안내한다. 공개된 기능은 단계적 배포를 검토할 출발점이지만, 실제 트래픽 분할 방식, 고객별 격리, 자동 승격 조건, 서비스 수준 목표는 배포 대상과 계약에 따라 별도로 확인해야 한다. [SRC-007]

[설계 해석] 배포 단계는 이름보다 전환 조건이 중요하다. 개발자는 새 모델을 테스트 단계에 올리고, 평가는 미리 정한 데이터·지표·안전 규칙을 확인하며, 운영자는 실제 요청의 지연·오류·자원 사용을 본다. 이 세 관점이 다른 식별자를 사용하면 “시험한 모델”과 “실제로 노출된 모델”이 달라질 수 있다. 각 단계 전환 기록에는 모델 ID, 서빙 이미지, 입력 스키마, 자원 설정, 트래픽 범위, 승인자, 되돌릴 대상이 함께 있어야 한다.

| 전환 | 들어가기 전 증거 | 운영 중 관측 | 중단 또는 되돌림 조건 |
|---|---|---|---|
| 개발 → 테스트 | 재현 가능한 학습·평가 묶음 | 기능 오류·입력 호환성 | 입력 계약이 깨질 때 |
| 테스트 → 제한 배포 | 평가 결과·위험 검토·트래픽 범위 | 지연·오류·안전 이벤트 | 기준선 대비 악화가 확인될 때 |
| 제한 배포 → 확대 | 제한 범위의 결과·운영자 승인 | 업무 완료·재시도·지원 요청 | 피해 범위가 확대될 때 |
| 확대 → 안정 운영 | 런북·온콜·롤백 연습 | SLO·비용·모델 품질 | 롤백 경로가 검증되지 않았을 때 |

[실무 제안] 단계 전환에 자동화가 있더라도, 자동화의 입력은 검증 가능한 증거여야 한다. 예컨대 오류율이 낮다는 조건만으로 확대하지 말고, 평가 데이터와 실제 요청의 분포 차이, 사용자에게 영향이 큰 실패 유형, 긴 꼬리 지연, 수동 승인 필요 여부를 함께 검토한다. 이 가드레일은 AI EasyMaker의 특정 자동 승격 기능을 주장하지 않는다.

## 파이프라인과 재현성

[공식 발표] AI EasyMaker의 공개 안내는 Kubeflow Pipelines SDK를 이용해 전처리·학습·평가·배포 단계를 연결하는 파이프라인 범위를 제시한다. 파이프라인이 있다는 사실은 단계를 코드화할 가능성을 보여주지만, 개별 조직의 데이터 계보·승인·비밀 관리 정책이 자동으로 완성된다는 뜻은 아니다. [SRC-007]

[설계 해석] 재현성은 “한 번 더 실행된다”보다 강한 조건이다. 같은 실행 정의가 같은 결과를 보장하기 어려운 경우에도, 결과 차이가 데이터 변경, 코드 변경, 이미지 변경, 자원 조건, 외부 모델 버전 중 무엇에서 왔는지 좁힐 수 있어야 한다. 이를 위해 파이프라인 입력을 암묵적 기본값으로 숨기지 않고, 검증된 기본값의 버전과 실행마다 달라지는 값을 구분한다.

| 파이프라인 경계 | 입력 계약 | 출력 계약 | 검토 포인트 |
|---|---|---|---|
| 전처리 | 원천 범위·필터·권한 | 데이터 참조·품질 보고 | 학습 데이터 누락·누수 |
| 학습 | 코드·이미지·파라미터·GPU 조건 | 아티팩트·로그·자원 기록 | 중단 후 재시작 가능성 |
| 평가 | 모델 ID·평가 세트·임계값 | 판정·오류 표본·승인 요청 | 비교 기준의 변경 이력 |
| 배포 | 승인 모델·서빙 구성·트래픽 범위 | 엔드포인트 버전·실행 ID | 이전 버전으로의 복귀 |

[실무 제안] 파이프라인 실패를 하나의 “실패”로만 보지 않는다. 입력 검증 실패, 인프라 부족, 외부 의존성 오류, 모델 품질 미달, 승인 대기, 배포 중단은 서로 다른 처리와 재시도 권한을 가진다. 실패 유형별로 자동 재시도할 범위와 사람에게 넘길 범위를 정해 두면, 재실행이 데이터 중복이나 불필요한 GPU 소비를 만들지 않도록 할 수 있다.

## RAG·Triton의 위치

[공식 발표] AI EasyMaker 릴리스 노트와 개요는 RAG 관련 기능과 NVIDIA Triton Inference Server 관련 항목을 안내한다. RAG는 문서를 벡터화하고 검색 결과를 LLM 응답 생성에 연결하는 흐름이며, Triton은 모델 서빙 계층을 다루는 기술이다. 두 항목은 수명주기에 놓이는 위치가 다르므로, 모두를 “모델 배포”라는 한 칸에 넣으면 데이터 갱신과 추론 실행의 책임이 흐려진다. [SRC-007, SRC-008]

[설계 해석] RAG의 변경 단위에는 문서 원본의 권한·보존 조건, 청크 규칙, 임베딩 모델, 인덱스 버전, 검색 파라미터, 프롬프트 템플릿이 함께 들어간다. 반면 서빙 변경 단위에는 모델 아티팩트, 런타임 이미지, 배치·동시성 설정, 자원 제한, 엔드포인트 라우팅이 들어간다. 같은 요청 경로에서 만날 수는 있어도, 되돌려야 할 원인과 승인자는 다를 수 있다.

| 변경 대상 | 대표 식별자 | 평가의 초점 | 롤백 단위 |
|---|---|---|---|
| RAG 지식 | 문서 집합·인덱스·임베딩 버전 | 검색 적합성·권한 누출·최신성 | 이전 인덱스 또는 문서 집합 |
| 생성 모델 | 모델 아티팩트·프롬프트 버전 | 품질·안전성·지연 | 이전 승인 모델·프롬프트 |
| Triton 서빙 | 런타임 이미지·서빙 구성 | 요청 처리·자원·오류 | 이전 이미지·구성 |
| 엔드포인트 | 트래픽 규칙·도메인 전환 | 사용자 영향·오류 분포 | 이전 라우팅 상태 |

[실무 제안] RAG의 문서 갱신을 모델 재학습과 같은 승인 흐름으로 취급할지, 별도 데이터 변경으로 취급할지는 업무 위험도에 따라 정한다. 중요한 것은 어느 선택이든 사용자가 받은 답변을 당시의 문서·인덱스·모델·프롬프트 조합으로 설명할 수 있다는 점이다. 공개 문서가 제공 여부를 확인하지 않은 세부 계보 화면이나 자동 품질 판정을 이 체계의 전제로 두지 않는다.

## 롤백과 계보

[설계 해석] 롤백은 이전 모델 파일을 다시 배포하는 단일 버튼이 아니다. 입력 계약, 서빙 이미지, 트래픽 라우팅, RAG 인덱스, 권한 정책, 관측 대시보드가 새 버전과 함께 바뀌었을 수 있다. 따라서 롤백 계획은 “어디로 돌아가는가”뿐 아니라 “어떤 조합을 고정해 두었는가”를 명시해야 한다. 불변 모델 ID만 남기고 다른 구성 요소가 바뀌면 이전 품질이 재현되지 않을 수 있다.

[실무 제안] 계보 레코드를 다음 두 방향으로 조회할 수 있게 설계한다. 정방향은 특정 데이터·코드 변경이 어떤 모델·엔드포인트·업무 결과로 이어졌는지 찾는 경로다. 역방향은 특정 사용자 영향 사건이 어떤 엔드포인트·모델·평가·데이터 참조에서 왔는지 찾는 경로다. 이 원칙은 특정 AI EasyMaker 화면이나 저장 방식의 주장이 아니라, 운영 인수에 필요한 증거 모델이다.

| 사건 | 즉시 확보할 식별자 | 복구 전에 확인할 것 | 사후 검토 |
|---|---|---|---|
| 품질 저하 | 요청 범위·모델·프롬프트·인덱스 | 이전 승인 조합과 차이 | 평가 세트의 공백 |
| 지연 급증 | 엔드포인트·서빙 구성·GPU 할당 | 트래픽 변화·자원 포화 | 용량·배치 정책 |
| 권한 오류 | 사용자·문서·도구 권한·배포 버전 | 노출 범위와 보존 로그 | 데이터 경계의 누락 |
| 배포 실패 | 배포 ID·이미지·구성·오류 코드 | 이전 상태의 유효성 | 변경 검토·런북 보완 |

## 설계 리뷰

- [공식 발표] AI EasyMaker의 공개 기능과, 조직이 별도로 마련해야 할 계보·승인·드리프트·보존 규칙을 구분했는가. [SRC-003, SRC-007, SRC-008]
- [설계 해석] 코드·이미지·데이터 참조·파라미터·자원 조건·평가 결과가 모델과 양방향으로 연결되는가.
- [설계 해석] 테스트·제한 배포·확대·안정 운영의 전환 조건에 모델 ID와 되돌릴 조합이 포함되는가.
- [공식 발표] RAG, Triton, 파이프라인을 모두 같은 변경 단위로 취급하지 않고 공개된 기능 범위 안에서 역할을 나눴는가. [SRC-007, SRC-008]
- [실무 제안] 실패 유형별 자동 재시도와 사람 검토의 경계가 데이터 중복·비용·안전성까지 고려하는가.

## 핵심 요약

- [공식 발표] AI EasyMaker는 Notebook, CPU/GPU 학습, 최대 10노드 분산 학습, 모델·엔드포인트 관리 등 공개 기능을 안내한다. [SRC-007]
- [공식 발표] 릴리스 노트의 RAG·Triton·파이프라인 등 기능은 기준일과 버전을 함께 확인해야 한다. [SRC-008]
- [설계 해석] 수명주기의 핵심은 화면 간 이동이 아니라 코드·데이터·환경·평가·배포를 연결하는 증거다.
- [실무 제안] 배포 단계는 트래픽 비율이 아니라 전환 조건, 관측 신호, 되돌릴 조합, 승인 권한으로 정의한다.
- [설계 해석] RAG의 지식 변경과 모델·서빙 변경은 서로 다른 식별자·평가·롤백 단위를 가진다.
