이 책의 근거와 경계

이 책은 NHN FactoryX의 공식 공개 페이지와 기술별 1차 자료를 바탕으로 KLIC가 독립 집필한 실무서입니다. 신청형 기술 백서의 제공되지 않은 본문은 추정하지 않았습니다.

NHN 발표, 공개 원자료, 저자의 설계 해석과 실무 제안을 문법적으로 구분했습니다. FactoryX 내부 구현으로 확인되지 않은 기술은 업계 설계 대안으로만 설명합니다.

이 책은 KLIC의 독립 연구 편집물이며 NHN Cloud 또는 NHN FactoryX의 공식 문서가 아니다. 제품명과 상표의 권리는 각 권리자에게 있다. 외부 사실과 수치는 장별 출처 원장에 표시했다.

공개 자료 확인 기준일은 2026년 8월 12일입니다. 제품 기능과 문서 버전은 출판 전 다시 확인해야 합니다.

이 책은 NHN FactoryX를 소개하는 홍보물이 아니라, 공개 자료를 기술 의사결정에 쓸 수 있는 질문과 증거로 바꾸는 독립 실무서다. NHN Cloud·NHN FactoryX가 공개한 제품 페이지와 뉴스룸 발표, TOP500 원자료, 표준·정부·오픈소스 프로젝트의 1차 문서를 교차해 인프라에서 에이전트 실행 환경까지 연결했다. 신청을 거쳐 제공되는 FactoryX 기술 백서의 본문은 입수하지 않았고, 안내 페이지에서 확인되는 주제 밖의 내용을 추정하지 않았다.

이 책의 범위

FactoryX의 공개 구조를 Infrastructure–Platform–Service 세 계층으로 읽되, 각 계층을 전력·냉각·GPU·패브릭·스토리지·자원 할당·MLOps·관측·보안·에이전트 운영의 검증 항목으로 풀었다. 제품 내부 구현이 공개되지 않은 곳에서는 Kubernetes DRA, Kueue, MIG, Slurm, DCGM 같은 기술을 업계 설계 대안으로만 다룬다. 이 책의 설명이 곧 FactoryX의 내부 아키텍처라는 뜻은 아니다.

공개 자료 확인 기준일은 2026년 8월 12일이다. 이후 출시, 기능, 가격, 문서 버전, 정책이 바뀔 수 있으므로 실제 계약·도입 단계에서는 원문과 최신 제품 문서를 다시 확인해야 한다.

독립성과 상표

1장 FactoryX를 읽는 법

FactoryX를 GPU의 수량표로 읽으면 중요한 질문을 놓친다. GPU는 연산을 담당하지만, 실제 업무 결과는 전력과 냉각의 여유, 노드와 네트워크의 데이터 이동, 자원 배정, 모델 배포, 권한과 감사의 연결 위에서 나온다. 이 장은 NHN이 공개한 FactoryX의 범위를 확인 가능한 사실로 한정하고, 그 사실을 투자·설계·운영 판단으로 번역하는 방법을 다룬다. 신청형 자료의 본문을 채워 넣지 않으며, 제품 내부 구현은 공개 근거가 있을 때만 말한다.

공개 자료의 경계

[공식 발표] FactoryX 공식 페이지와 NHN 뉴스룸은 FactoryX를 Infrastructure–Platform–Service의 세 레이어로 소개한다. 공식 페이지에는 수랭식 데이터센터·GPU 클러스터·GPU 라인업, GPU Live·AI EasyMaker, ProjectX가 각각의 공개 위치로 제시된다. 이 분류는 제품 전체의 기능 명세가 아니라 공개된 브랜드 구조로 읽어야 한다. SRC-001, SRC-003

[공식 발표] NHN의 기술 백서 안내 페이지는 GPU 인프라, AI 데이터센터, 클러스터 운영, 플랫폼 아키텍처 등을 주제로 든다. 다만 해당 페이지는 신청형 백서의 안내이며, 이 책이 확인한 범위는 안내 페이지의 공개 정보뿐이다. 페이지에 보이지 않는 구성도, 운영 절차, 실험 결과를 백서에 있었을 것이라고 재구성하는 일은 근거가 아니다. SRC-002

[미공개] FactoryX 서울의 상세 랙 배치, 노드 내부 결선, 자원 스케줄러, 스토리지 계층, PUE 실측값, CDU의 온도·유량·압력, 전력 이중화 구성은 이 장의 공개 자료만으로 확인할 수 없다. 따라서 DRA, Kueue, MIG, Slurm 같은 기술을 설명할 때에도 FactoryX의 내부 구현이라고 쓰지 않고, 나중에 검증할 수 있는 업계 설계 대안으로만 취급한다. SRC-001, SRC-002, SRC-003

공개 범위를 표시하는 일은 소극적인 면책이 아니다. 설계 회의에서 알려진 항목과 확인이 필요한 항목을 같은 칸에 넣으면, 이후의 성능 약속과 비용 가정도 출처를 잃는다. 공개된 명제는 출발점이고, 미공개 항목은 구매 전 실증·계약·운영 인수에서 확인해야 할 질문 목록이다.

2장 워크로드에서 시작하는 요구사항

AI 인프라 요구사항은 필요한 GPU 수로 시작하지 않는다. 같은 GPU라도 대규모 학습, 온라인 추론, 검색증강생성(RAG), 도구를 실행하는 에이전트는 기다릴 수 있는 시간, 이동해야 할 데이터, 실패 뒤 복구할 상태가 다르다. 이 장의 목표는 업무 문장을 자원 견적서로 성급히 바꾸지 않고, SLO·데이터·규제·용량·실패 모델의 검증 가능한 입력으로 바꾸는 데 있다.

워크로드 네 가지

[설계 해석] 학습은 정해진 품질 조건에서 모델을 완성할 시간과, 중단 뒤 이어갈 수 있는 상태가 핵심이다. GPU 연산만 보지 말고 데이터 공급, 노드 간 동기화, 체크포인트 기록·복원, 큐 대기까지 하나의 완료 시간으로 잡아야 한다. NHN Cloud AI 인프라 페이지가 GPU 클러스터와 스토리지를 함께 AI 인프라의 맥락으로 제시하는 이유도 이 연결에 있다. SRC-006, SRC-019

[설계 해석] 추론은 사용자 요청이 들어온 뒤 첫 결과와 전체 응답을 언제 끝내는지가 중심이다. 모델 크기와 배치 방식은 GPU 메모리와 처리량에 영향을 주지만, 서비스 수준은 입력 길이, 동시성, 캐시, 모델 교체, 외부 의존성까지 포함해 정한다. 최대 토큰 처리량만으로 업무 경험을 약속하지 않는 이유가 여기에 있다. SRC-006, SRC-019

[설계 해석] RAG는 모델 호출 앞에 데이터 검색과 컨텍스트 구성이라는 단계를 둔다. 따라서 GPU가 놀고 있어도 색인 최신성, 접근 권한 필터, 검색 지연, 인용 가능한 근거의 누락이 결과를 막을 수 있다. 요구사항에는 검색 대상의 소유자, 갱신 주기, 삭제 전파, 문서별 권한과 모델에 넘길 최대 컨텍스트를 분리해 적는다. 이 문단은 공개된 특정 FactoryX 구현이 아니라 데이터·플랫폼을 함께 설계하라는 일반적 해석이다. SRC-006, SRC-019

[설계 해석] 에이전트는 모델의 답변이 실제 도구 호출로 이어질 수 있다는 점에서 앞의 셋과 다르다. 요청 성공은 텍스트 생성이 아니라 올바른 신원으로 허용된 도구를 실행하고, 실패 시 중복 없이 복구하며, 사후에 누가 무엇을 승인했는지 설명할 수 있을 때 성립한다. ProjectX의 내부 기능을 전제하지 않고도 이 조건은 에이전트 실행 환경의 검증 질문으로 남는다. SRC-001, SRC-003

워크로드 주된 병목 가설 완료 조건의 예 먼저 확인할 증거
학습 데이터 공급·동기화·체크포인트 정해진 평가 기준과 마감 전 완료 데이터 버전, 재시작 시간, 큐 대기
추론 메모리·동시성·지연 응답 지연과 오류율의 범위 요청 분포, 토큰 길이, 모델별 지연
RAG 검색·권한 필터·색인 최신성 근거 있는 답변을 제한 시간 내 반환 색인 시점, 권한 판정, 검색 실패율
에이전트 도구 의존성·승인·복구 허용된 실행과 감사 가능한 결과 권한 범위, 승인 기록, idempotency

[실무 제안] 네 유형을 하나의 AI 작업 큐에 넣기 전에, 중단 가능성·재시도 비용·데이터 민감도·피크 시간대를 비교표로 만든다. 특히 학습의 긴 점유와 추론의 짧은 지연 민감 요청을 같은 우선순위 규칙으로 운영하면 어느 한쪽의 완료 조건을 훼손할 수 있다. 이는 특정 스케줄러의 채택 제안이 아니라, 고밀도 AI 데이터센터의 수요와 공급을 함께 설계하라는 일반 원칙을 요청 분류에 적용한 것이다. SRC-019, SRC-006

SLO와 완료 조건

[설계 해석] SLO는 플랫폼이 빠르다는 표현을 측정 가능한 약속으로 바꾸는 장치다. 그러나 단일 숫자로 끝내면 안 된다. 학습에는 완료 시각·재시작 가능성·평가 통과가, 추론에는 지연의 백분위·오류·처리량이, RAG에는 검색 성공·권한 위반 없음·근거 최신성이, 에이전트에는 승인된 실행·복구·감사가 함께 필요하다. 각 항목은 업무 담당자가 실제로 손실을 판단할 수 있는 단위로 써야 한다. SRC-006, SRC-019

[실무 제안] 요구서에는 평균값보다 경계 조건을 먼저 적는다. 예를 들어 평균 응답이 빠르다는 표현 대신 피크 시간, 긴 입력, 모델 교체, 검색 대상 부재, 외부 도구 지연, 승인 거절의 경우에 어떤 결과를 반환할지 정한다. 이렇게 하면 용량 부족·데이터 오류·권한 거절을 모두 GPU 성능 문제로 오진하는 일을 줄일 수 있다. SRC-019, SRC-021

대상 SLO 항목 완료 판정 측정 경계
학습 기한 내 성공 실행, 재시작 시간 평가 기준 충족 모델·계보 보존 제출부터 결과 등록까지
추론 지연 백분위, 오류, 처리량 요청별 응답 또는 명시적 실패 게이트웨이 수신부터 마지막 출력까지
RAG 검색 지연, 근거 적합성, 권한 오류 허용 문서만 사용한 응답 질의부터 인용 가능한 컨텍스트까지
에이전트 승인 대기, 도구 성공, 복구 시간 정책 안의 실행과 감사 기록 계획 생성부터 결과 확인까지

[설계 해석] SLO의 측정 경계를 정하면 팀 경계도 자연스럽게 드러난다. 네트워크 지연을 모델 팀이, 권한 거절을 GPU 운영팀이 단독으로 해결할 수는 없다. 관측 신호는 시설·클러스터·모델·업무의 계층으로 나뉘어야 하며, 사건이 발생했을 때 같은 요청 식별자로 연결될 수 있어야 한다. 이 책은 이후 장에서 그 연결을 운영 설계로 확장한다. SRC-019, SRC-021

데이터·규제 경계

[설계 해석] 데이터 요구사항은 저장 위치만으로 끝나지 않는다. 원본 문서·파생 청크·임베딩·프롬프트·응답·평가 데이터·로그가 각각 언제 생성되고 누가 읽으며 언제 삭제되는지 적어야 한다. 같은 문서라도 학습 재사용 가능 여부, 검색 전용 여부, 감사 보존 여부가 다를 수 있다. 이 분류는 특정 제품의 데이터 기능을 주장하는 것이 아니라, AI 인프라와 데이터 운영을 통합해 설계하기 위한 요구사항이다. SRC-006, SRC-019

[실무 제안] 규제 또는 사내 정책이 있는 업무는 데이터가 내부에 있다는 말 대신 네 가지 증거를 요구한다. 데이터 분류표, 접근 권한 결정 기록, 전송·보존 경로, 삭제·보류의 실행 기록이다. RAG와 에이전트에는 문서 권한이 모델 컨텍스트와 도구 권한으로 승격되는 지점도 별도 검증한다. SRC-019, SRC-021

경계 확인 질문 최소 증거 실패 시 영향
원본 데이터 누가 어떤 목적으로 읽는가? 분류·소유자·보존 정책 무단 접근 또는 삭제 실패
검색 색인 언제 갱신되고 무엇을 제외하는가? 색인 버전·권한 필터 결과 오래되거나 과도한 컨텍스트
모델 입출력 무엇을 기록하고 가리는가? 마스킹·접근·보존 규칙 민감 정보의 과다 노출
도구 실행 어떤 신원과 범위로 호출하는가? 위임 권한·승인·감사 이력 과권한 실행·복구 불가

용량 가정

[공식 발표] NHN의 제조업 AX·DX 공개 요약은 109개사 조사 맥락에서 78.9%가 DX 초기·확장 단계에 있고, 45.2%가 DX 전용 예산을 확보했으며, 49%가 하이브리드 클라우드를 선호한다고 제시한다. 이 세 수치는 FactoryX 고객의 수요나 특정 기업의 도입 성공률이 아니다. 설문 문항·모집단·시점의 제약을 가진 공개 요약값으로만 사용한다. SRC-009

[설계 해석] 용량 계획은 외부 설문 비율로 GPU 대수를 산출하는 계산이 아니다. 설문은 어떤 조직이 무엇을 먼저 확인할지 알려 주는 맥락 자료일 뿐이다. 실제 산정에는 업무별 요청 도착률, 입력·출력 길이, 동시 실행, 모델·배치, 데이터 전송량, 피크 지속 시간, 허용 큐 대기, 재시도, 성장 가정을 같은 기준일로 수집해야 한다. SRC-009, SRC-019

[실무 제안] 가정을 세 층으로 기록한다. 첫째는 관측값이며, 기간·표본·계측 위치를 적는다. 둘째는 정책값이며, 우선순위·쿼터·예약·보존 기간을 적는다. 셋째는 추정값이며, 낙관·기준·보수 시나리오를 병렬로 둔다. GPU 수, 랙 전력, 네트워크 대역폭을 한 개의 가정에서 연쇄 계산할 때에는 어떤 가정이 바뀌면 다시 계산해야 하는지도 함께 적는다. SRC-019, SRC-021

실패 모델

[설계 해석] 실패 모델은 완료 조건이 깨지는 방식, 감지 위치, 인계 대상을 함께 정의하는 모델이다. 학습 노드가 사라지는 경우, 추론 큐가 길어지는 경우, 검색 권한이 바뀌는 경우, 도구 호출이 중단되는 경우는 모두 다른 복구 단위를 가진다. 완벽한 가용성을 약속하기보다, 재시도 가능한 작업과 사람의 판단이 필요한 작업을 분리하는 편이 안전하다. SRC-019, SRC-021

[실무 제안] 모든 워크로드에 적어도 하나의 의도적 실패 시험을 둔다. 학습은 체크포인트에서 복원하는지, 추론은 부하가 넘칠 때 제한된 응답을 내는지, RAG는 권한 없는 문서를 제외하는지, 에이전트는 승인 거절과 도구 시간 초과 뒤 중복 실행 없이 멈추는지를 확인한다. 시험 결과는 단순 성공·실패가 아니라 발생 시각, 입력 버전, 관련 로그, 복구 판단으로 남긴다. SRC-019, SRC-021

3장 전력·열·D2C 수랭

고밀도 GPU 인프라에서 전력은 서버실 바깥의 시설 문제이고, 열은 GPU 안에서 끝나지 않는 운영 문제다. 랙의 전력 밀도가 올라갈수록 전기·냉각·제어·안전의 경계는 더 촘촘하게 맞물린다. 이 장은 FactoryX 서울에 관해 공개된 수치를 발표 범위 안에서 읽고, 시설수(FWS)·냉각분배장치(CDU)·기술 냉각수(TCS)·direct-to-chip(D2C)의 역할을 일반 설계 배경으로 분리한다. 특정 제조사 참조 설계를 FactoryX의 상세 구성으로 바꾸지 않는다.

랙 전력은 시설 문제다

[공식 발표] NHN은 FactoryX 서울을 랙당 75 kW급 고밀도 환경으로 설명하고, B200 GPU 7,656장과 GPU 기준 100% 수랭식 냉각 적용을 발표했다. 이 수치는 NHN의 발표 범위와 기준을 가진다. 랙별 실제 IT 부하 분포, 시설 전체 전력, 발전기·UPS·PDU 이중화, PUE 실측값은 공개 자료만으로 확정할 수 없다. SRC-003, SRC-005, SRC-010

[원자료] AI 데이터센터의 전력·냉각은 서버 선택 이후에 덧붙이는 설비가 아니라 통합 설계 대상으로 다뤄진다. ASHRAE의 AI 데이터센터 프레임워크와 미국 DOE 가이드는 IT 부하, 전력 변환, 냉각, 제어·계측의 경계를 함께 설계할 필요를 설명한다. 다만 이 일반 프레임워크의 예시 수치나 설계 범위를 FactoryX의 측정 성능으로 옮길 수는 없다. SRC-019, SRC-021

FWS·CDU·TCS

[원자료] 액체 냉각 설계에서는 시설수(FWS)와 장비 측 기술 냉각수(TCS)를 CDU가 열교환으로 분리하는 구성이 일반적인 설명 틀이다. FWS는 시설의 열 배출 계통과 연결되고, TCS는 장비·랙 매니폴드·cold plate 쪽의 제어 가능한 루프가 된다. 두 회로는 열을 전달하지만 물의 품질, 압력, 온도 제어, 유지보수 책임을 같은 값으로 취급하지 않는다. SRC-020, SRC-021, SRC-022

[원자료] ASHRAE의 W1~W5는 시설 공급수 환경 클래스를 구분한다. 이 분류는 GPU 접합부 온도나 서버 내부 센서값이 아니라 시설 공급수 조건을 설명한다. TCS 공급수, 공기 흡입 온도, GPU 온도를 하나의 값으로 묶으면 설계와 장애 분석 모두가 틀어진다. SRC-020

[설계 해석] CDU는 열을 옮기는 장치이면서 책임 경계를 드러내는 장치다. 시설팀은 FWS의 용량·수질·열 배출·정비를, IT·플랫폼팀은 TCS의 유량·압력·온도·장비 경보와 작업 제한을 같은 사건 식별자로 연결해야 한다. 이때 각 팀이 보는 단위는 달라도, 어떤 조건에서 신규 작업을 막고 기존 작업을 감속·중단할지의 결정은 하나여야 한다. SRC-019, SRC-021, SRC-022

D2C의 열포획

[원자료] D2C는 냉각 매체가 CPU·GPU 같은 발열 부품의 cold plate에 직접 전달되는 액체 냉각 방식을 가리키는 일반 용어다. OCP의 cold plate 요구사항은 유량·압력·온도·GPU 온도·전력 같은 신호와 누수 대응을 다루며, 액체 냉각 장비도 공랭 구성요소를 함께 가질 수 있음을 전제로 한다. SRC-022

[공식 발표] NHN은 FactoryX 서울에 GPU 기준 100% 수랭식 냉각을 적용했다고 설명한다. 이 표현을 전체 랙 열의 100%가 액체로 포획된다는 의미로 확장하면 안 된다. 서버·랙에는 팬, NIC, 전원장치, 저장장치처럼 열·기류·정비 요구가 다른 구성요소가 있을 수 있으며, 공개 자료만으로 FactoryX의 열포획 비율이나 배관 상세를 계산할 수 없다. SRC-003, SRC-005, SRC-022

누수와 열 관성

[원자료] OCP의 cold plate 요구사항은 누수 대응을 단일 스위치가 아니라 감지·경보·사람의 대응·IT 전원 차단·냉각수 차단으로 이어지는 단계적 개입으로 다룬다. 어느 단계를 자동화할지는 누수 위치, 감지 신뢰도, 장비 상태, 인명·자산 위험, 복구 절차에 따라 결정해야 한다. SRC-022

[설계 해석] 열 관성 때문에 냉각 이상과 GPU 작업의 실패는 동시에 나타나지 않을 수 있다. 반대로 전원을 즉시 꺼도 배관·cold plate·랙 내부에 남은 열과 유체의 상태를 확인하지 않으면 안전한 재가동을 보장할 수 없다. 따라서 사고 절차는 감지 값 하나가 아니라 추세, 영향 범위, 차단 상태, 작업 체크포인트, 현장 확인을 순서대로 기록해야 한다. SRC-021, SRC-022

[실무 제안] 누수 시험에서는 물을 흘리는 연출보다 의사결정 경로를 시험한다. 센서가 어느 구역을 식별하는지, 알림이 누구에게 가는지, 신규 GPU 작업을 언제 막는지, 실행 중 작업을 어떤 순서로 저장·감속·중단하는지, 유체 차단 뒤 어떤 현장 확인을 거치는지를 시간 순서로 점검한다. 재가동은 경보 해제만으로 허용하지 않고 원인·영향·수정·재검증의 증거가 갖춰졌을 때만 허용한다. SRC-021, SRC-022

전력 장애 상태

[원자료] NVIDIA DGX B200 사용자 가이드는 한 DGX B200 시스템의 최대 전력을 14.3 kW로 안내하고, 6개 PSU의 5+1 구성을 설명한다. 해당 가이드에서 PSU 1개 상실은 영향 없음, 2~3개 상실은 BMC 경보와 성능 저하, 4개 상실은 시스템 종료로 이어지는 일반 참조 상태다. 이 정보는 FactoryX의 HPE B200 구성이나 실제 전력 보호 설계를 증명하지 않는다. SRC-014

[설계 해석] 이 참조 상태가 주는 교훈은 PSU 수를 외우는 데 있지 않다. 시설 전원 상실, 랙 배전 이상, 서버 PSU 장애, GPU 작업 실패는 서로 다른 감지·격리·복구 경로를 가진다. 설계자는 각 경로가 어느 범위의 작업을 멈추게 하는지, 성능 저하 상태에서 어떤 SLO를 유지할지, 상태가 바뀐 사실을 어떤 로그로 남길지 정해야 한다. SRC-014, SRC-021

[실무 제안] 전력 장애 훈련은 정상·성능 저하·안전 종료·복구 네 상태를 분리한다. 성능 저하 상태에서는 모든 작업을 계속하는 대신, 우선순위가 낮은 작업을 줄여 지연 민감 서비스의 안전 범위를 지킬 수 있는지 검증한다. 안전 종료 후에는 데이터 무결성, 체크포인트, 작업 재배치, 냉각 상태, 현장 승인까지 확인한 뒤 부하를 단계적으로 올린다. SRC-014, SRC-021

미공개 운영값

[미공개] FactoryX 서울의 공식 PUE, 전체 시설 전력, 랙별 실제 IT 부하, 전력·냉각 설비의 이중화 구성, CDU 공급·환수 온도, 유량, 압력, 접근온도는 이 책의 공개 근거에서 확인되지 않는다. 이 값들을 업계 평균, 다른 NHN 센터의 과거 PUE, 벤더 참조 시스템의 전력으로 메우면 FactoryX의 사실처럼 보이는 잘못된 계산이 된다. SRC-003, SRC-005, SRC-019, SRC-021

[공식 발표] NHN은 수랭식 적용 후 GPU 연간 장애율이 기존 공랭식 대비 약 3배 낮고 평균 무고장 시간이 약 2.6배 향상됐다고 발표한다. 하지만 표본 수, 기간, GPU 모델, 장애 정의, 공랭 대조군의 조건과 측정 방법은 공개 자료에 상세히 제시되지 않았다. 따라서 이 값은 NHN 발표의 정규화된 비교 표기로만 보여 주며, 독자가 실제 장애율이나 SLA를 계산하는 입력으로 사용해서는 안 된다. SRC-003

[실무 제안] 미공개 운영값은 빈칸으로 남기는 대신 질문지로 바꾼다. POC에서는 어느 계측점의 시계열을 받을 수 있는지, 경보 임계값의 소유자가 누구인지, 작업 감속과 시설 조치가 어떻게 연결되는지, 장애율의 분모·기간·분류가 무엇인지, 에너지 절감의 측정 경계가 어디인지 확인한다. 답을 받지 못한 값은 보수적 시나리오에 두고, 확정값으로 재사용하지 않는다. SRC-019, SRC-021, SRC-022

4장 GPU 노드와 내부 패브릭

GPU 클러스터의 성능을 말할 때 노드를 단순히 GPU 여러 장을 꽂은 상자로 취급하기 쉽다. 그러나 학습과 대규모 추론에서 한 노드는 독립적인 메모리 계층, 내부 교환망, PCIe 장치 경로, 전원·냉각 경계와 장애 상태를 가진 작은 클러스터다. 따라서 노드 수를 늘리기 전에 먼저 한 노드 안에서 어떤 데이터가 어디를 지나며, 어느 경로가 확인되었고 어느 경로가 추정인지를 구분해야 한다.

[원자료 | SRC-011] 2026년 6월 TOP500은 NIPA(NHN Cloud)-CL-1의 서버를 HPE ProLiant Compute XD685, 가속기를 NVIDIA B200, 인터커넥트를 InfiniBand NDR400, 운영체제를 Ubuntu 24.04로 기록한다. 이 행은 FactoryX에서 확인할 수 있는 시스템 식별 정보이지만 GPU 장수, HCA 수, NVSwitch 연결, rail 배치, 로컬·공유 스토리지는 적지 않는다. [설계 해석 | SRC-011] 이 장의 목적은 이 빈칸을 DGX B200 사양으로 채우는 것이 아니라, 도입자가 빈칸을 검증 질문으로 바꾸도록 돕는 데 있다.

노드는 작은 클러스터다

노드 내부에는 적어도 네 종류의 흐름이 동시에 있다. GPU와 HBM 사이에는 연산 중인 텐서와 모델 상태가 머문다. GPU끼리는 병렬 연산의 중간 결과를 교환한다. CPU와 DRAM은 작업 시작, 데이터 준비, 런타임 제어 같은 호스트 역할을 맡는다. NIC 또는 HCA는 노드 밖의 다른 GPU와 패브릭을 연결하고, 로컬 NVMe나 원격 스토리지는 입력과 체크포인트를 공급한다. 한 흐름이 다른 흐름을 대체하지 않으므로 ‘대역폭이 크다’는 한 문장만으로 노드가 균형 잡혔다고 판단할 수 없다.

[원자료 | SRC-014] NVIDIA DGX B200 사용자 가이드는 8개 GPU로 구성된 DGX B200을 하나의 일반 시스템 단위로 설명한다. [원자료 | SRC-013] NVIDIA의 DGX SuperPOD B200 참조 아키텍처는 이 노드 단위를 묶어 확장하는 일반 설계 예를 제공한다. 두 문서는 NVIDIA의 참조·제품 범위를 설명할 뿐, HPE XD685 기반 NHN 시스템의 내부 형태를 증명하지 않는다. [미공개 | SRC-011] TOP500 행만으로는 CL-1이 8-GPU 노드인지, 같은 내부 스위치 구성을 쓰는지, 어떤 NIC를 몇 개 장착했는지 확인할 수 없다.

[실무 제안] 제안서나 운영 문서에는 ‘노드 사양’ 한 줄 대신 경로별 인터페이스를 적는다. 예를 들어 GPU↔GPU에는 내부 패브릭의 가시성, GPU↔NIC에는 PCIe·NUMA 친화성, GPU↔스토리지에는 DMA 경로와 파일시스템 조건, CPU↔GPU에는 호스트 메모리 개입 여부를 기록한다. 이 목록은 벤더 비밀을 요구하는 것이 아니라, 성능 시험과 장애 분석에 필요한 관찰점을 계약하는 방식이다.

HBM과 CPU의 역할

GPU 노드에서 HBM은 GPU가 반복적으로 읽고 쓰는 모델 파라미터, 활성값, 옵티마이저 상태와 같은 작업 집합의 가까운 메모리다. CPU DRAM은 운영체제, 런타임, 데이터 전처리, 통신 제어, 일부 호스트 버퍼처럼 다른 종류의 상태를 담당한다. [설계 해석 | SRC-014, SRC-017] 두 메모리 계층의 용량이나 대역폭을 서로 대입해 우열을 말하는 것은 도움이 되지 않는다. 필요한 질문은 특정 작업이 어느 계층의 부족으로 멈추는가다.

예를 들어 모델이 GPU 메모리에 들어가더라도 입력 변환이 CPU에서 길게 대기하면 GPU는 유휴해질 수 있다. 반대로 CPU 사용률이 낮아도 GPU 메모리 부족으로 배치 크기나 병렬화 방식이 제한될 수 있다. 체크포인트를 만들 때에는 GPU에서 호스트 또는 스토리지로 이동하는 순간이 또 다른 병목이 된다. [실무 제안] 초기 벤치마크는 GPU 사용률 하나 대신 GPU 메모리 점유, CPU 준비 시간, 호스트↔장치 전송 대기, 입력 큐 깊이, 체크포인트 소요 시간을 같은 타임라인에 남긴다. 그래야 ‘GPU가 느리다’는 증상을 어느 계층의 원인으로 분해할 수 있다.

[원자료 | SRC-017] GPUDirect RDMA 가이드는 GPU 메모리와 PCIe peer device 사이의 직접 데이터 경로를 다루며, PCIe 토폴로지가 중요한 조건임을 설명한다. 이는 어떤 GPU–NIC 경로가 자동으로 최적이라는 보장은 아니다. [설계 해석 | SRC-017] 따라서 메모리 설계 검토는 장치 이름 목록보다 GPU, NIC, PCIe root complex, CPU 소켓의 실제 배치와 런타임이 선택한 경로를 함께 확인해야 한다.

관찰 대상 답하려는 질문 수집할 증거 해석의 주의
GPU 메모리 배치·모델 상태가 장치에 안정적으로 들어가는가 피크 점유·할당 실패·재계산 횟수 높은 점유 자체가 병목 증거는 아님
CPU·DRAM 입력 준비와 런타임 제어가 연산을 기다리게 하는가 전처리 시간·호스트 큐·CPU run queue CPU 사용률만으로 데이터 파이프라인을 판단하지 않음
GPU↔NIC 노드 간 통신이 어느 PCIe·NUMA 경로를 쓰는가 토폴로지 출력·지연·재전송·대역폭 시험 일반 참조 토폴로지를 실제 구성으로 가정하지 않음
GPU↔저장소 체크포인트와 데이터 공급이 연산을 멈추게 하는가 I/O 시간·큐 길이·fallback 여부 파일시스템·드라이버 조건을 분리해 기록

NVLink·NVSwitch

노드 내부 다중 GPU 작업은 GPU 사이의 데이터 교환을 요구한다. [원자료 | SRC-013, SRC-014] NVIDIA의 B200 계열 DGX 참조 자료는 GPU 간 연결을 설명하는 NVLink와 여러 GPU 경로를 교환하는 NVSwitch를 일반 설계 배경으로 제시한다. 이 두 이름은 같은 뜻이 아니다. NVLink는 링크·접속의 계층이고, NVSwitch는 다수 경로를 교환하는 구성 요소의 계층이다. 문서에 둘을 함께 쓸 때에는 세대, 링크 수, 집계 방식이 각기 다른 사양일 수 있음을 명시해야 한다.

[원자료 | SRC-015] NCCL은 토폴로지 인지형 multi-GPU collective communication 라이브러리로 문서화되어 있다. [설계 해석 | SRC-015] 이 사실에서 따라오는 실무 결론은 ‘내부 패브릭이 있으니 collective가 항상 빠르다’가 아니다. 집단 통신의 시간은 연산을 참여 GPU에 어떻게 쪼갰는지, 중간 결과가 얼마나 자주 교환되는지, 노드 안과 밖의 경계를 몇 번 넘는지에 따라 달라진다. 동일 모델도 tensor parallelism, data parallelism, pipeline 병렬화의 조합에 따라 내부 경로와 외부 패브릭의 부담이 달라진다.

[미공개 | SRC-011] CL-1·CL-2의 TOP500 표기에는 NVLink/NVSwitch 토폴로지나 NCCL 버전·환경 변수가 없다. FactoryX가 특정 collective 라이브러리, 특정 설정 파일, 특정 NVSwitch 구성을 사용한다고 쓰면 공개 자료의 경계를 넘는다. [실무 제안] 실제 환경에서는 토폴로지 덤프, GPU 간 링크 상태, collective 마이크로벤치, 애플리케이션 단계별 통신 시간을 함께 보관한다. 원시 벤치마크 결과가 서비스 수준의 근거가 되려면 모델, 정밀도, 메시지 크기, 참여 GPU 수와 실행 시점을 같이 적어야 한다.

NIC·rail·NUMA

노드 밖으로 나가는 통신은 NIC 또는 HCA와 PCIe 경로를 지난다. 여기서 rail은 대체로 여러 NIC·스위치 경로를 분산해 대역폭과 장애 격리 목표를 달성하려는 설계 단위를 가리킨다. [설계 해석 | SRC-013, SRC-017] rail의 수는 한 숫자로 좋고 나쁨을 판정할 값이 아니라, GPU–NIC 친화성, 스위치 계층, 혼잡 제어, 장애 시 우회, 소프트웨어의 경로 선택을 묶는 설계 가정이다.

[원자료 | SRC-017] GPUDirect RDMA는 GPU와 제3자 PCIe 장치 사이의 직접 경로를 다루며, 적절한 PCIe root complex 배치가 중요한 제약으로 제시된다. 따라서 NIC가 있다고 해서 모든 GPU가 같은 비용으로 그 NIC에 닿는다는 뜻은 아니다. [실무 제안] 노드 수를 늘리기 전 다음 세 시험을 분리한다. 첫째, 같은 노드 GPU 간 통신이다. 둘째, 서로 다른 노드의 가까운 GPU–NIC 경로다. 셋째, 의도적으로 불리한 NUMA 경로를 포함한 교차 경로다. 결과 차이는 장치 배치·프로세스 바인딩·rail 정책을 바꿀 근거가 된다.

경로 설계 시 확인할 질문 장애·성능 징후 되돌리기 또는 완화
GPU↔GPU 작업의 교환이 노드 안에 머무는가 collective 시간 증가, 링크 상태 경고 병렬화 분할·배치 크기·참여 수 재검토
GPU↔NIC GPU와 NIC의 PCIe·NUMA 관계가 의도와 맞는가 노드별 편차, 특정 프로세스만 지연 바인딩·배치 정책 조정, 토폴로지 재측정
NIC↔패브릭 경로 분산과 장애 우회가 검증됐는가 rail 편중, 재전송, queue 누적 장애 주입 시험, 경로·큐 정책 검토
GPU↔스토리지 데이터·체크포인트 경로가 연산을 가로막는가 입력 공백, 긴 저장 지연 비동기화·스테이징·파일 레이아웃 재검토

[미공개 | SRC-011, SRC-004] NHN의 TOP500 공개 정보와 뉴스룸 설명은 NDR400 사용을 뒷받침하지만, HCA 수, switch 모델, rail 수, NUMA 정책을 공개하지 않는다. [설계 해석 | SRC-011, SRC-017] 그러므로 외부 평가자는 ‘NDR400이므로 rail-aware’라는 결론 대신, 어떤 GPU가 어떤 NIC와 가까운지와 장애 시 교차 경로가 무엇인지 시연해 달라고 요청해야 한다.

벤더 참조와 FactoryX 사실의 경계

FactoryX를 설명할 때 가장 위험한 오류는 서로 맞물려 보이는 두 사실을 같은 사실로 합치는 일이다. 한편으로 [원자료 | SRC-011] TOP500은 NHN Cloud 시스템의 HPE XD685, NVIDIA B200, InfiniBand NDR400을 기록한다. 다른 한편으로 [원자료 | SRC-013, SRC-014] NVIDIA는 DGX B200과 DGX SuperPOD B200의 제품·참조 아키텍처를 제공한다. 전자는 특정 등재 시스템의 공개 식별 정보이고, 후자는 NVIDIA가 제시한 일반 설계이다. 벤더, 섀시, 장치 수, 케이블링, 관리·스토리지 패브릭이 다를 수 있으므로 둘을 겹쳐 그린 도식은 반드시 경계 표시를 가져야 한다.

[공식 발표 | SRC-004] NHN은 FactoryX 서울과 TOP500 등재 맥락에서 NDR400·수랭식 구성을 설명했다. 그러나 이 발표는 공개된 범위 안에서 읽어야 하며, 내부 노드 토폴로지의 상세 증거로 바꾸면 안 된다. [미공개 | SRC-011, SRC-004] GPU 장수와 GPU별 메모리, HCA 배치, NVLink/NVSwitch 구성, NCCL·MPI 버전, GDS 사용 여부는 이 장의 공개 근거로 확인되지 않는다.

이 경계는 표현의 엄격함을 위한 장식이 아니라 설계 책임의 분리다. [실무 제안] 기술 검증 문서에는 ‘확인됨’, ‘일반 참조’, ‘미확인’을 별도 열로 유지한다. 일반 참조가 실제 환경에 적합한지는 성능 시험, 장애 시험, 운영 증적을 통해 확인한다. 확인 전에는 특정 설계를 약속하는 구매 근거나 SLA 가정으로 사용하지 않는다.

5장 InfiniBand·RDMA·집단 통신·스토리지

대규모 GPU 작업에서 연산 장치는 데이터가 도착한 뒤에만 계산할 수 있다. 그러므로 패브릭과 스토리지는 GPU의 부속품이 아니라 학습 단계와 서비스 응답 시간을 함께 결정하는 데이터 이동 계층이다. 여기서 NDR400, RDMA, NCCL, MPI, GPUDirect Storage를 하나의 ‘고속 통신’으로 묶으면 검증 대상이 사라진다. 각각은 포트 속도, 메모리 접근, 집단 통신 API, 표준 인터페이스, 파일 I/O 경로라는 다른 책임을 가진다.

[원자료 | SRC-011] TOP500의 NIPA(NHN Cloud)-CL-1과 CL-2에는 NVIDIA B200과 InfiniBand NDR400이 공개 항목으로 기록돼 있다. [공식 발표 | SRC-004] NHN도 TOP500 등재 소식에서 FactoryX 서울의 NDR400 맥락을 발표했다. 반면 [미공개 | SRC-011, SRC-004] 스위치 모델, rail 수, fat-tree 같은 토폴로지, HCA 수, NCCL·MPI·UCX 버전, 파일시스템과 GDS 사용 여부는 공개 근거에 없다. 이 장은 확인된 ‘NDR400 사용’에서 출발하되, 나머지를 일반 기술 배경과 검증 질문으로 남긴다.

NDR400과 RDMA

[원자료 | SRC-013] NVIDIA의 B200 참조 아키텍처는 NDR InfiniBand를 방향당 최대 400 Gbps로 설명한다. 이 값은 포트·방향 기준의 링크 속도다. 애플리케이션이 처리하는 유효 대역폭, 하나의 노드가 동시에 얻는 합계, 특정 워크로드의 step time과 같은 값은 아니다. 프로토콜 오버헤드, 메시지 크기, 혼잡, 경로 편중, GPU–NIC PCIe 관계, 소프트웨어 버전이 실제 결과를 바꿀 수 있다. [설계 해석 | SRC-013, SRC-017] 따라서 ‘NDR400’이라는 표기는 설계 검토의 출발점이며 성능 보증 문장이 아니다.

[원자료 | SRC-017] GPUDirect RDMA는 GPU 메모리와 제3자 PCIe 장치 사이의 직접 데이터 경로를 다루는 기술이다. CPU를 거치는 복사 경로를 줄일 수 있다는 설명과, 실제 모든 전송이 그 경로를 사용한다는 주장은 다르다. PCIe root complex, IOMMU·드라이버 설정, 메모리 등록, NIC·GPU의 배치, 메시지 패턴에 따라 경로와 효과가 달라진다. [실무 제안] 실험 보고서에는 RDMA 활성 여부만 쓰지 말고 GPU–NIC 쌍, 메시지 크기 구간, 동시 통신 수, CPU 개입, 재시도·오류 지표를 함께 남긴다.

용어 직접 답하는 질문 직접 보장하지 않는 것 FactoryX 공개 상태
NDR400 포트가 지닌 명목 링크 속도는 무엇인가 애플리케이션 유효 대역폭·토폴로지 NDR400 표기는 확인됨 [원자료 | SRC-011]
RDMA 원격 메모리 접근 경로를 어떻게 줄일 수 있는가 모든 작업의 GPU 직접 경로 기술 일반 배경 [원자료 | SRC-017]
GPUDirect RDMA GPU와 PCIe peer 간 경로 조건은 무엇인가 특정 클러스터의 활성화·처리량 NHN 사용 여부 미공개 [미공개 | SRC-011]
rail 여러 네트워크 경로를 어떻게 배치·격리하는가 자동 균등 분산과 무장애 NHN rail 구성 미공개 [미공개 | SRC-011, SRC-004]

[설계 해석 | SRC-011, SRC-013] 같은 400 Gbps라는 표기를 가진 두 환경도 포트가 어느 GPU와 가까운지, 스위치 업링크가 어떻게 과구독되는지, 장애 때 어느 경로를 쓰는지에 따라 다르게 동작한다. 리뷰에서 필요한 질문은 ‘NDR400인가’보다 ‘누가 어느 포트로, 어떤 크기의 데이터를, 어느 시간에 보내는가’다.

집단 통신 패턴

여러 GPU가 하나의 학습 단계를 마칠 때 자주 등장하는 것은 같은 값을 모으거나, 나누거나, 모든 참여자에게 배포하는 집단 통신이다. AllReduce, AllGather, ReduceScatter, Broadcast는 데이터가 어느 참여자에 모이고 다시 어떻게 나뉘는지를 가리킨다. [원자료 | SRC-015] NVIDIA NCCL 문서는 이러한 multi-GPU collective를 제공하며 토폴로지를 인식해 통신을 수행한다고 설명한다. [설계 해석 | SRC-015] 여기서 토폴로지 인지는 라이브러리가 경로 정보를 활용할 수 있다는 뜻이지, 혼잡·불균형·패킷 손실이 사라진다는 약속은 아니다.

통신 패턴을 설계에서 분리해야 하는 이유는 데이터량만 같아도 시간적 모양이 다르기 때문이다. 모든 GPU가 한 번에 전송을 시작하면 링크를 공유하는 순간이 짧고 강하게 나타날 수 있다. 파이프라인 단계가 어긋나면 작은 메시지가 여러 차례 쌓일 수 있다. 체크포인트 저장은 training collective와 같은 NIC·스토리지 경로를 경쟁할 수 있다. [실무 제안] ‘평균 네트워크 사용률’만으로 판단하지 말고 단계 경계의 p50·p95·p99 통신 시간, 참여 GPU 수, 메시지 크기 분포, 실패 후 재시도 시간을 분리해 본다.

[미공개 | SRC-011] TOP500 등재 정보는 해당 NHN 시스템이 어떤 collective 알고리즘, 메시지 분할, NCCL 환경 변수, 혼잡 제어 정책을 썼는지 공개하지 않는다. [설계 해석 | SRC-011, SRC-015] 그러므로 특정 시스템이 ring·tree·계층형 알고리즘 중 무엇을 사용했다고 단정하지 않고, 작업별로 선택된 경로와 실행 로그를 보존하도록 요구해야 한다.

패턴 또는 상태 관찰할 데이터 이동 성능 검토 질문 장애 검토 질문
AllReduce 계열 참여 GPU의 결과를 줄이고 다시 배포 연산 대비 통신 비중은 얼마인가 한 참여자 지연이 전체 단계를 얼마나 늦추는가
AllGather 계열 분할된 조각을 모든 참여자에 모음 메모리·메시지 크기가 피크를 만드는가 특정 조각 손실 뒤 재시도 범위는 어디까지인가
ReduceScatter 계열 줄인 결과를 각 참여자에 분산 분할 방식이 다음 연산과 맞는가 불균형한 조각이 긴 꼬리를 만드는가
체크포인트 동시 실행 모델 상태를 스토리지로 이동 collective와 I/O가 경합하는가 저장 실패 시 재시작 지점은 명확한가

NCCL과 MPI의 책임

NCCL과 MPI는 종종 같은 작업에서 보이지만 같은 계층의 대체재라고 단순화할 수 없다. [원자료 | SRC-015] NCCL은 NVIDIA GPU 환경의 collective communication을 위한 라이브러리 문서다. [원자료 | SRC-018] MPI 4.1은 process topology와 collective communication을 포함한 병렬 프로그램 인터페이스의 공개 표준이다. 한 애플리케이션이 MPI로 프로세스의 논리적 협업을 표현하면서 GPU 집단 통신에는 NCCL을 사용할 수 있고, 다른 실행 환경은 다른 구현 조합을 사용할 수 있다.

[설계 해석 | SRC-015, SRC-018] 운영상 핵심은 라이브러리 이름을 맞히는 것이 아니라 오류와 성능 책임이 어느 층에 있는지 가르는 일이다. NCCL 초기화 실패, MPI rank 배치 오류, NIC 링크 상태, 스위치 혼잡, 스토리지 backpressure는 같은 ‘분산 학습 실패’로 보이지만 수집할 로그와 복구 방법이 다르다. 로그에는 작업 식별자, rank 또는 GPU 배치, collective 종류, 네트워크 인터페이스, 오류 코드, 재시도·중단 결정을 연결해야 한다.

[미공개 | SRC-011, SRC-004] NHN의 공개 자료는 CL-1·CL-2에서 NCCL, MPI 또는 다른 런타임의 제품명·버전을 확인시키지 않는다. [실무 제안] 벤더 평가에서는 ‘어떤 라이브러리를 쓰는가’보다 ‘집단 통신 오류를 노드·NIC·스위치·프로세스 층으로 구분해 보여줄 수 있는가’, ‘장애가 났을 때 어느 rank와 어느 작업을 안전하게 다시 시작하는가’를 질문한다.

스토리지 데이터 경로

학습용 데이터, 임시 캐시, 체크포인트, 모델 아티팩트는 서로 다른 접근 패턴을 가진다. 데이터셋은 큰 파일을 순차로 읽을 수 있고, 체크포인트는 일정 시점에 많은 worker가 함께 쓰기를 시작할 수 있으며, 추론 모델은 시작 시 적재 후 비교적 안정된 메모리 접근을 할 수 있다. [설계 해석 | SRC-016] 따라서 스토리지 성능을 단일 GB/s 숫자로 표현하면 읽기·쓰기, 크기, 동시성, 캐시, 일관성 요구가 지워진다.

[원자료 | SRC-016] NVIDIA GPUDirect Storage는 GPU 메모리와 스토리지 사이의 직접 DMA 경로를 다루며, cuFile, O_DIRECT, 지원 파일시스템·드라이버·토폴로지 조건을 설명한다. 직접 경로가 가능할 때 CPU bounce buffer를 줄일 수 있다는 설명은 ‘항상 zero-copy’라는 의미가 아니다. 지원되지 않는 조건, 정렬되지 않은 I/O, 구성 제약에서는 compatibility 또는 fallback 경로가 사용될 수 있다. [실무 제안] GDS 도입 검증은 기능 켜짐 여부가 아니라 파일시스템별·I/O 크기별·동시성별 경로와 fallback 횟수, GPU 유휴 시간, 체크포인트 복구 시간을 측정하는 방식으로 수행한다.

[미공개 | SRC-011, SRC-004] NHN의 공개 TOP500·뉴스룸 자료에는 CL-1·CL-2의 공유 스토리지 종류, 로컬 NVMe 사용, GPUDirect Storage 활성화, 메타데이터 서버, 파일시스템 조정 값이 없다. 따라서 GDS가 지원 가능한 일반 기술이라는 문장을 FactoryX가 사용 중이라는 문장으로 바꾸면 안 된다.

혼잡·rail·장애

혼잡은 평균 사용률이 낮아도 특정 단계에 집중될 수 있다. 여러 작업이 같은 스위치 업링크, 같은 NIC, 같은 스토리지 대상에 몰리면 짧은 대기열이 collective의 긴 꼬리로 증폭될 수 있다. [설계 해석 | SRC-013, SRC-015, SRC-016] 이 현상은 패브릭만의 문제가 아니다. 작업 스케줄러가 같은 시간에 checkpoint를 유도하거나, 데이터 로더가 같은 파일 조각을 읽거나, 장애 재시도가 한 경로로 몰려도 발생한다.

[원자료 | SRC-013] DGX SuperPOD B200 참조 자료는 확장 패브릭과 스토리지·관리 네트워크를 구분하는 일반 구조를 제시한다. [설계 해석 | SRC-013] 이 분리는 실제 환경에서도 장애 도메인과 관측 책임을 나누는 유용한 출발점이 될 수 있지만, NHN의 실제 분리 방식에 대한 증거는 아니다. [미공개 | SRC-011] CL-1·CL-2의 rail 설계, 스위치 수, 과구독 비율, 우회 경로는 공개되지 않았다.

[실무 제안] 장애 시험은 단순 링크 down만으로 끝내지 않는다. 하나의 NIC·rail·스위치 경로가 성능 저하 상태일 때 작업이 어떤 알림을 내는지, 새로운 작업 admission을 제한하는지, 이미 실행 중인 job을 재시도하는지, checkpoint가 일관되게 남는지를 순서대로 확인한다. 복구 목표에는 네트워크 복구 시간뿐 아니라 작업 재개 시간과 데이터 무결성 검증 시간을 포함한다.

6장 클러스터 성능·용량·벤치마크

성능 수치는 설계의 출발점이지만, 다른 시험과 단위를 같은 막대에 놓으면 판단을 망친다. FP8 EFlops, TOP500 Rmax·Rpeak, GPU 장수, TOP500 cores는 서로 다른 질문에 답한다.

[공식 발표 | SRC-003] NHN은 FP8 기준 27.4 EFlops를 제시했다. [공식 발표 | SRC-003, SRC-005] 7,656 B200 GPU와 4,080 GPU는 별도 발표 범위다. [원자료 | SRC-011] TOP500은 CL-1·CL-2의 Rmax·Rpeak·순위·#Proc./Cores를 공개한다. 이 값들은 같은 축에서 비율·합계·우열을 계산하지 않는다.

Rmax와 Rpeak

[원자료 | SRC-012] TOP500은 Rmax를 LINPACK 시험에서 달성된 성능으로, Rpeak를 시스템의 이론적 최대 성능으로 설명하고 Rmax를 기준으로 목록을 정렬한다. 이 정의는 명확하지만 ‘해당 시스템이 모든 AI 작업에서 이만큼 빠르다’는 뜻은 아니다. LINPACK은 특정 선형대수 시험이고, 실제 학습·추론에는 모델 구조, 정밀도, 통신, 입력·출력, 메모리 용량, 재시도와 큐 대기가 더해진다.

[원자료 | SRC-011] 2026년 6월 목록에서 NIPA(NHN Cloud)-CL-1은 20위, Rmax 137.40 PFlop/s, Rpeak 156.48 PFlop/s로 기록됐다. 같은 목록의 CL-2는 40위, Rmax 68.42 PFlop/s, Rpeak 77.94 PFlop/s다. 이 네 성능 값은 같은 LINPACK 문맥 안에서 CL-1과 CL-2를 읽을 때만 비교할 수 있다. [설계 해석 | SRC-011, SRC-012] 두 값의 차이는 벤치마크 효율, 구성, 시험 조건을 살필 출발점이지, 특정 LLM 학습 시간 또는 사용자 요청 처리량의 배수로 곧장 바꿀 근거는 아니다.

FP8 EFlops의 별도 의미

[공식 발표 | SRC-003] 27.4 EFlops는 NHN이 FactoryX에 대해 FP8 기준으로 제시한 AI 연산 성능이다. ‘E’와 ‘P’는 접두어가 달라 숫자 크기를 환산할 수 있어 보이지만, 환산 가능한 접두어라는 사실은 벤치마크와 정밀도, 연산 정의, 시스템 경계까지 같다는 뜻이 아니다. FP8 AI 연산 성능과 TOP500 LINPACK Rmax·Rpeak는 측정 정밀도와 워크로드가 다르다. [원자료 | SRC-012] TOP500 수치는 LINPACK 정의로 읽어야 한다.

[설계 해석 | SRC-003, SRC-011, SRC-012] FP8 발표값과 CL-1의 LINPACK 수치를 한 그래프·비율로 만들면 다른 시험을 경쟁시키는 오류가 된다. FP8 발표값을 7,656 GPU 또는 4,080 GPU로 나눠 장치당 성능이라고 표현해서도 안 된다. 시스템 경계와 수량의 관계가 공개되지 않았기 때문이다.

[실무 제안] 대시보드는 FP8 발표, TOP500 LINPACK, 학습 완료 시간, 추론 SLO를 별도 카드로 둔다. 카드는 연결해도 공통 순위 축으로 합치지 않는다.

학습 성능

학습 성능의 질문은 ‘요구 품질로 언제 끝나는가’다. [설계 해석] 단계 시간 = 연산 + 통신 + 입력 + 대기·재시도는 계측 항목을 빠뜨리지 않기 위한 운영 모델이며 공식 벤치마크가 아니다. 모델·batch·정밀도·병렬화·checkpoint·혼잡에 따라 각 항의 비중이 달라진다.

[원자료 | SRC-015] NCCL은 토폴로지 인지형 GPU collective를, [원자료 | SRC-016] GDS는 조건부 스토리지–GPU 직접 DMA 경로를 설명한다. [설계 해석 | SRC-015, SRC-016] 둘은 완료 시간 보증이 아니다. 시험에는 데이터셋·모델·드라이버 버전, 분산 방식, 참여 GPU, warm-up, 재시도를 남긴다.

[실무 제안] 학습 계획은 최고 token/s 대신 총 step, 허용 완료 시각, 재시도 예산, checkpoint 복구 시간을 먼저 정한다. 정상·혼잡·부분 장애 세 조건을 반복 측정해 보정한다.

추론 성능

추론은 평균 처리량만으로 사용자 경험을 설명하기 어렵다. 첫 응답, 토큰 간 지연, 긴 입력의 메모리·큐 압력, 오류·fallback 결과가 함께 보인다. [설계 해석] 배치 처리량을 높이면 지연이, 복제본을 줄이면 대기열이 커질 수 있으므로 학습 완료 시간과 추론 지연·처리량을 하나의 값으로 합치지 않는다.

[실무 제안] 추론 SLO는 첫 응답·생성 지연, 성공률, 품질·안전 통과율, 큐 대기, 요청당 가속기 시간으로 나눈다. 프롬프트·출력 길이, 동시성, 도구·캐시 여부를 함께 기록한다.

[미공개 | SRC-003, SRC-001] FactoryX 공식 공개 자료는 이 장에서 제시한 특정 모델의 추론 지연, token 처리량, 큐 정책, 서비스별 GPU 배치 값을 확인시키지 않는다. [설계 해석 | SRC-001, SRC-003] 공개된 27.4 EFlops를 개별 API의 SLO나 사용자당 처리량으로 환산하지 않는 이유도 여기에 있다.

용량 계획식

[설계 해석] 용량 계획은 GPU 장수에서 시작하지 않고 수요·완료 조건·손실 요인을 명시하는 식에서 시작한다. 한 기간의 필요한 GPU-시간을 단순화하면 예상 작업 수 × 작업당 GPU 수 × 작업당 실행 시간으로 적을 수 있다. 여기에 재시도, 운영 여유, 계획된 점검, 수요 피크, 예약 단위로 생기는 손실을 별도 항으로 더한다. 이 식은 실측 값이 아니라 가정을 공개하기 위한 틀이다. 숫자를 넣을 때에는 정상 조건과 혼잡·장애 조건을 같은 표에 섞지 않는다.

학습은 장시간 예약·복구 비용을, 추론은 짧은 피크·지연 SLO를 우선한다. [설계 해석 | SRC-011, SRC-015, SRC-016] 패브릭·스토리지 제한은 GPU가 남아도 시작·완료를 막을 수 있으므로 예약률만으로 여유를 정의하지 않는다.

7장 GPU 동적 할당과 GPUaaS 제어면

GPUaaS의 품질은 서로 다른 요청을 어떤 규칙으로 받아들이고 실행·회수하는가에 좌우된다. 학습은 긴 시간의 다수 GPU 묶음을, 추론은 짧은 지연과 예측 가능한 복구를 요구한다. 이 장은 공개된 FactoryX 주장과 검증용 업계 설계 대안을 분리한다.

GPU Live의 공개 범위

[공식 발표] NHN은 FactoryX의 Platform 레이어에 GPU Live를 두고, 학습·추론 자동 분리, 동적 자원 할당, 에너지 효율 기반 스케줄링을 제공한다고 발표했다. 이 설명만으로 우선순위 함수, 선점·분할 방식, 스케줄러, 텔레메트리 보존 기간까지 알 수는 없다. [SRC-001, SRC-003]

[미공개] 공개 자료에서 GPU Live의 내부 구현이 Kubernetes DRA, Kueue, NVIDIA MIG, Slurm GRES 가운데 무엇을 쓰는지, 또는 이들을 어떤 조합으로 연결하는지는 확인되지 않는다. 따라서 아래의 기술 이름은 FactoryX 기능의 증거가 아니라 제품 평가 시 책임을 나누기 위한 업계 설계 대안이다. 이 경계를 지키면 “동적 할당”이라는 한 표현으로 장치 모델링, 큐 운영, 하드웨어 분할, HPC 예약을 모두 설명하는 오류를 피할 수 있다. [SRC-002, SRC-003, SRC-023, SRC-024, SRC-026, SRC-027]

구분 공개 자료로 확인한 내용 공개 자료만으로 확인할 수 없는 내용 근거
GPU Live 학습·추론 분리, 동적 자원 할당, 에너지 효율 스케줄링이라는 기능 설명 실제 오케스트레이터, 큐 정책, 장치 드라이버 [공식 발표] SRC-003
FactoryX Platform GPU Live와 AI EasyMaker의 공개 위치 두 제품 사이의 내부 API·상태 모델 [공식 발표] SRC-001
기술 백서 안내 GPU 동적 할당과 GPUaaS 운영 구조가 주제에 포함됨 신청형 백서 본문의 구현 세부 [공식 발표] SRC-002

[설계 해석] 이 표의 빈 칸은 부족한 설명을 상상으로 채울 자리가 아니라, 도입 전 데모와 운영 문서로 확인할 질문의 목록이다. 예를 들어 고객이 “즉시 회수”를 요구한다면, 최소 보장 실행 시간, 체크포인트 가능 여부, 선점 통지, 재시도 순서가 함께 제시되어야 한다. GPU를 동적으로 붙이는 것과 이미 실행 중인 작업을 안전하게 중단시키는 것은 다른 능력이다.

제어면과 데이터면

[설계 해석] 제어면은 요청을 받아 정책을 적용하고 “누가, 어떤 조건에서, 어느 정도의 자원을 얻는가”를 결정하는 부분이다. 데이터면은 그 결정 뒤에 실제 컨테이너·프로세스·GPU 메모리·네트워크가 일을 수행하는 부분이다. 제어면의 승인 레코드가 데이터면의 실행 ID와 연결되지 않으면, 큐 대기는 줄었는데 작업 완료 시간이 늘어난 이유나, 특정 회수 조치가 어느 사용자 작업에 영향을 주었는지를 사후에 재구성하기 어렵다.

요청에는 GPU 개수 외에 묶음 조건, 분할 프로파일, 예상 시간, 체크포인트, 재시도, 마감 시각이 필요하다. 지원하지 않는 속성도 명확히 돌려줘야 수락된 요청과 실행 가능한 요청을 혼동하지 않는다.

[원자료] Kubernetes DRA는 특수 장치를 ResourceClaim 등으로 표현하여 워크로드의 장치 요청과 할당을 연결하는 일반적인 모델을 제공한다. DRA의 장치 상태와 할당은 장치 표현의 문제이지, 공정 큐 정책이나 모든 형태의 선점을 자동으로 해결하는 기능은 아니다. 특히 문서화된 제약을 확인하지 않고 DRA를 즉시 회수 장치로 간주해서는 안 된다. [SRC-023]

제어면 결정 데이터면에서 확인할 결과 실패 시 남길 증거 설계상 질문
요청 수락 또는 거절 제출 ID와 검증 오류 요청 원문·정책 버전 어떤 속성이 필수인가
입장 허가 큐·쿼터·우선순위 상태 승인 시각·대기 원인 대기 순위는 설명 가능한가
장치 할당 노드·장치·프로파일 할당 ID·장치 건강 상태 동일 요청을 재현할 수 있는가
실행 종료 또는 회수 종료 코드·체크포인트·해제 조치 주체·통지·복구 결과 누가 어떤 기준으로 회수했는가

[실무 제안] 제어면 변경은 정책 버전과 함께 기록한다. 같은 작업이 어제와 오늘 다른 큐에서 승인되었다면, GPU 사용률 그래프만으로는 이유를 알 수 없다. 요청 속성, 당시의 쿼터·우선순위 규칙, 장치 상태, 최종 배치 결정을 하나의 추적 키로 묶어야 한다. 이 제안은 특정 제품의 내장 기능을 뜻하지 않으며, 운영 계약에 포함할 증거 형식이다.

장치 할당·큐·분할·GRES

[원자료] Kubernetes DRA는 장치를 선언·발견·선택·할당하는 경로를 다룬다. Kueue는 워크로드의 admission, quota, priority, resource flavor, cohort 같은 큐 운영 책임을 다룬다. NVIDIA MIG는 지원되는 GPU에서 하드웨어 자원을 격리된 인스턴스로 나누는 방식이며, Slurm GRES는 HPC 작업이 GPU 같은 일반 자원을 예약하고 바인딩하는 방식이다. DCGM Exporter는 GPU 텔레메트리를 Prometheus 형식으로 노출하는 관측 대안이다. 다섯 기술은 같은 계층의 동의어가 아니다. [SRC-023, SRC-024, SRC-026, SRC-027, SRC-028]

[원자료] MIG 구성 변경은 해당 GPU의 사용자 워크로드가 없는 상태를 요구할 수 있고, 운영 환경에 따라 노드 차단이나 재시작 절차가 수반될 수 있다. Slurm GRES 문서도 MIG 파티셔닝 자체를 Slurm이 동적으로 수행하는 기능으로 설명하지 않는다. 그러므로 “분할” 요구사항에는 프로파일 전환을 위한 중단 창, 기존 작업의 안전한 배출, 구성 변경 뒤 재발견, 관측 공백을 함께 적어야 한다. [SRC-026, SRC-027]

[설계 해석] 핵심은 장치 분할, 큐 권리 계산, 노드 바인딩, 관측의 책임을 섞지 않는 것이다. 제품 데모에서는 요청 하나의 거절·대기·승인·실행·종료 상태와 소유자를 따로 확인한다.

공정성과 우선순위

[원자료] Kueue의 공정 공유 문서는 cohort 안에서 유휴 quota를 빌리고, 사용량과 가중치를 바탕으로 admission 우선순위를 조정하는 개념을 설명한다. 이는 “먼저 온 요청이 항상 먼저 실행된다”는 정책과 다르며, 공정성의 정의가 조직의 우선순위와 기간별 사용량에 따라 달라질 수 있음을 보여준다. Kueue가 FactoryX에 사용된다는 뜻은 아니다. [SRC-024, SRC-025]

[설계 해석] GPU 플랫폼의 공정성은 단일 비율이 아니라 세 질문의 조합이다. 첫째, 팀마다 보장된 최소 용량이 있는가. 둘째, 남는 용량을 어느 팀이 어떤 기간 동안 빌릴 수 있는가. 셋째, 긴 학습이 짧은 긴급 추론 요청을 막을 때 어떤 작업을 보호하고 어떤 작업을 조정할 것인가. 이 질문에 답하지 않은 “공정 스케줄링”은 운영자가 분쟁을 판정할 규칙을 제공하지 못한다.

보장 쿼터 팀·서비스별 최소량과 기간 보장량 미사용·초과 사용 과도한 유휴 예약이 반복될 때
대여 남는 자원의 대여 단위와 만료 대여량·반납 지연 보장 팀의 대기 시간이 악화될 때
우선순위 긴급도·업무 영향·마감의 증거 우선 요청 비율·대기 분포 일반 작업이 지속 기아 상태일 때
선점·회수 통지·유예·체크포인트 규칙 중단 횟수·복구 성공률 재시도 비용이 절감 효과를 넘을 때

[실무 제안] 정책은 과거 요청 로그 시뮬레이션과 제한 풀 관찰로 나눠 검증한다. 전자는 예상치 못한 대기를, 후자는 실제 체크포인트·운영자 개입과 거절 사유의 설명 가능성을 확인한다.

단편화와 회수

[저자 계산] CHT-008은 8-GPU 노드 한 대, 비선점 작업, 요청별 GPU가 같은 노드에 모여야 한다는 조건만 둔 설명용 계산이다. 먼저 3-GPU 작업과 2-GPU 작업을 허용하면 잔여 용량은 3 GPU다. 그 시점에 4-GPU 요청은 총 잔여가 3 GPU이므로 대기한다. 3-GPU 작업이 끝나면 잔여 용량은 6 GPU가 되고 4-GPU 요청을 허용할 수 있다. 이는 실측 활용률이나 FactoryX의 배치 규칙이 아니라, 요청 크기와 남은 연속 할당 가능 용량이 어긋날 때 대기가 생기는 과정을 보이는 가정이다. [CLM-022]

여러 노드 풀에는 노드별 여유, GPU 모델·메모리, 네트워크 근접성, 분할 프로파일, 예약 만료가 더해진다. [설계 해석] 단편화는 하나의 숫자가 아니라 묶음 요구와 자원 이질성을 함께 보여 주는 관찰 항목이다.

[실무 제안] 회수에는 최소 네 상태가 필요하다. 완료로 인한 정상 해제, 사용자가 취소한 해제, 정책이 통지 후 수행한 중단, 장애로 확인되어 보류된 해제다. 이 상태를 모두 “free”로 합치면, 회수 정책이 대기를 줄였는지 단지 작업을 잃게 했는지 구별할 수 없다. 회수 전에는 체크포인트 주소와 마지막 정상 진행 시점을 확인하고, 회수 후에는 다음 작업이 받은 장치와 이전 작업의 재시도 결과를 연결한다.

벤더 검증 질문

[공식 발표] GPU Live의 공개 기능은 학습·추론 분리와 동적 자원 할당이다. 검증은 단순 할당 시연보다 요청의 실패·대기·회수까지 설명해야 한다. [SRC-003]

검증 질문 받아야 할 증거 불충분한 답변의 예
학습과 추론은 어떤 속성으로 구분되는가 분류 규칙·예외·변경 이력 화면에서 다른 색으로 보인다는 설명
요청이 대기한 이유는 무엇인가 쿼터·우선순위·장치 조건별 사유 단순히 자원이 부족하다는 메시지
분할 프로파일을 바꾸면 무엇이 중단되는가 영향 작업·통지·복구 절차 무중단이라는 일반적 약속
정책 회수 뒤 작업은 어떻게 재개되는가 체크포인트·재시도·실패 코드 재시작 가능하다는 추상적 답변
에너지 효율 정책은 무엇을 제한하는가 전력·열·지연·완료시간 가드레일 전력만 낮아진다는 주장

[실무 제안] 이 질문은 DRA·Kueue·MIG·Slurm·DCGM을 채택하라는 목록이 아니다. 각 기술이 다루는 책임을 이용해, 어떤 구현이든 설명해야 할 상태 전이와 증거를 빠뜨리지 않게 하는 질문 목록이다. 공개 문서에 없는 답을 요구할 때는 비공개 아키텍처를 추측하지 말고, 고객 환경에서 제공 가능한 운영 로그·API·SLA·장애 절차의 범위를 계약으로 확인한다.

모델의 첫 학습은 수명주기의 시작일 뿐이다. 운영에서 다시 써야 할 것은 가중치 파일 하나가 아니라, 어떤 데이터와 코드와 환경에서 만들어졌는지, 어떤 평가를 통과했는지, 어느 엔드포인트에 어떤 방식으로 배포되었는지, 문제가 생기면 무엇으로 돌아갈지를 설명하는 증거 묶음이다. 이 장은 AI EasyMaker의 공개 기능을 출발점으로 삼되, 공개 자료에 없는 feature store·자동 드리프트 감지·승인형 레지스트리 같은 기능을 제품 사실로 확장하지 않는다.

AI EasyMaker의 공개 기능

[공식 발표] AI EasyMaker 공식 개요는 TensorFlow·PyTorch 기반 Jupyter Notebook 개발 환경, CPU/GPU 인스턴스와 저장공간을 지정하는 학습, 최대 10노드 분산 학습, TensorBoard 기반 결과 분석, 모델 아티팩트 관리와 성능 비교, 엔드포인트 관리의 범위를 안내한다. FactoryX 발표는 AI EasyMaker를 컨테이너 기반 표준 환경에서 학습·배포·운영을 지원하는 Platform 레이어의 제품으로 설명한다. 이 두 출처는 학습부터 운영까지 연결하려는 공개 방향을 뒷받침하지만, 모든 MLOps 기능의 제공을 보증하지는 않는다. [SRC-003, SRC-007]

[공식 발표] AI EasyMaker 릴리스 노트에는 ML Pipeline, 개인 컨테이너 이미지, 배치 추론, RAG, NVIDIA Triton Inference Server, 엔드포인트 리소스 설정, 파인 튜닝 같은 기능 변화가 날짜와 함께 기록되어 있다. 이러한 항목은 현재 기능을 확인할 때 유용하지만, 롤링 릴리스 문서이므로 기준일과 버전을 함께 보아야 한다. [SRC-008]

수명주기 영역 공개 문서에서 확인한 범위 이 장에서 제품 사실로 단정하지 않는 범위 근거
개발·학습 Notebook, CPU/GPU 학습, 저장공간, 최대 10노드 분산 학습 모든 프레임워크·모든 분산 방식의 지원 [공식 발표] SRC-007
실험 TensorBoard 기반 분석, 반복 실험 비교, 튜닝 관련 기능 전사 표준 실험 추적 정책 [공식 발표] SRC-007·SRC-008
모델·서빙 모델 아티팩트 관리·성능 비교, 엔드포인트 관리 승인형 레지스트리·드리프트 자동 판정 [공식 발표] SRC-007
파이프라인·확장 기능 Kubeflow Pipelines SDK, RAG, Triton 관련 공개 안내 FactoryX 내부 연결 방식과 보존 정책 [공식 발표] SRC-007·SRC-008

[설계 해석] “통합 MLOps”라는 표현은 도구 목록이 아니라 경계의 질문으로 읽어야 한다. 개발 환경에서 생성한 산출물의 식별자가 학습 작업, 평가 결과, 모델 아티팩트, 배포 구성, 운영 사건과 이어질 때만 특정 결과를 다시 만들거나 되돌릴 수 있다. 제품 화면이 여러 단계를 제공해도, 단계 사이에 무엇을 보존하고 누가 승인하는지 정하지 않으면 수명주기는 끊긴다.

실험에서 등록까지

[설계 해석] 실험은 “좋아 보이는 모델”을 만드는 활동이 아니라, 다음 판정을 재현할 수 있게 만드는 활동이다. 따라서 실험 기록에는 최소한 코드 리비전, 컨테이너 이미지 식별자, 데이터셋의 버전 또는 조회 조건, 학습 파라미터, 하드웨어·분산 조건, 난수 시드의 처리 방식, 생성된 아티팩트의 해시 또는 불변 식별자를 남긴다. 데이터 원문을 모두 복사하라는 뜻은 아니다. 접근 권한과 보존 정책을 해치지 않는 범위에서 “동일한 입력을 다시 선택할 수 있는 참조”를 남기라는 뜻이다.

[공식 발표] AI EasyMaker는 학습 결과 분석과 반복 실험 비교를 위한 TensorBoard 기반 기능을 안내한다. 이 기능은 실험의 비교 화면에 해당한다. 그러나 어떤 지표가 배포 승인 기준인지, 누가 기준을 변경할 수 있는지, 비교 대상 데이터셋을 언제 동결하는지는 팀의 운영 규칙으로 별도 결정해야 한다. [SRC-007]

단계 반드시 연결할 입력 보존할 산출물 재현 질문
개발 코드 리비전·의존성·컨테이너 실행 명령·이미지 식별자 같은 환경을 만들 수 있는가
학습 데이터 참조·파라미터·자원 조건 로그·체크포인트·모델 아티팩트 같은 입력에서 차이를 설명할 수 있는가
평가 평가 데이터셋·지표 정의·임계값 점수·오류 표본·판정자 같은 기준으로 통과 여부를 재판정할 수 있는가
등록 승인된 모델 식별자·부모 실험 계보 링크·변경 사유 배포 대상이 어느 실험에서 왔는가

[실무 제안] 등록은 파일을 한 폴더로 옮기는 행위가 아니라, 배포 후보를 가리키는 불변 참조를 만드는 단계로 설계한다. 사람 친화적인 별칭은 바뀔 수 있지만, 운영 배포가 참조한 모델·평가·구성 조합은 나중에 변하면 안 된다. 등록을 허용하는 사람과 평가를 만든 사람이 같아도 되는지, 비상 배포에서 어떤 사후 승인이 필요한지는 조직의 위험도에 맞춰 결정한다.

[설계 해석] 비교의 단위도 명확히 해야 한다. 하나의 모델이 점수에서 앞서더라도 응답 지연, 메모리 사용, 안전성 오류, 실패 요청의 재시도 비용이 달라질 수 있다. 그러므로 “새 버전이 더 좋다”라는 결론은 지표, 평가 데이터 범위, 측정 시각, 비교 대상, 허용 오차를 함께 기록한 판정문이어야 한다. 외부 벤치마크 순위나 단일 평균 점수만으로 업무 배포를 승인하지 않는 이유가 여기에 있다.

배포와 단계 전환

[공식 발표] AI EasyMaker 문서는 엔드포인트 관리, 이중화, 테스트 스테이지와 기본 도메인 전환을 안내한다. 공개된 기능은 단계적 배포를 검토할 출발점이지만, 실제 트래픽 분할 방식, 고객별 격리, 자동 승격 조건, 서비스 수준 목표는 배포 대상과 계약에 따라 별도로 확인해야 한다. [SRC-007]

[설계 해석] 배포 단계는 이름보다 전환 조건이 중요하다. 개발자는 새 모델을 테스트 단계에 올리고, 평가는 미리 정한 데이터·지표·안전 규칙을 확인하며, 운영자는 실제 요청의 지연·오류·자원 사용을 본다. 이 세 관점이 다른 식별자를 사용하면 “시험한 모델”과 “실제로 노출된 모델”이 달라질 수 있다. 각 단계 전환 기록에는 모델 ID, 서빙 이미지, 입력 스키마, 자원 설정, 트래픽 범위, 승인자, 되돌릴 대상이 함께 있어야 한다.

전환 들어가기 전 증거 운영 중 관측 중단 또는 되돌림 조건
개발 → 테스트 재현 가능한 학습·평가 묶음 기능 오류·입력 호환성 입력 계약이 깨질 때
테스트 → 제한 배포 평가 결과·위험 검토·트래픽 범위 지연·오류·안전 이벤트 기준선 대비 악화가 확인될 때
제한 배포 → 확대 제한 범위의 결과·운영자 승인 업무 완료·재시도·지원 요청 피해 범위가 확대될 때
확대 → 안정 운영 런북·온콜·롤백 연습 SLO·비용·모델 품질 롤백 경로가 검증되지 않았을 때

[실무 제안] 단계 전환에 자동화가 있더라도, 자동화의 입력은 검증 가능한 증거여야 한다. 예컨대 오류율이 낮다는 조건만으로 확대하지 말고, 평가 데이터와 실제 요청의 분포 차이, 사용자에게 영향이 큰 실패 유형, 긴 꼬리 지연, 수동 승인 필요 여부를 함께 검토한다. 이 가드레일은 AI EasyMaker의 특정 자동 승격 기능을 주장하지 않는다.

파이프라인과 재현성

[공식 발표] AI EasyMaker의 공개 안내는 Kubeflow Pipelines SDK를 이용해 전처리·학습·평가·배포 단계를 연결하는 파이프라인 범위를 제시한다. 파이프라인이 있다는 사실은 단계를 코드화할 가능성을 보여주지만, 개별 조직의 데이터 계보·승인·비밀 관리 정책이 자동으로 완성된다는 뜻은 아니다. [SRC-007]

[설계 해석] 재현성은 “한 번 더 실행된다”보다 강한 조건이다. 같은 실행 정의가 같은 결과를 보장하기 어려운 경우에도, 결과 차이가 데이터 변경, 코드 변경, 이미지 변경, 자원 조건, 외부 모델 버전 중 무엇에서 왔는지 좁힐 수 있어야 한다. 이를 위해 파이프라인 입력을 암묵적 기본값으로 숨기지 않고, 검증된 기본값의 버전과 실행마다 달라지는 값을 구분한다.

파이프라인 경계 입력 계약 출력 계약 검토 포인트
전처리 원천 범위·필터·권한 데이터 참조·품질 보고 학습 데이터 누락·누수
학습 코드·이미지·파라미터·GPU 조건 아티팩트·로그·자원 기록 중단 후 재시작 가능성
평가 모델 ID·평가 세트·임계값 판정·오류 표본·승인 요청 비교 기준의 변경 이력
배포 승인 모델·서빙 구성·트래픽 범위 엔드포인트 버전·실행 ID 이전 버전으로의 복귀

[실무 제안] 파이프라인 실패를 하나의 “실패”로만 보지 않는다. 입력 검증 실패, 인프라 부족, 외부 의존성 오류, 모델 품질 미달, 승인 대기, 배포 중단은 서로 다른 처리와 재시도 권한을 가진다. 실패 유형별로 자동 재시도할 범위와 사람에게 넘길 범위를 정해 두면, 재실행이 데이터 중복이나 불필요한 GPU 소비를 만들지 않도록 할 수 있다.

RAG·Triton의 위치

[공식 발표] AI EasyMaker 릴리스 노트와 개요는 RAG 관련 기능과 NVIDIA Triton Inference Server 관련 항목을 안내한다. RAG는 문서를 벡터화하고 검색 결과를 LLM 응답 생성에 연결하는 흐름이며, Triton은 모델 서빙 계층을 다루는 기술이다. 두 항목은 수명주기에 놓이는 위치가 다르므로, 모두를 “모델 배포”라는 한 칸에 넣으면 데이터 갱신과 추론 실행의 책임이 흐려진다. [SRC-007, SRC-008]

[설계 해석] RAG의 변경 단위에는 문서 원본의 권한·보존 조건, 청크 규칙, 임베딩 모델, 인덱스 버전, 검색 파라미터, 프롬프트 템플릿이 함께 들어간다. 반면 서빙 변경 단위에는 모델 아티팩트, 런타임 이미지, 배치·동시성 설정, 자원 제한, 엔드포인트 라우팅이 들어간다. 같은 요청 경로에서 만날 수는 있어도, 되돌려야 할 원인과 승인자는 다를 수 있다.

변경 대상 대표 식별자 평가의 초점 롤백 단위
RAG 지식 문서 집합·인덱스·임베딩 버전 검색 적합성·권한 누출·최신성 이전 인덱스 또는 문서 집합
생성 모델 모델 아티팩트·프롬프트 버전 품질·안전성·지연 이전 승인 모델·프롬프트
Triton 서빙 런타임 이미지·서빙 구성 요청 처리·자원·오류 이전 이미지·구성
엔드포인트 트래픽 규칙·도메인 전환 사용자 영향·오류 분포 이전 라우팅 상태

[실무 제안] RAG의 문서 갱신을 모델 재학습과 같은 승인 흐름으로 취급할지, 별도 데이터 변경으로 취급할지는 업무 위험도에 따라 정한다. 중요한 것은 어느 선택이든 사용자가 받은 답변을 당시의 문서·인덱스·모델·프롬프트 조합으로 설명할 수 있다는 점이다. 공개 문서가 제공 여부를 확인하지 않은 세부 계보 화면이나 자동 품질 판정을 이 체계의 전제로 두지 않는다.

롤백과 계보

[설계 해석] 롤백은 이전 모델 파일을 다시 배포하는 단일 버튼이 아니다. 입력 계약, 서빙 이미지, 트래픽 라우팅, RAG 인덱스, 권한 정책, 관측 대시보드가 새 버전과 함께 바뀌었을 수 있다. 따라서 롤백 계획은 “어디로 돌아가는가”뿐 아니라 “어떤 조합을 고정해 두었는가”를 명시해야 한다. 불변 모델 ID만 남기고 다른 구성 요소가 바뀌면 이전 품질이 재현되지 않을 수 있다.

[실무 제안] 계보 레코드를 다음 두 방향으로 조회할 수 있게 설계한다. 정방향은 특정 데이터·코드 변경이 어떤 모델·엔드포인트·업무 결과로 이어졌는지 찾는 경로다. 역방향은 특정 사용자 영향 사건이 어떤 엔드포인트·모델·평가·데이터 참조에서 왔는지 찾는 경로다. 이 원칙은 특정 AI EasyMaker 화면이나 저장 방식의 주장이 아니라, 운영 인수에 필요한 증거 모델이다.

사건 즉시 확보할 식별자 복구 전에 확인할 것 사후 검토
품질 저하 요청 범위·모델·프롬프트·인덱스 이전 승인 조합과 차이 평가 세트의 공백
지연 급증 엔드포인트·서빙 구성·GPU 할당 트래픽 변화·자원 포화 용량·배치 정책

설계 리뷰

  • [공식 발표] AI EasyMaker의 공개 기능과, 조직이 별도로 마련해야 할 계보·승인·드리프트·보존 규칙을 구분했는가. [SRC-003, SRC-007, SRC-008]
  • [설계 해석] 코드·이미지·데이터 참조·파라미터·자원 조건·평가 결과가 모델과 양방향으로 연결되는가.
  • [설계 해석] 테스트·제한 배포·확대·안정 운영의 전환 조건에 모델 ID와 되돌릴 조합이 포함되는가.
  • [공식 발표] RAG, Triton, 파이프라인을 모두 같은 변경 단위로 취급하지 않고 공개된 기능 범위 안에서 역할을 나눴는가. [SRC-007, SRC-008]

  • [공식 발표] AI EasyMaker는 Notebook, CPU/GPU 학습, 최대 10노드 분산 학습, 모델·엔드포인트 관리 등 공개 기능을 안내한다. [SRC-007]

9장 관측·신뢰성·에너지·비용

GPU 인프라의 장애는 한 계층에서 시작해 다른 계층의 실패로 보일 수 있다. 관측의 목표는 모든 수치를 한 대시보드에 모으는 일이 아니라, 시설·클러스터·큐·모델·업무 신호의 단위와 책임을 보존한 채 하나의 사건을 따라가는 데 있다.

관측 계층

[원자료] Kubernetes 관측성 문서는 metrics, logs, traces를 서로 보완하는 기본 신호로 설명한다. OpenTelemetry 의미 규약은 trace·metric·log의 공통 의미와 속성 이름을 맞추는 기준을 제공한다. 이 두 자료는 신호를 수집하는 일반 원칙이지, FactoryX가 어떤 관측 저장소·대시보드·보존 기간을 사용한다는 증거는 아니다. [SRC-029, SRC-033]

[설계 해석] 시설은 전력·냉각·누수를, 클러스터는 노드·GPU·네트워크·스토리지를, 제어면은 요청·큐·할당·회수를, 모델은 요청 처리·품질을, 업무는 실제 완료를 다룬다. 계층마다 시간 해상도와 보존 규칙이 다르므로 동일 평균값으로 합치지 않는다.

계층 먼저 묻는 질문 대표 신호의 예 상위 계층으로 넘길 연결 키
시설 전력·열·냉각 조건이 안전 범위인가 전력 상태·냉각 경보·누수 사건 시간 창·시설·랙 식별자
클러스터 노드와 GPU·패브릭이 요청을 처리 가능한가 장치 건강·자원 사용·네트워크 오류 노드·장치·작업 식별자
제어면 요청은 왜 대기·거절·회수됐는가 큐 시간·할당 실패·정책 결정 요청·할당·정책 버전
모델 모델 응답은 기술 목표를 지키는가 지연·오류·처리량·평가 표본 모델·프롬프트·엔드포인트 버전
업무 사용자가 일을 마쳤는가 완료·재작업·승인 실패 업무 사건·권한·사용자 범주

[실무 제안] 연결 키를 원문 프롬프트·도구 인수의 무분별한 복제로 만들지 않는다. GenAI 의미 규약의 버전·민감 정보 처리를 확인하고, 조사 가능성·정보 보호·보존 비용을 함께 결정한다. [SRC-033]

GPU·패브릭·큐 SLI

[원자료] NVIDIA DCGM Exporter는 DCGM 텔레메트리를 Prometheus 형식으로 노출하는 일반적인 수집 경로이며 GPU 또는 GPU 인스턴스 단위의 지표와 Kubernetes Pod 메타데이터 라벨 연결을 지원한다. Kubernetes 기본 Resource Metrics API가 GPU 사용률·전력·MIG 프로파일·작업별 비용을 자동으로 제공하는 것은 아니므로, GPU 관측의 수집 경로와 의미를 별도로 검증해야 한다. 이는 FactoryX의 실제 수집 항목이나 보존 정책을 뜻하지 않는다. [SRC-028, SRC-029]

[설계 해석] GPU SLI는 할당까지의 시간, 장치 건강, 메모리 압박, 재시작, 노드·rail 편중을 분리한다. 패브릭은 이론 대역폭이 아닌 완료 조건의 영향을, 큐는 평균뿐 아니라 우선순위·팀·요청 크기별 분포와 거절 사유를 본다.

SLI 묶음 정의할 관찰 단위 이상 시 먼저 구분할 원인 단독 사용이 위험한 이유
GPU 할당 요청별 승인·할당·해제 시각 쿼터·장치 조건·노드 부족 할당률은 대기 경험을 숨길 수 있음
GPU 실행 작업·장치·프로파일별 실행 창 장치 건강·메모리 압박·재시작 사용률은 모델 품질을 말하지 않음
패브릭 작업군·노드군·시간 창 통신 경로·혼잡·NIC 오류 평균 처리량은 꼬리 지연을 가릴 수 있음
큐 요청 크기·우선순위·테넌트별 대기 정책·대여·회수·예약 평균 대기는 긴급 요청의 실패를 가릴 수 있음
스토리지 데이터·체크포인트 작업별 시간 데이터 경로·용량·재시도 읽기 성공은 학습 완료를 보장하지 않음

[실무 제안] SLI에는 관찰 대상과 제외 대상을 함께 쓴다. 예를 들어 “큐 대기 시간”은 제출부터 입장 허가까지인지, 장치 할당까지인지, 컨테이너 시작까지인지가 달라질 수 있다. 정의가 변했을 때는 이전 추세와 같은 그래프로 연결하지 않는다. SLO를 정할 때도 GPU 시간의 절감만 목표로 삼지 말고, 최장 대기·중단 후 복구·업무 마감에 미치는 영향을 함께 가드레일로 둔다.

모델·업무 SLI

[원자료] OpenTelemetry 의미 규약은 trace·metric·log를 연결할 공통 이름과 맥락을 제공한다. 규약만으로 모델의 사실성·안전성·사용자 만족도가 측정되지는 않으므로, 모델·업무 SLI는 평가 데이터와 사람의 검토를 포함해 별도 정의한다. [SRC-033]

[설계 해석] 모델 SLI는 요청 처리·오류·정의된 품질 검사를, 업무 SLI는 실제 완료·재작업·승인 실패를 본다. 응답이 빨라도 재작업이 반복되면 업무 품질은 좋아졌다고 말할 수 없다.

계층 SLI의 예 반드시 함께 기록할 맥락 잘못된 해석 방지
요청 처리 지연 분포·오류 비율·취소 모델·엔드포인트·입력 범주 평균 지연만으로 사용자 경험 판단 금지
모델 품질 사전 정의한 평가 통과·오류 유형 평가 세트·임계값·판정 버전 한 점수로 위험 범위 일반화 금지
검색·RAG 검색 성공·권한 오류·문서 버전 인덱스·청크·권한 정책 모델 오류와 지식 오류 혼동 금지
업무 결과 완료·재작업·승인 실패 업무 흐름·사용자 역할·변경 시각 모델 응답 수를 완료 수로 대체 금지

[실무 제안] 업무 SLI를 수집할 때는 “성공”의 정의를 제품 팀·현업·감사 담당자가 함께 합의한다. 자동 처리 건수는 처리량일 수 있으나, 재작업·보류·사람의 승인 절차를 제외하면 실제 완료와 다르다. 고위험 업무는 모델 응답의 내용 대신 승인 이벤트와 결과 코드 중심으로 기록하고, 원문 보존이 필요할 때는 접근 통제·마스킹·보존 만료를 별도 설계한다.

장애 대응

[설계 해석] 사고 대응에는 자동 완화·사람 승인·새 요청 차단·기존 작업 보호의 기준이 미리 필요하다. 냉각·전력·노드·큐·모델·업무 사건은 서로 다른 조치 권한을 가지며, 한 대시보드가 이를 하나의 책임으로 만들지는 않는다.

사건 신호 초기 조치의 목적 확인할 연결 증거 복구 완료의 판단
시설 경보 인명·장비 위험을 낮추고 영향 범위 격리 시간 창·시설·랙·전력·냉각 사건 안정 조건과 장비 상태가 확인됨
GPU·노드 이상 새 배치를 피하고 실행 중 작업 보호 장치 건강·작업·체크포인트 재배치 또는 정상 종료가 검증됨
큐 급증 사용자가 기다리는 이유를 설명 요청 크기·정책·쿼터·할당 실패 대기 원인과 우선순위가 해소됨
모델 오류 증가 노출 범위 축소와 안전한 복귀 모델·프롬프트·인덱스·배포 ID 이전 승인 조합의 결과가 확인됨
업무 실패 잘못된 행동의 확산 중지 업무 사건·권한·승인·도구 실행 영향 건의 보정과 재발 방지가 확인됨

[실무 제안] 런북에는 초기 신호, 수정 권한, 자동 조치 중단 조건, 통지 기준, 복귀 절차를 기록한다. 사후 검토는 경보의 맥락·관측 키 단절·회수와 재시도의 추가 비용을 본다.

에너지와 비용

[공식 발표] NHN은 수랭식 적용 후 GPU 연간 장애율이 기존 공랭식 대비 약 3배 낮아졌고 평균 무고장 시간이 약 2.6배 향상됐다고 발표했다. 이 값은 NHN의 공식 발표이며, 표본·기간·장애 정의·측정 방법이 공개되지 않았으므로 독립 비교값이나 다른 시설의 예상치로 일반화할 수 없다. [SRC-003]

CHT-004는 두 발표를 같은 축으로 그리지 않는다. 장애율은 공랭 100·수랭 약 33.3, 평균 무고장 시간은 공랭 100·수랭 260의 별도 지수다. 패널 간 막대 길이를 비교하거나 실제 장애 건수·PUE·절감액을 계산해서는 안 된다. [공식 발표] SRC-003; [CLM-007, CLM-008]

[원자료] ASHRAE의 AI 데이터센터 통합 설계 원칙과 미국 에너지부의 데이터센터 설계 가이드는 전력과 냉각을 별개 조달 항목이 아니라 함께 설계할 운영 조건으로 다룬다. 이 일반 원칙을 FactoryX의 실제 PUE, 랙별 전력, 냉각수 운영값으로 바꾸어 말해서는 안 된다. [SRC-019, SRC-021]

[설계 해석] 비용 모델에는 예약·실행·대기·재시도·중단, 전력·냉각, 스토리지·네트워크·관측, 운영자 개입과 재작업을 구분해 넣는다. 금액을 만들기 전에도 GPU 시간 밖 비용과 미공개 항목을 명시한다.

비용 또는 에너지 결정 함께 두어야 할 가드레일 나쁜 최적화의 징후 검토 주기
GPU 활용률 상승 큐 대기·완료 시간·중단 후 복구 사용률은 높지만 긴급 업무가 대기 정책 변경 전후
저전력 운전 열 여유·지연·오류·작업 마감 전력은 줄었지만 SLO가 악화 시설·작업 시간 창별
대여 자원 확대 보장 쿼터·공정성·회수 비용 유휴는 줄었지만 기아가 증가 쿼터 기간별
비용 귀속 요청·할당·실행·재시도 구분 중단·재작업 비용이 사라짐 월 단위와 사건 후

최적화의 가드레일

[설계 해석] 최적화에는 항상 목적 함수와 금지선을 함께 둔다. 예를 들어 GPU 활용률을 높이는 정책은 큐 대기와 마감 지연을, 에너지 절감 정책은 열 여유와 오류·성능을, 비용 절감 정책은 품질과 재작업·운영자 부담을 함께 감시해야 한다. 한 지표가 좋아졌다는 결과만으로 운영이 좋아졌다고 결론내리면, 비용을 다른 팀이나 다음 달로 이동시킨 효과를 놓칠 수 있다.

[실무 제안] 가드레일은 숫자 하나의 임계값보다 우선순위 있는 행동 규칙으로 작성한다. “전력 제한을 낮춘다”가 아니라 “낮춘 뒤 특정 업무의 완료 조건이 악화되면 원래 정책으로 복귀하고, 시설 상태가 안정될 때 다시 제한된 범위에서 시험한다”처럼 되돌릴 조건을 포함한다. 정책 실험에는 대상 풀, 시작·종료 시각, 가설, 관찰 SLI, 중단 기준, 책임자를 기록해 같은 조치를 나중에 해석할 수 있게 한다.

최적화 실험 가설 최소 관측 묶음 즉시 중단할 조건
큐 정책 조정 대기 분포를 더 균등하게 만든다 요청별 대기·거절·완료·재시도 특정 우선순위의 지속 기아

10장 프라이빗 AI의 데이터·보안·거버넌스

프라이빗 AI는 모델을 사내에 둔다는 한 문장으로 결정되지 않는다. 업무 요청이 어디서 들어오고, 어떤 데이터가 모델의 문맥이 되며, 누가 어떤 도구를 통해 실제 변경을 일으키는지, 그리고 그 결정을 나중에 재구성할 수 있는지가 함께 정해져야 한다. 이 장은 특정 제품의 내부 구성을 설명하지 않는다. 공개 자료로 확인할 수 있는 범위와 업계 검증 기준을 분리한 뒤, 조직이 스스로 계약해야 할 통제 경계를 제시한다.

프라이빗의 네 가지 경계

첫째는 데이터 경계다. 입력 문서, 대화, 검색 색인, 모델에 보낸 프롬프트, 도구 결과, 메모리는 같은 민감도를 갖지 않는다. 문서 접근권이 있다고 해서 원문 전체를 프롬프트와 로그에 복제할 권한까지 생기는 것은 아니다. 둘째는 테넌트와 권한 경계다. 조직·부서·사용자·서비스 계정·도구가 서로 다른 주체임을 명시하지 않으면, 편의를 위한 공용 자격증명이 곧 우회 통로가 된다. 셋째는 모델·도구 공급망 경계다. 모델 파일, 임베딩 모델, 컨테이너 이미지, 라이브러리, 프롬프트 템플릿, 커넥터 정의 모두가 실행 결과를 바꾼다. 넷째는 증거 경계다. 무엇을 했는지만 남기는 것이 아니라 누가 어떤 정책 버전으로 허용·거부·승인했는지와 결과 상태를 이어야 한다.

[설계 해석] 네 경계는 서로 대체되지 않는다. 저장 위치를 국내 리전으로 제한해도 고권한 도구가 모든 사용자를 대신해 실행하면 권한 경계는 무너진다. 반대로 세밀한 권한을 두더라도 검색 문서에 섞인 지시가 신뢰된 시스템 정책처럼 처리되면 데이터 경계가 무너진다. 따라서 “프라이빗”을 배포 위치의 동의어로 사용하지 말고, 각 경계의 계약과 검증 증거를 요구사항으로 써야 한다.

경계 먼저 정할 계약 실패 신호 검증 증거
데이터 등급, 사용 목적, 보존 기간, 학습 재사용 여부 원문이 불필요한 프롬프트·로그에 남음 데이터 흐름도, 샘플 로그, 삭제 시험
테넌트·권한 주체, 범위, 위임, 재인가 시점 공용 고권한 계정으로 실행 권한 매트릭스, 접근 거부 시험
모델·도구 공급망 허용 버전, 출처, 변경 승인, 취약점 대응 미검증 이미지·커넥터가 운영 투입 SBOM, 서명·검토 기록, 회귀 결과
증거·감사 기록 항목, 마스킹, 보존·열람·폐기 결과만 있고 정책 판단이 없음 trace, 승인 기록, 복구 연습 결과

[원자료] NIST AI RMF는 AI 위험관리를 Govern, Map, Measure, Manage의 네 기능으로 설명한다. 이는 자발적 위험관리 프레임워크이며, 특정 배포 형태나 제품 인증을 뜻하지 않는다 (SRC-030). [원자료] 생성형 AI 프로필은 모델 출력만이 아니라 인간의 과신, 정보 무결성, 가치사슬 통합 같은 운영 맥락을 함께 다룬다 (SRC-031). 이 두 자료는 위 네 경계를 제품 기능 목록이 아니라 조직의 책임 분해로 읽게 한다.

데이터와 테넌트

데이터 설계의 시작은 “사내 데이터”라는 넓은 표현을 더 이상 쓰지 않는 것이다. 계약서, 고객 문의, 생산 지시, 소스 코드, 인사 정보는 접근 근거와 보존 규칙이 다르다. 검색 결과가 문맥에 들어오는 순간 원문에는 없던 결합 위험도 생긴다. 한 문서씩 합법적으로 읽을 수 있더라도, 여러 문서를 한 응답에서 결합하면 권한 없는 추론이나 재식별이 발생할 수 있다. [실무 제안] 데이터 카탈로그에는 분류뿐 아니라 허용된 작업을 적는다. 예를 들어 “검색 가능, 요약 가능, 외부 전송 불가, 장기 메모리 저장 불가”처럼 결과 행동까지 명시한다.

테넌트 격리는 논리적인 구분과 실행 시점의 재인가를 함께 요구한다. 사용자 화면의 조직 선택값만으로는 충분하지 않다. 검색 인덱스 조회, 파일 다운로드, 데이터베이스 질의, 외부 SaaS 호출 각각에서 대상 테넌트와 사용자 범위를 다시 확인해야 한다. [실무 제안] 도구 호출에는 actor, tenant, purpose, resource, scope, expiry를 구조화해 넘기고, 다운스트림 서비스가 그 값을 독립적으로 검사하게 한다. 모델이 만든 자연어 설명은 권한 판정의 입력일 수 있지만 판정 그 자체가 되어서는 안 된다.

데이터 상태 문맥 투입 로그 기록 장기 메모리 기본 처리
공개·저위험 업무 목적 안에서 허용 식별자와 요약 우선 소유자 승인 시 출처를 붙여 사용
내부 일반 역할·목적 확인 후 해시 또는 마스킹 별도 검토 후 최소 조각만 검색
민감·규제 대상 업무별 명시 허가 후 원문 기본 금지 기본 금지 격리 경로와 추가 승인
도구 결과·외부 입력 신뢰되지 않은 콘텐츠 구조화된 결과와 오류 코드 기본 금지 지시가 아닌 데이터로 처리

[설계 해석] 표의 분류는 보편 법규 표가 아니라 운영 계약의 출발점이다. 실제 분류 체계는 산업 규제, 국가, 단체협약, 고객 계약에 맞춰 법무·보안·업무 책임자가 확정해야 한다. 이때 “모델 제공자가 학습에 재사용하지 않는다” 같은 약속은 출시 문서, 계약 조건, 보존 설정, 삭제 검증으로 각각 확인한다. 설정 화면 한 장이나 영업 설명만으로 증명할 수 없다.

모델·도구 공급망

모델 이름만 고정해도 동일한 응답이 보장되는 것은 아니다. 시스템 지침, 검색 인덱스, 임베딩 모델, 재순위기, 도구 스키마, 실행 컨테이너, 정책 파일 중 하나가 바뀌면 행동이 바뀔 수 있다. [원자료] NIST 생성형 AI 프로필은 생성형 AI 위험을 시스템 생명주기와 가치사슬 관점에서 다룬다 (SRC-031). 그러므로 모델 교체뿐 아니라 프롬프트·도구 정의·지식원 변경도 릴리스 대상으로 취급하는 편이 합리적이다.

[원자료] OWASP의 Excessive Agency 지침은 과도한 기능, 권한, 자율성이 함께 위험을 키우며 최소 권한, 사용자 승인, 다운스트림의 완전한 재검증을 권고한다 (SRC-032). 이 지침은 특정 서비스의 취약점 진단 결과가 아니다. [설계 해석] 도구를 “업무 자동화”라는 큰 단위로 제공하는 대신, 조회·초안·제출·삭제·권한 변경을 별도 도구와 별도 범위로 잘게 분리해야 한다. 하나의 도구가 검색, 파일 삭제, 외부 전송을 모두 수행할수록 승인 화면도 실행 기록도 모호해진다.

공급망 항목 변경 때 묻는 질문 최소 증거 되돌리기 수단
모델·임베딩 버전·사용 조건·평가 결과가 바뀌었는가 승인된 버전 목록과 평가 리포트 이전 승인 버전으로 라우팅
프롬프트·정책 허용 행동과 거부 조건이 달라졌는가 diff, 담당자 검토, 공격 시험 정책 버전 고정·즉시 비활성화
도구·커넥터 입력·출력 스키마와 권한이 확대됐는가 스키마, scope, timeout, idempotency 도구 차단·토큰 폐기
이미지·의존성 실행 환경에 새 코드가 들어왔는가 SBOM, 서명, 취약점 검토 이미지 pin과 이전 배포본

[실무 제안] 변경 요청에는 사용자 가치와 함께 실패 영향, 데이터 등급, 권한 변화, 평가 케이스, 중단·복구 방법을 한 장으로 붙인다. “프롬프트만 바꿨다”는 예외 사유가 될 수 없다. 특히 이전에는 읽기만 하던 에이전트가 쓰기 도구를 받는 변경은 모델 품질 개선이 아니라 권한 확대다. 업무 책임자와 보안 책임자의 승인 조건을 분리하는 편이 좋다.

NIST AI RMF

[원자료] NIST AI RMF 1.0의 Govern·Map·Measure·Manage는 한 번의 심사 순서가 아니라 서로 반복되는 위험관리 기능이다 (SRC-030). 프라이빗 AI에서는 이를 별도 거버넌스 문서로 보관하기보다, 업무 정의·변경·운영 기록에 연결해야 한다. 예컨대 성능이 좋아져도 승인 없는 외부 전송이 한 번 발생했다면 Manage의 판단은 출시 확대가 아니라 통제 재설계가 될 수 있다.

AI RMF 기능 프라이빗 AI에 던질 질문 남길 산출물 운영 연결점
Govern 누가 위험을 수용·중단할 권한을 갖는가 책임자, 예외·승인 정책, 교육 기록 변경 승인과 사고 지휘
Map 어떤 사용자·데이터·도구·피해가 연결되는가 시스템 카드, 데이터 흐름, 위협 모델 업무 범위와 위험 등급
Measure 정확성 외에 무엇을 반복 측정하는가 평가 세트, 거부·우회 시험, 기준선 배포 전 게이트와 드리프트 감시
Manage 잔여 위험을 어떻게 줄이거나 수용하는가 출시 결정, 완화 계획, 재평가 일정 롤백, 기능 축소, 사고 후 조치

[실무 제안] Map 단계에서 가장 먼저 고위험 행동 목록을 만든다. 금전 이동, 대외 발송, 권한 부여, 삭제, 운영 배포는 잘못된 결과가 곧 외부 효과가 되는 행동이다. 각 행동에 대해 자동 실행 가능 여부, 필요한 사람 승인, 실행 전 재인가, 사후 보상 동작, 최대 피해 범위를 합의한다. 이 목록이 없으면 평가가 문장 유창성이나 데모 성공률에 머물기 쉽다.

[설계 해석] Measure는 단일 정답률보다 다면적이어야 한다. 정상 요청 성공률, 정책 위반 시도 차단률, 도구 인자 정확도, 재시도·중단률, 사람 개입률, 실행 후 복구 성공률은 서로 다른 실패를 드러낸다. 목표 숫자는 업계 평균을 복사하지 않고, 업무의 되돌릴 수 없음과 사용자 수, 데이터 등급을 근거로 정한다. 공개된 제품 자료가 없다면 특정 제품이 이 측정 체계를 내장한다고 말할 수 없다.

평가와 거버넌스

평가 데이터는 실제 업무를 비식별화·분할한 세트와 공격·실패 세트를 함께 가져야 한다. 정상 요청만 통과하는 평가는 실제 운영의 경계 조건을 보여 주지 않는다. [원자료] NIST 생성형 AI 프로필은 정보 무결성과 인간-AI 상호작용 위험을 함께 다룬다 (SRC-031). [원자료] OWASP의 해당 지침은 외부 콘텐츠가 모델의 행동을 조작할 수 있는 상황에서 최소 권한과 사용자 확인을 강조한다 (SRC-032). 따라서 검색 문서에 “이 지시를 따르라”는 내용이 포함된 경우, 권한 밖 데이터 요청, 도구 응답이 늦거나 부분 실패하는 경우를 평가에 넣어야 한다.

평가 층 확인할 실패 예시 판정 출시 전 기준의 성격
업무 결과 틀린 완료·누락·잘못된 상태 변경 최종 상태와 근거 확인 업무 책임자가 정함
정책 준수 권한 초과·승인 우회·금지 데이터 노출 허용·거부·승인 요구가 맞는지 고위험은 보수적으로
도구 실행 잘못된 인자·중복 호출·시간 초과 스키마·idempotency·재시도 시스템별 계약
운영 회복성 중단 뒤 고아 작업·복구 실패 롤백·보상·수동 전환 복구 시간과 증거 포함

[실무 제안] 평가 결과를 평균 하나로 보고하지 않는다. 모델·프롬프트·도구·정책 버전, 데이터셋 버전, 실행 환경, 담당 검토자, 실패 사례의 재현 절차를 함께 기록한다. 제품 또는 모델을 바꾼 뒤 기준선을 다시 수집하지 않으면 “개선”이라는 말의 기준이 사라진다. 거버넌스 회의는 지표를 승인하는 자리가 아니라, 어느 위험을 누구의 권한으로 수용·완화·중단했는지 결정하는 자리여야 한다.

감사와 보존

감사는 원문을 많이 모으는 일과 다르다. 필요한 것은 원인을 재구성할 수 있는 최소 증거다. 요청 식별자, 사용자·서비스 주체, 정책과 프롬프트 버전, 검색된 자료의 식별자와 등급, 도구명과 인자 해시, 승인자와 유효 기간, 다운스트림 결과, 변경 전후 상태, 복구 작업 식별자를 이어야 한다. [실무 제안] 원문 프롬프트와 도구 인자를 기본 수집 대상으로 두지 말고, 민감도에 따라 마스킹·해시·제한 보존을 기본값으로 삼는다. 상세 원문 열람은 사고 조사 같은 예외 절차로 좁힌다.

[원자료] NIST AI RMF는 위험관리 활동을 문서화하고 측정·관리하는 반복 구조를 제시한다 (SRC-030). [설계 해석] 그래서 감사 로그는 보안팀만의 산출물이 아니라 운영자가 “무엇을 멈추고 어디로 되돌릴지”를 판단하는 입력이다. 로그가 빠른 분석을 막을 만큼 민감하거나, 반대로 결과만 남아 결정을 연결할 수 없다면 둘 다 운영 실패다.

보존 대상 최소 연결 키 보존 시 주의 사용 장면
실행 trace request·conversation·trace ID 원문 문맥은 기본 마스킹 장애 재현
정책·승인 policy version·approver·expiry 승인 범위와 실제 실행을 분리 기록 책임 확인
도구 효과 tool call·대상·전후 상태 비밀값 대신 참조·해시 사용 중복·오작동 복구
평가·배포 모델·프롬프트·데이터셋 버전 평가 데이터의 재식별 방지 회귀 판단

설계 리뷰

이 장의 설계 결론은 간단하다. 프라이빗 AI의 신뢰성은 모델을 어디에 두는가보다 데이터, 주체, 공급망, 증거의 경계를 얼마나 검증 가능하게 연결하는가에 달려 있다. NIST와 OWASP는 이 연결을 검토할 업계 기준을 제공한다. 그러나 그 기준을 인용했다고 해서 어떤 제품이 자동으로 준수하거나 기능을 제공하는 것은 아니다 (SRC-030, SRC-032).

[실무 제안] 도입 심사에서는 다음 세 질문으로 설계를 압축한다. 첫째, 이 요청이 어떤 데이터와 어떤 권한으로 어떤 효과를 낼 수 있는가. 둘째, 거부·승인·실행 중 어느 결정을 누가 재현할 수 있는가. 셋째, 잘못된 효과가 나면 어느 범위까지 되돌릴 수 있는가. 세 질문에 문서·테스트·운영 기록으로 답하지 못하면 자동화 범위를 줄여야 한다.

핵심 요약

  • [설계 해석] 프라이빗 AI는 배포 위치 하나가 아니라 데이터, 테넌트·권한, 공급망, 감사의 네 경계를 묶는 운영 계약이다.
  • [원자료] NIST AI RMF의 Govern·Map·Measure·Manage는 제품 인증이 아닌 지속적 위험관리의 기준점이다 (SRC-030).
  • [원자료] 생성형 AI 위험과 과도한 에이전트 권한은 출력 품질만이 아니라 정보 무결성, 사람의 판단, 도구 권한을 함께 보게 한다 (SRC-031, SRC-032).
  • [실무 제안] 모델·프롬프트·도구·정책·커넥터를 모두 변경관리와 회귀 평가의 대상으로 다룬다.
  • [실무 제안] 감사는 원문 수집 경쟁이 아니라 정책 판단, 실행 효과, 복구 가능성을 연결하는 최소 증거 설계다.

11장 엔터프라이즈 에이전트 실행 환경

에이전트는 모델의 답변과 실제 업무 실행이 만나는 지점이다. 좋은 데모와 안전한 운영은 다른 질문을 요구한다. 이 장은 ProjectX를 완성된 런타임으로 가정하지 않고, 공개 발표의 범위 밖을 제품 검증 질문으로 남긴다.

ProjectX의 공개 범위

[공식 발표] NHN은 2026-05-28 FactoryX를 공개하면서 Service 레이어에 ProjectX를 배치했다. 같은 발표는 비개발자가 자연어 기반으로 업무 맞춤형 에이전트를 설계하고 사내 시스템·데이터와 연동하는 방향을 설명했으며, 2026년 하반기 출시 예정이라고 밝혔다 (SRC-003). [공식 발표] FactoryX 공식 페이지도 ProjectX를 Service 레이어의 구성 요소로 소개한다 (SRC-001).

이 사실은 제품 방향과 발표 시점만 확인한다. 기준일 2026-08-12에 공개 자료만으로 출시 완료 여부, API, 배포·저장 조건, 테넌트 격리, RBAC, 승인·감사·평가·복구 상세는 확인할 수 없다. 모두 [미공개]이며, 아래 구조는 제품 내장 기능이 아닌 도입 검증 질문이다.

항목 2026-05-28 공개 범위 기준일 현재 판단
제품 위치 FactoryX Service 레이어에 ProjectX를 배치했다고 발표 [공식 발표] (SRC-001, SRC-003)
목표 방향 자연어 기반 업무 맞춤형 에이전트와 사내 연동 방향을 발표 [공식 발표] (SRC-003)
출시 일정 2026년 하반기 출시 예정이라고 발표 [공식 발표] (SRC-003)
현재 기능·운영 구성 API, 권한, 승인, 감사, 평가, 복구의 상세 [미공개]
배포·데이터 조건 SaaS·전용 테넌트·private cloud·온프레미스 여부와 보존 조건 [미공개]

[설계 해석] 기업용 에이전트 실행 환경이라는 표현은 문제 범위를 가리킬 뿐 세부 기능을 뜻하지 않는다. 권한 위임, 고위험 행동 승인, 실행 기록, 복구는 NIST·OWASP·OpenTelemetry에서 도출한 검증 질문이지 ProjectX 제공 기능의 증거가 아니다 (SRC-030, SRC-032, SRC-033).

컨텍스트는 신뢰 경계다

모든 문맥이 같은 명령은 아니다. 시스템 정책은 관리된 지시이고, 사용자 요청은 업무 의도지만 권한 확대의 근거가 아니다. 검색 문서, 전자우편, 티켓, 도구 응답, 메모리는 유용해도 신뢰된 정책으로 승격되어서는 안 된다.

[원자료] OWASP는 과도한 자율성의 위험에서 최소 기능·최소 권한과 사람 확인, 다운스트림 시스템의 재검증을 권고한다 (SRC-032). [설계 해석] 이 원칙은 프롬프트에 “문서를 믿지 말라”라고 쓰는 것으로 끝나지 않는다. 검색·도구 결과의 출처, 민감도, 테넌트, 수집 시점, 허용된 사용 목적을 구조화된 필드로 전달하고, 도구 호출의 권한 판정은 모델 출력 밖에서 이뤄져야 한다.

문맥 종류 신뢰 수준 모델에 주는 역할 실행 전 처리
시스템 정책 관리된 신뢰 입력 금지 행동·형식·상한 버전 고정, 변경 승인
사용자 요청 목적 입력 업무 목표와 범위 사용자 권한과 대상 확인
검색·문서 신뢰되지 않은 증거 근거 후보·요약 대상 출처·등급·테넌트 필터
도구 결과 신뢰되지 않은 상태 다음 판단의 자료 스키마·오류·대상 재검증
장기 메모리 조건부 신뢰 승인된 업무 상태 출처, TTL, 검토 상태 검사

[실무 제안] 메모리 쓰기는 조회보다 더 좁게 설계한다. 사용자 요청 속의 지시나 문서의 임의 문장을 장기 메모리로 저장하면, 일회성 오염이 다음 실행에도 남는다. 메모리 항목에는 작성 주체, 근거 출처, 만료 시점, 재검토 상태를 붙이고, 정책·권한·비밀값은 일반 대화 메모리와 분리한다. 이러한 제안은 ProjectX의 현 기능이 아니라 검증 가능한 에이전트 설계 원칙이다.

정책·승인·도구

모델은 행동 후보와 인자를 제안할 수 있지만 “할 수 있음”과 “해도 됨”은 다르다. 정책 계층은 주체, 범위, 데이터 등급, 위험 등급, 승인 필요 여부를 결정해야 한다. [원자료] OWASP는 다운스트림 재검증과 고위험 행동의 사용자 승인을 권고한다 (SRC-032). [설계 해석] 판정은 재현 가능한 규칙·권한 검사로 남기고 LLM이 직접 실행하지 못하게 한다.

행동 등급 예시 기본 처리 필요한 증거
읽기 권한 있는 문서 검색·요약 범위 확인 뒤 실행 사용자·테넌트·출처 로그
초안 보고서·메일·변경안 작성 자동 생성, 사용자 검토 초안 버전과 근거
제한적 쓰기 되돌릴 수 있는 내부 상태 변경 정책 허용과 조건부 승인 idempotency·전후 상태·롤백
고위험 효과 외부 발송, 삭제, 권한 변경, 배포 독립 승인 뒤 재인가 승인 범위·만료·실행 결과

[실무 제안] 승인 화면은 “계속할까요?”가 아니라 대상, 효과, 데이터 범위, 되돌리기 방법, 유효 기간을 보여야 한다. 승인한 사람이 다른 대상이나 다른 권한의 실행까지 승인한 것으로 해석되면 안 된다. 또한 승인 직후 대상 권한이 바뀌었을 수 있으므로 도구 게이트웨이는 실행 시점에 다시 인가한다. 이중 확인은 불편을 늘리기 위한 것이 아니라 승인 증거와 실제 효과를 같은 범위로 묶기 위한 것이다.

현재 ProjectX가 이 정책·승인·도구 경계를 어떤 방식으로 제공하는지는 [미공개]이다. “에이전트 설계”라는 발표 문구만으로 도구 allowlist, JSON schema 검증, delegated identity, rate limit, sandbox, approval expiry가 존재한다고 추정해서는 안 된다. 확인 전에는 쓰기 행동을 열지 않고 read-only 또는 초안 생성에 범위를 제한하는 것이 합리적이다.

평가와 관측

에이전트 평가는 답변 품질과 실행 안전성을 나눠 본다. 업무 결과에서는 최종 상태와 재작업을, 통제에서는 권한 거부, 승인 우회, 도구 인자, 중복·오류 처리를 본다. [원자료] NIST AI RMF는 Measure와 Manage를 반복 활동으로 설명한다 (SRC-030). [실무 제안] 정상·악성 문서·모호한 요청·부분 실패·반복 실행을 한 회귀 묶음으로 관리한다.

[원자료] OpenTelemetry Semantic Conventions는 trace·metric·log의 공통 의미 체계와 GenAI 속성의 버전 경계를 제시한다 (SRC-033). 이는 ProjectX의 OTel 지원 선언이 아니며 trace export 범위는 [미공개]이다. [설계 해석] 실행 관측은 agent/version, trace, 정책·승인·도구 결과를 연결하되 원문 지시·질의·인자는 기본 수집하지 않는다.

관측 층 남길 신호 목적 민감도 통제
업무 완료·중단·수동 전환·재작업 사용자 가치와 실패 유형 파악 업무 식별자 가명화
정책 allow·deny·approval과 규칙 버전 우회·오판·변경 영향 확인 이유 코드는 구조화
도구 이름·스키마 버전·대상·결과 코드 실행 오류·중복·시간 초과 분석 인자는 해시·마스킹
모델·검색 모델·프롬프트·retrieval 버전 회귀와 드리프트 추적 원문은 opt-in 열람

[실무 제안] 지표에는 거부율만 두지 말고 거부 후 사용자 성공률과 수동 전환 시간을 함께 둔다. 모든 요청을 막으면 정책 준수율은 좋아 보일 수 있지만 업무 가치가 사라진다. 반대로 성공률만 높이면 승인 없는 실행이나 숨은 권한 초과가 평균에 묻힌다. 위험 등급별로 서로 다른 기준선을 두고, 변경 전후에 동일 시험을 실행해야 한다.

감사와 복구

에이전트 실행은 여러 시스템의 상태를 바꾼다. timeout 뒤 실제 성공·중복·부분 변경을 확인해야 한다. [실무 제안] 쓰기 도구에는 idempotency key, deadline, 실행 상태와 보상 또는 수동 처리 큐를 둔다. 되돌릴 수 없는 행동은 자동화하지 않는다.

[원자료] GitHub Enterprise Audit Log 문서는 감사 활동 내보내기를 설명하지만, 저장소 감사 로그와 애플리케이션 실행 감사의 범위는 다르다 (SRC-037). [설계 해석] 코드·정책 변경의 PR 기록만으로 에이전트가 실제로 어떤 사용자 대신 어떤 도구를 실행했는지 알 수 없다. 반대로 실행 trace만으로 누가 위험한 정책 변경을 승인했는지도 알 수 없다. 두 증거 사슬은 공통 릴리스·정책·trace 식별자로 연결하되, 각각 독립 보존해야 한다.

실패 상황 즉시 행동 복구 증거 재발 방지 질문
도구 timeout 상태 조회 후 재시도 여부 결정 call ID, 대상 상태, deadline 중복 실행을 막았는가
부분 성공 보상 또는 수동 큐로 전환 전후 상태, 담당자, 보상 ID 원자성 가정이 틀렸는가
정책 우회 의심 도구·토큰·정책 경로 격리 deny 기록, 영향 범위, 조사 trace 재인가가 실제로 작동했는가
잘못된 문맥 주입 해당 run과 메모리 항목 격리 출처, 저장 이력, 재평가 결과 신뢰 경계가 구조화됐는가

ProjectX가 audit trail, idempotency, 보상 동작, 외부 로그 내보내기를 제공하는지는 [미공개]이다. 따라서 계약·POC에서는 “지원한다”는 답변보다 API·샘플 로그·오류 시연·데이터 삭제·복구 연습으로 확인 가능한 결과를 요청해야 한다.

도입 전 질문

질문은 운영 범위를 좁히는 도구다. 답이 없는 항목은 기능 부재의 판정도, 존재 근거도 아니다. 증거가 없으면 read-only 또는 초안 단계에 머문다.

확인 질문 필요한 증거 미확인 시 기본 결정
정식 출시일·현재 버전·변경 이력은 무엇인가 릴리스 노트, 지원 정책 [미공개]; 생산 쓰기 보류
데이터 위치·보존·학습 재사용 조건은 무엇인가 계약 조항, 설정, 삭제 시험 민감 데이터 제외
사용자·부서·에이전트·도구 권한을 분리하는가 권한 모델, deny 시연 공용 계정 사용 금지
문서·도구 결과를 신뢰되지 않은 입력으로 분리하는가 아키텍처 설명, 공격 시험 외부·검색 입력 제한
고위험 행동을 LLM 밖에서 승인·재인가하는가 정책·승인·실행 trace 쓰기 도구 비활성
trace·감사·복구를 내보낼 수 있는가 샘플 export, timeout·rollback 시연 제한 배포로 한정

[실무 제안] POC는 하나의 업무를 끝까지 검증해야 한다. 예를 들어 “문서를 읽어 답한다”는 데모에 그치지 말고, 사용자가 권한 없는 자료를 요청했을 때의 거부, 악성 지시가 포함된 문서의 처리, 승인 범위 밖 도구 호출의 차단, 실패 뒤 실행 상태 재구성을 같은 시나리오로 시험한다. 공개 발표의 방향이 좋아도 이러한 실행 증거 없이는 보안·감사 기능을 구매 조건으로 간주할 수 없다.

설계 리뷰

ProjectX에 대해 확인된 사실은 2026-05-28의 공개 위치·방향과 2026년 하반기 출시 예정 발표다 (SRC-001, SRC-003). 이 장의 구조는 발표의 빈칸을 채우지 않기 위한 검증 프레임이다. [미공개] 기능을 이미 제공되는 것처럼 쓰지 않는 것이 핵심 경계다.

[실무 제안] 운영 자동화는 모델이 아닌 효과의 위험도로 단계화한다. 문서 검색과 요약에서 출발해, 사용자 검토가 있는 초안, 되돌릴 수 있는 제한적 쓰기, 독립 승인이 있는 고위험 행동 순으로 올라간다. 어느 단계에서든 정책·관측·복구 증거가 부족하면 이전 단계로 후퇴할 수 있어야 한다.

핵심 요약

  • [공식 발표] ProjectX는 2026-05-28에 FactoryX Service 레이어의 방향으로 공개됐고 2026년 하반기 출시 예정으로 발표됐다 (SRC-001, SRC-003).
  • [미공개] 현재 출시 상태, API, 배포 형태, 권한·승인·감사·평가·복구의 상세는 공개 자료만으로 확인할 수 없다.
  • [원자료] NIST·OWASP·OpenTelemetry는 위험관리, 최소 권한·재검증, 관측 의미 체계의 업계 기준이며 ProjectX 내장 기능의 증거가 아니다 (SRC-030, SRC-032, SRC-033).
  • [설계 해석] 컨텍스트를 신뢰 수준별로 분리하고, 모델 제안과 실제 도구 실행 사이에 외부 정책·승인·재인가를 둬야 한다.
  • [실무 제안] 도입 증거는 기능 설명보다 권한 거부, 승인 범위, 오류 복구, trace 내보내기를 재현하는 시연으로 수집한다.

12장 도입 로드맵·변경 통제·운영 인수

AI 인프라와 에이전트 도입은 일정 관리이면서 되돌릴 수 없는 자동화의 범위를 조절하는 위험관리다. 이 장은 작은 업무에서 증거를 만들고 제한 배포를 거쳐 운영 책임을 넘기는 흐름을 제안한다. 특정 FactoryX 또는 ProjectX 기능을 전제로 하지 않는다.

문제 선택

첫 문제는 기술 시연용이 아니라 결과와 실패 비용을 설명할 수 있는 업무여야 한다. 입력·출력·담당자·기존 처리 시간이 보이고, 사람이 검토할 수 있는 검색·근거 있는 초안·반복 분류가 적합하다. 삭제, 대외 발송, 권한 변경, 설비 제어처럼 외부 효과가 큰 행동은 더 늦게 검토한다.

[공식 발표] NHN Cloud의 제조업 AX·DX 공개 요약은 109개사 조사에서 DX 초기·확장 단계 78.9%, DX 전용 예산 확보 45.2%, 하이브리드 클라우드 선호 49%를 제시한다 (SRC-009). 서로 다른 항목이므로 합계·인과관계·FactoryX 고객 성과로 일반화할 수 없다. [설계 해석] 실제 선정은 자사 업무·데이터·권한·복구 조건으로 한다.

선택 기준 확인 질문 제한 배포에 적합한 신호 뒤로 미룰 신호
업무 가치 누가 결과를 쓰고 기존 비용은 무엇인가 재작업·대기 시간을 관찰 가능 성공 정의가 데모 반응뿐
데이터 합법적으로 좁은 자료 묶음을 만들 수 있는가 등급·소유자·보존이 명확 민감 데이터의 출처 불명
권한 사람 검토가 실행을 가로막을 수 있는가 read-only·초안부터 시작 가능 공용 고권한 계정 필요
복구 잘못된 효과를 취소하거나 보상할 수 있는가 상태 확인·수동 전환 가능 피해 범위와 복구 주체 불명

[실무 제안] 후보 업무마다 사용자, 기준선, 기대 결과, 금지 행동, 데이터·도구, 수동 절차, 중단 권한을 적은 한 장의 정의서를 만든다. 목표는 관찰 가능한 문장으로 쓰며, 이 문서는 POC 범위와 확장 판단의 기준이 된다.

POC와 제한 배포

POC는 가장 작은 안전한 가설을 깨는 실험이다. 하나의 사용자 집단·업무 흐름·허용 데이터·읽기 또는 초안 행동·관찰 기간으로 좁힌다. 품질뿐 아니라 정책 거부, 사람 개입, 오류·지연·비용·근거 누락을 측정한다. [원자료] NIST AI RMF는 반복적 위험관리를 제시한다 (SRC-030). [설계 해석] 통과는 좋은 답변이 아니라 위험 상한 안의 반복 가능한 증거다.

단계 허용 범위 반드시 검증할 것 중단 조건
관찰 검색·요약·초안, 실제 효과 없음 출처·권한 필터, 사용자 재작업 민감 데이터 노출·근거 혼동
제한 배포 소수 사용자와 승인된 업무 정책 거부, latency, 오류 처리 승인 우회·설명 불가한 결과
조건부 쓰기 되돌릴 수 있는 내부 변경 재인가, idempotency, rollback 중복·부분 성공을 복구 못함
확장 검토 부서·연동 시스템 확대 drift, 지원 체계, 비용 배분 운영자 인수 조건 미충족

[실무 제안] 동일 요청을 반복 실행해 분산을 기록하고, 실험 중 모델·프롬프트·정책·도구 버전을 고정한다. 수동 개입은 별도 결과로 기록하며, 보정이 많다면 다음 단계 확대의 근거가 아니다.

증거 사슬

좋은 도입은 결정과 실행을 연결한다. 문제 정의에는 선택 이유, ADR에는 대안·위험, PR에는 변경·검토, CI에는 시험, 배포에는 환경 승인, trace에는 실제 정책·도구 결과가 남는다. 연결이 끊기면 변경 이유와 승인 범위를 답할 수 없다.

증거 답하는 질문 최소 연결 키 보존 책임
문제 정의·risk register 무엇을 자동화하고 왜 제한했는가 업무 ID·위험 등급 업무 책임자
ADR 어떤 대안과 트레이드오프를 택했는가 ADR ID·릴리스 설계 책임자
PR·리뷰·CI 무엇이 바뀌고 어떤 시험을 했는가 commit·PR·평가 버전 개발·보안 책임자
배포 승인 누가 어느 환경의 변경을 허용했는가 release·environment 배포 책임자
실행 trace·복구 실제 어떤 효과가 발생했는가 request·trace·tool call 운영 책임자

[원자료] GitHub Rulesets는 브랜치·태그·push에 규칙을 적용하고 여러 규칙이 함께 적용될 수 있는 구조를 설명한다 (SRC-034). [원자료] CODEOWNERS는 경로별 담당자에게 검토를 요청하고, 브랜치 보호 설정과 결합해 소유자 승인을 요구할 수 있다 (SRC-035). [원자료] Deployment Environments는 환경 보호 규칙과 승인 흐름을 지원한다 (SRC-036). 이들은 변경 통제를 구현할 수 있는 공식 GitHub 기능이지, FactoryX나 ProjectX가 GitHub를 내장하거나 이 흐름을 사용한다는 증거가 아니다.

Issue·ADR·PR·CI

[실무 제안] 프롬프트, 정책, 도구 스키마, 권한 매핑, 평가 데이터, 배포 매니페스트는 별도 경로·소유자로 관리한다. 변경에는 위험 등급·평가 결과를 붙이고, 고위험 권한 확대에는 업무·보안 검토를 모두 요구한다.

변경 대상 Issue·ADR에 적을 것 PR·CI 게이트 배포 전 확인
프롬프트·정책 허용·거부 행동과 영향 범위 소유자 리뷰, 공격·회귀 시험 이전 버전 복귀 가능성
도구 스키마·권한 대상·scope·쓰기 효과·보상 스키마 검증, 최소 권한 검토 승인·재인가 경로
모델·검색 지식 버전·데이터·품질 변화 기준선 비교, 민감도 점검 drift 관측과 중단 기준
인프라·배포 자원·네트워크·비밀값 변화 IaC 검토, 취약점·정책 검사 환경 승인과 rollback

[원자료] GitHub 감사 로그는 활동 내보내기를 설명하지만 저장소 이벤트가 애플리케이션 실행 전체를 대신하지는 않는다 (SRC-037). [설계 해석] CI는 코드 변경, trace는 실제 효과의 증거다. 보존 정책과 열람 통제를 분리하고 릴리스 식별자로 연결한다.

확장과 운영 인수

확장은 사용자 수가 아니라 실패 도메인과 책임 경계를 넓히는 일이다. 부서가 달라지면 데이터 보존 규칙, 큐 대기, 비용도 달라진다. [실무 제안] 새 업무·데이터·도구·권한 조합은 별도 변경으로 취급하고, 새 위험 모델과 평가 세트를 추가한다.

운영 인수의 완료 조건은 “운영팀에 넘겼다”가 아니다. 알람을 누가 받고, 비용 한도를 누가 조정하며, 정책 우회가 의심되면 누구에게 어떤 순서로 연락하고, 안전한 중단·복구를 어떻게 실행하는지가 문서와 연습으로 확인돼야 한다. 운영자에게 모델을 튜닝하는 법보다 먼저, 영향 범위 확인·도구 차단·권한 폐기·큐 전환·사용자 공지의 순서를 제공한다.

인수 항목 운영자가 받아야 할 것 연습으로 확인할 것
서비스 수준 업무·정책·도구 SLI, 알람 임계값, 담당자 지연·오류·거부율 급증 대응
변경 통제 소유자, 승인 경로, 긴급 우회 기준 정책·도구 권한의 긴급 롤백
사고 대응 격리·조사·공지·복구 runbook 잘못된 실행과 데이터 노출 가정
비용·용량 한도, 태그, 우선순위, 중단 기준 급격한 사용량과 대기열 증가
증거 보존 trace·승인·배포 기록의 위치와 열람권 사건을 처음부터 재구성

[실무 제안] 운영 인수 전에 ‘운영자 없이 데모를 되풀이하지 않는다’는 원칙을 둔다. 개발팀의 개인 지식으로만 해결되는 장애가 있다면 인수가 끝난 것이 아니다. 반대로 운영팀이 안전하게 기능을 끄고 이전 상태로 되돌릴 수 있다면, 새로운 기능을 배우는 동안에도 피해 범위를 제한할 수 있다.

30·60·90일 로드맵

아래 일정은 예시다. 규제·조달·데이터 정비에 따라 기간은 달라지며, 각 구간은 날짜가 아니라 산출물과 중단 가능성으로 평가한다.

기간 목표 핵심 산출물 다음 단계 진입 조건
0–30일 문제를 좁히고 read-only 기준선을 만든다 문제 정의, 데이터·권한 맵, risk register, 기준선 소유자·금지 행동·수동 절차 합의
31–60일 제한 사용자로 평가와 승인 흐름을 검증한다 평가 세트, PR·CI 기록, trace 샘플, 사고 연습 거부·승인·오류 복구를 재현
61–90일 조건부 확장과 운영 인수를 판단한다 SLO, runbook, 비용 기준, 인수 리허설 운영자가 중단·복구·감사를 수행

[원자료] NIST AI RMF는 위험을 통치·맥락화·측정·관리하는 반복 구조로 제시한다 (SRC-030). [설계 해석] 따라서 90일째에 자동으로 전사 확장하는 것이 아니라, 증거가 약하면 범위를 유지하거나 축소하는 것이 정상적인 결과다. 기술 준비가 되어도 데이터 소유권이나 운영 인수 준비가 안 됐다면 출시 조건은 충족되지 않는다.

설계 리뷰

도입 로드맵의 핵심은 속도가 아니라 증거의 밀도다. 제한 배포는 자동화 범위를 학습하는 기간이다. GitHub의 Rulesets, CODEOWNERS, Environments, 감사 로그는 변경 통제의 선택지지만, 실제 가용성은 환경·요금제·정책에서 확인해야 한다 (SRC-034, SRC-035, SRC-036, SRC-037).

[실무 제안] 한 단계의 확대는 최소 네 증거로 승인한다. 업무 기준선의 변화, 정책·권한 시험 결과, 운영 trace와 복구 연습, 책임자의 명시적 수용이다. 네 증거가 한 릴리스 식별자로 연결되지 않으면 확장 사유가 아니라 다음 POC의 조사 항목으로 남긴다.

  • CDU(Coolant Distribution Unit) — 시설수와 장비 냉각수 사이에서 열교환·유량 제어를 담당하는 장치.
  • Cold plate — GPU·CPU 같은 발열 부품에 접촉해 냉각수로 열을 옮기는 열교환 부품.
  • D2C(Direct-to-Chip) — 냉각수를 발열 부품의 cold plate까지 전달하는 직접 수랭 방식.
  • FWS(Facility Water System) — 데이터센터가 열을 받아 외부로 배출하는 시설수 계통.
  • PDU(Power Distribution Unit) — 전력을 랙·장비에 분배하고 측정·보호하는 장치.
  • PUE — 데이터센터 전체 에너지를 IT 장비 에너지로 나눈 효율 지표. 측정 경계와 기간이 필수다.
  • TCS(Technology Cooling System) — IT 장비 쪽 냉각수 루프와 그 구성 요소의 계통.
  • W1–W5 — ASHRAE의 시설수 온도 환경 클래스. 숫자가 GPU 온도를 뜻하지 않는다.
  • 랙 전력 밀도 — 랙 하나에 공급·소비되는 전력 규모. 배전과 냉각 설계를 함께 결정한다.
  • 열 관성 — 전력·펌프 상실 뒤에도 온도가 시간에 따라 변하는 물리적 지연 특성.
  • 열포획률 — 발생 열 가운데 액체 냉각 경로가 제거하는 비율. 수랭 채택률과 같은 말이 아니다.
  • 누수 감지 — 센서·압력·유량 변화 등으로 냉각수 누출 가능성을 찾아 격리로 연결하는 기능.

GPU·패브릭·스토리지

  • B200 — NVIDIA Blackwell 세대 데이터센터 GPU 제품명. 시스템 구성은 공급자별로 확인해야 한다.
  • Collective communication — 여러 프로세스·GPU가 broadcast, reduce, all-reduce 같은 집단 연산에 참여하는 통신.
  • CUDA — NVIDIA GPU 프로그래밍 플랫폼과 소프트웨어 생태계.
  • DMA — CPU의 반복 복사 개입을 줄이고 장치가 메모리 사이 데이터를 전송하는 방식.
  • EFlops — 초당 10¹⁸회 부동소수점 연산 규모. 정밀도와 산정 방식을 함께 표시한다.
  • GDS(GPUDirect Storage) — 지원 구성에서 스토리지와 GPU 메모리 사이 데이터 경로를 단축하는 기술.
  • GPUDirect RDMA — 지원 장치 사이에서 GPU 메모리에 직접 접근하는 RDMA 데이터 경로.
  • HBM — GPU 가까이에 배치된 고대역폭 메모리. 용량과 대역폭 모두 모델 실행을 제약한다.
  • HCA — InfiniBand·RDMA 네트워크에 호스트를 연결하는 어댑터.
  • InfiniBand — 고성능 컴퓨팅에 널리 쓰이는 저지연·고대역폭 패브릭 기술.
  • MPI — 분산 프로세스 사이 메시지 전달 인터페이스의 표준.
  • NCCL — NVIDIA GPU 간 collective 통신을 구현하는 라이브러리.
  • NDR400 — 링크당 400 Gb/s급을 가리키는 InfiniBand 세대 표기. 실제 유효 처리량은 별도 측정한다.
  • NIC — 노드를 네트워크에 연결하는 인터페이스 장치.
  • NUMA — CPU·메모리·PCIe 장치 사이 접근 거리가 균일하지 않은 구조.
  • NVLink — 지원되는 NVIDIA GPU·시스템 구성 요소 사이 고속 연결 기술.
  • NVSwitch — 여러 GPU의 NVLink 연결을 스위칭하는 시스템 구성 요소.
  • O_DIRECT — 운영체제 페이지 캐시 경로를 우회하는 파일 입출력 방식.
  • Rail — 노드의 NIC와 패브릭을 병렬 경로로 배치할 때 구분하는 네트워크 축.
  • RDMA — 원격 호스트 메모리에 낮은 CPU 개입으로 데이터를 전달하는 접근 방식.
  • Rmax — LINPACK 시험으로 측정한 최대 성능값.
  • Rpeak — 시스템 구성에서 계산한 이론상 최대 부동소수점 성능값.
  • TOP500 — HPL/LINPACK 결과를 기준으로 고성능 시스템 순위를 공개하는 프로젝트.
  • 체크포인트 — 장시간 작업을 재개할 수 있도록 모델·옵티마이저·진행 상태를 저장한 데이터.
  • 토폴로지 — GPU·CPU·NIC·스위치·스토리지 사이 연결 관계와 거리.

스케줄링·MLOps·관측

  • Admission — 요청을 즉시 실행하지 않고 정책·쿼터·가용 자원을 확인해 실행 대상을 결정하는 단계.
  • AI EasyMaker — NHN Cloud가 공개한 개발·학습·모델·엔드포인트 관리 제품.
  • DCGM — NVIDIA 데이터센터 GPU의 상태·진단·텔레메트리를 다루는 관리 도구군.
  • DRA(Dynamic Resource Allocation) — Kubernetes에서 특수 장치를 선언·발견·할당하는 모델.
  • Endpoint — 모델 추론 요청을 받는 배포 단위 또는 네트워크 접근점.
  • Fair sharing — 장기 사용량·가중치·유휴 쿼터 등을 반영해 자원을 나누는 정책.
  • GPU Live — FactoryX Platform 레이어에 공개된 GPU 운영 제품명. 내부 스케줄러는 공개 자료로 단정하지 않는다.
  • GPUaaS — GPU 자원을 서비스 형태로 요청·할당·운영하는 제공 모델.
  • GRES — Slurm이 GPU 같은 일반 자원을 표현·예약하는 방식.
  • Kueue — Kubernetes 워크로드의 admission·quota·priority를 다루는 오픈소스 프로젝트.
  • Lineage — 데이터·코드·이미지·설정·모델·배포 사이 생성 관계와 변경 이력.
  • Metric — 시간에 따라 수치로 집계되는 관측 신호.
  • MIG — 지원 GPU를 격리된 GPU 인스턴스로 분할하는 NVIDIA 기술.
  • MLOps — 모델 개발·학습·평가·등록·배포·관측을 반복 가능하게 운영하는 실무 체계.
  • OpenTelemetry — trace·metric·log의 생성·전달·의미 규약을 제공하는 관측성 프로젝트.
  • Pipeline — 전처리·학습·평가·배포 같은 단계를 입력·출력 의존성으로 연결한 실행 정의.
  • Prometheus — 시계열 metric 수집·질의에 널리 쓰이는 오픈소스 시스템.
  • Quota — 조직·팀·큐가 사용할 수 있는 자원 한도 또는 공유 기준.
  • ResourceClaim — Kubernetes DRA에서 워크로드가 필요로 하는 장치를 표현하는 객체.
  • RAG — 검색한 외부 근거를 모델 입력에 결합해 응답을 생성하는 패턴.
  • Slurm — HPC 클러스터의 작업·자원 예약과 실행을 관리하는 워크로드 매니저.
  • SLI — 서비스 수준을 관측하기 위해 정의한 정량 지표.
  • SLO — 일정 기간에 달성하려는 서비스 수준의 목표.
  • TensorBoard — 학습 metric과 실험 결과를 시각화·비교하는 도구.
  • Trace — 하나의 요청이 여러 구성 요소를 통과한 실행 경로와 구간 기록.
  • Triton Inference Server — 여러 모델 프레임워크의 추론 배포를 지원하는 NVIDIA 서버 소프트웨어.
  • 단편화 — 총자원은 남아 있지만 크기·형태·위치가 맞지 않아 요청을 배치하지 못하는 상태.
  • 선점 — 우선순위가 높은 작업을 위해 실행 중인 작업의 자원을 회수하는 정책.

보안·거버넌스·에이전트

  • AI RMF — NIST가 제시한 자발적 AI 위험관리 프레임워크.
  • Audit trail — 누가 언제 어떤 입력·정책·승인으로 어떤 행동을 했는지 재구성하는 기록 사슬.
  • Compensation — 이미 실행된 외부 변경을 취소하거나 상쇄하기 위한 후속 동작.
  • Delegated identity — 사용자 또는 서비스의 권한을 제한된 범위로 위임해 실행에 사용하는 신원.
  • Excessive Agency — 모델·에이전트에 불필요하게 넓은 기능·권한·자율성을 부여해 생기는 위험.
  • Govern — AI 위험관리의 책임·정책·문화·감독을 세우는 기능.
  • Idempotency — 같은 요청이 반복돼도 의도한 결과가 한 번만 반영되도록 하는 성질.
  • Map — 사용 맥락·영향·이해관계자와 위험을 식별하는 AI RMF 기능.
  • Measure — 시험·관측·평가로 위험의 크기와 상태를 확인하는 AI RMF 기능.
  • Manage — 우선순위에 따라 위험을 수용·감소·회피·전가하고 추적하는 AI RMF 기능.
  • Policy engine — 요청·신원·자원·행동 조건을 평가해 허용 여부를 결정하는 구성 요소.
  • Prompt injection — 입력이나 검색 문서의 지시가 의도한 정책을 우회하도록 모델 행동을 유도하는 공격·오염 방식.
  • ProjectX — FactoryX Service 레이어의 기업 AI 에이전트 실행 환경 방향으로 공개된 제품명. 세부 기능은 최신 자료로 확인한다.
  • RBAC — 역할에 권한을 묶고 사용자·서비스에 역할을 부여하는 접근통제 방식.
  • Sandbox — 코드·도구 실행의 파일·네트워크·프로세스 권한을 제한한 격리 환경.
  • Supply chain — 모델·데이터·이미지·패키지·도구가 만들어지고 전달되는 전체 공급 경로.
  • Tool allowlist — 에이전트가 호출할 수 있는 도구·동작을 명시적으로 제한한 목록.
  • Trust boundary — 신뢰 수준과 통제 책임이 바뀌는 시스템 경계.
  • 보존 정책 — 데이터·로그·모델·감사 기록을 저장하고 삭제하는 기간과 규칙.
  • 사람 전환 — 자동 판단이 불확실하거나 위험할 때 책임 있는 사람에게 결정을 넘기는 절차.
  • 최소 권한 — 업무에 필요한 최소 범위·시간·데이터에만 권한을 부여하는 원칙.
