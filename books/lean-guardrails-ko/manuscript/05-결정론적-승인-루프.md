## 결정론적 승인 루프

4장까지 준비물을 갖췄다. Lean 4라는 문법(3장)과, 자연어 정책을 그 문법으로 옮기는 번역가 Aristotle(4장). 이 장에서는 준비물을 조립해 실행 시스템을 완성한다. 논문이 제시하는 것은 상태 기계로 돌아가는 요청-응답 루프다. 거래 에이전트가 아무리 확률적으로 생각하더라도, 그 출력은 API 실행 직전의 결정론적 병목을 강제로 통과한다. 통과 조건은 하나다. 커널이 증명하면 간다, 못 하면 멈춘다.

루프는 시간의 결이 다른 두 국면으로 나뉜다. 정책을 미리 만들어 두는 비동기 국면과, 요청이 들어온 순간 판정하는 동기 국면이다.

### 정책을 미리 짓는 시간 — 비동기 구성

첫 국면은 서두르지 않는다. 규정 준수 담당자가 기관의 거래 한도와 리스크 파라미터를 일상어로 쓴다. "일일 가용 자본의 10퍼센트를 초과하는 거래를 집행하지 말라" 같은 문장이다. 특별한 표기법이 필요 없다. 정책의 저자는 여전히 사람이다.

다음으로 Aristotle이 이 문서를 처리한다. 비형식 추론 엔진이 문장을 해석하고, 증명 탐색 시스템이 그 제약을 Lean 4 코드로 자동 형식화한다. 생성된 코드는 Lean 커널이 컴파일하고, 논리적 모순이 있으면 4장의 자기수리 사이클이 반복해서 고친다. 컴파일이 성공하면 산출물 — 공리와 정리, 정의 — 는 정책 환경(Policy Environment)이라 불리는 불변 저장소에 쌓인다. 불변이라는 말이 무게를 갖는다. 한 번 검증된 정책은 몰래 고쳐질 수 없고, 바꾸려면 처음의 번역-컴파일-검증 고리를 다시 통과해야 한다.

이 국면이 비동기인 까닭은 간단하다. 번역과 증명 생성은 무겁고 느릴 수 있는 작업인데, 시장이 열려 있는 동안 하려면 늦는다. 그래서 미리, 거래가 없는 시간에 해 둔다.

### 요청을 걸러내는 시간 — 동기 승인 5단계

두 번째 국면은 실시간이다. 포트폴리오 리밸런싱 에이전트가 실시간 시세를 읽고 실행 의도를 만든다. 예를 들어 `execute_trade(symbol="AAPL", volume=50000, type="market")` 같은 API 호출이다. 이 순간부터 다섯 단계가 순서대로 진행된다.

첫 단계는 의도 생성이다. 에이전트가 특정 도구 호출을 설계한다. 여기까지는 에이전트의 자유다. 둘째 단계에서 오케스트레이터가 이 호출을 실행 환경에 닿기 전에 가로챈다. 요청을 토큰으로 분해해 파라미터와 현재 시스템 상태 변수 — 가용 자본, 최근 변동성 지수 — 를 추출한다. 셋째 단계에서 오케스트레이터는 정책 환경에 저장된 Lean 정리들에 이 값들을 대입해, 에이전트의 행동 하나를 하나의 수학적 추측(conjecture)으로 만든다. "이 거래는 모든 정책 정리를 만족하는가"라는 명제다. 넷째 단계에서 추측은 Lean 4 타입검사기에 제출되고, 커널이 증명을 시도한다.

다섯째 단계는 판정의 이행이다. 여기서 루프는 이진값으로 닫힌다. 상태 A — 증명 성공이면 커널은 참(True)을 반환하고, 게이트웨이가 열려 원래 API 호출이 실행 계층으로 흘러간다. 상태 B — 증명 실패면 거짓(False)이 반환된다. 거래 볼륨이 자본 정리를 초과했다는 식의 반증이고, 행동은 결정적으로 차단된다. 이때 시스템은 감사 로그용으로 형식 오류 추적을 남긴다. 왜 막혔는지가 수학의 언어로 기록되는 것이다.

다섯 단계에서 에이전트의 몫과 시스템의 몫이 정확히 갈린다. 에이전트는 첫 단계에서 생각할 자유를 갖는다. 의도를 만드는 일에는 확률이 개입해도 좋다. 그러나 둘째 단계 이후는 전부 오케스트레이터와 커널의 영토다. 생각하는 주체와 실행하는 주체를 이렇게 분리해 놓으면, 모델이 아무리 이상한 제안을 하더라도 그것이 세상에 닿는 길은 하나뿐임이 보장된다. 확률 필터가 '위험해 보이는 입력을 골라 막는' 방식과 결정적으로 다른 지점이다. 필터는 막히지 않고 통과한 것을 다시 검토하지 않지만, 이 루프는 통과 자체가 증명의 결과물이다. 다만 통과 뒤에 어떤 재심사도 필요 없다고까지 읽는 것은 필자의 확장 해석이다. 원문의 1단계 로드맵은 그림자 모드에서 인간 컴플라이언스 리뷰와의 대조를 명시적으로 유지한다(14장).

### 느리다는 편견 — 지연의 논증

이쯤에서 누구나 묻는다. 실행 경로마다 정리 증명을 돌리면 느리지 않은가. 형식 검증은 계산 비용이 크다는 것이 오랜 통념이고, 고빈도 거래 같은 밀리초의 세계에는 쓸 수 없다는 비판이 그 근거였다.

논문의 답은 증명 생성과 증명 검사의 분리에 있다. 무거운 일 — 증명을 만들고 정책을 형식화하는 일 — 은 전부 비동기 구성 국면에서 끝난다. 동기 실행 시점에 커널이 하는 일은 사전 컴파일된 바이너리를 대상으로 한 타입검사와 증명 검증뿐이다. 검사만큼은 Lean의 신뢰 커널이 최소한의 고성능 C++ 프리미티브로 구현되어 극도로 최적화되어 있다.

실측 근거도 있다. 아마존웹서비스(AWS)는 접근 제어 정책 언어 Cedar를 Lean 4로 형식 검증하는데, 차등 테스트 환경에서 형식화된 접근 제어 입력 하나를 Lean 모델로 평가하는 데 평균 5마이크로초가 걸렸다. 같은 입력을 고도로 최적화된 Rust 구현으로 평가한 평균은 7마이크로초였다. 즉 형식 모델의 평가가 손으로 다듬은 시스템 코드보다 빨랐다.

여기에 최근의 도구 진보가 더해진다. Lean 4 생태계에 도입된 자동화 전술 `grind`는 SMT(모듈로 이론 만족성) 풀이 능력을 증명기 안으로 끌어온다. 그래서 오케스트레이터가 `Trade_Value ≤ Capital_Limit` 같은 단순 산술 제약을 제출하면 커널은 서브밀리초에 답한다. 결론은 명쾌하다. 형식 검증은 실행 임계 경로의 병목이 아니다. 느린 학문이 아니라, 무거운 부분을 미리 하고 가벼운 부분만 현장에서 하는 공학이다.

측정 단위를 체감해 보자. 마이크로초는 밀리초의 천분의 일이다. 사람의 눈이 지연이라고 느끼는 문턱이 대략 백 밀리초인데, 커널의 판정은 그 문턱에서 이만 배쯔 아래에서 끝난다. 수백 밀리초를 얹는 LLM-as-a-judge 방식과 비교하면 차이는 자릿수 단위다. 도입부에서 확률 필터의 속도를 의심했던 독자라면, 오히려 판사 역할을 하는 언어 모델 쪽이 훨씬 무겁다는 사실을 새겨 둘 만하다.

정리해 보자. 비동기 국면이 정책을 수학으로 굳히고, 동기 국면이 매 행동을 그 수학에 대어 본다. 확률적 사고와 결정론적 실행이 만나는 접점은 오직 하나, 커널의 판정뿐이다. 다음 장부터는 이 구조가 실제 규제 문장들 — 시장 접근 규칙, 모형 리스크 관리, 설명 의무 — 과 어떻게 맞물리는지 확인한다.
