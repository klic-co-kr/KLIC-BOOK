### 타입 검사는 축소된 증명이다

원본 논문의 주장을 한 문장으로 줄이면 이렇다. 규정을 기계가 검사할 수 있는 명제로 만들고, 증명되지 않은 행동은 실행하지 마라. 이 장은 그 원리를 우리가 매일 쓰는 도구로 내려 옮긴다. 화면을 짓는 언어들 — TypeScript, Flutter의 Dart, React Native — 이 그 대상이다. 2부의 다른 장과 마찬가지로, 원본 논문의 개념을 UI 계층에 대입하는 일은 필자의 각색이다. 원본 논문은 금융 규제와 Lean 4만을 다룬다. 다만 각 절의 사실관계가 되는 논문들은 장 머리에 밝힌 대로 실물을 확인해 읽었다.

들어가며에서 예고한 문장이 있다. 타입 검사가 축소된 증명이라면, 증명은 완성된 타입 검사다. UI 계층은 이 사다리의 아래쪽 칸에 선다. 그래서 오히려 보기 좋다. 가드레일이 어떻게 만들어지고, 어디까지 막아 주고, 어디서부터 통제를 놓치는지를 가장 선명하게 드러내는 곳이기 때문이다.

### 633개의 버그가 말해 주는 것

TypeScript가 정말 버그를 줄이는지 묻는 대규모 실증은 놀랍게도 이 논문이 처음이다. 연구진은 16개 공개 저장소에서 633개의 버그 보고를 수집하고 하나하나 분류했다. 결과의 어조가 흥미롭다. 정적 타입은 확실히 일을 한다. 런타임 예외는 전체의 1.2퍼센트, 오류 처리 결함은 0.8퍼센트에 그쳤다. 자바스크립트 시절 연구와 비교하면 타입 관련 결함은 약 33퍼센트에서 12.4퍼센트로 떨어졌고, 과거 클라이언트 자바스크립트 버그의 68퍼센트를 차지하던 DOM 직접 조작 문제는 프레임워크가 DOM을 대신 다루면서 크게 물러났다.

그러면 무엇이 버그의 주범이 되었는가. 도구와 설정, 그리고 경계면이었다. 빌드·컴파일러·설정 결함이 27.8퍼센트로 가장 많았고, API 오용이 14.5퍼센트, UI 버그가 12.5퍼센트가 뒤를 이었다. `tsconfig.json` 한 줄의 경로 오류나 번들러 설정의 불일치처럼, 코드 밖의 계층에서 태어나 조용히 파이프라인을 타고 퍼지는 결함이다. 연구진은 이를 한마디로 압축한다. 신뢰성의 병목이 코드 안의 논리에서 생태계의 조율로 이동했다는 것이다.

여기에 가드레일 사고의 기본 자세가 들어 있다. 도구가 무엇을 막아 주는지, 그리고 무엇을 막지 못하는지를 데이터로 확인하는 일이다. 타입 시스템의 보장은 그 시스템이 검사하는 명제 안에서만 유효하다. 보장의 경계를 알 때 우리는 다음 계단을 어디에 놓을지 판단할 수 있다. 이것은 원본 논문이 기존 AI 가드레일의 한계를 짚던 방식과 정확히 같은 자세다.

### 언어 안에 내장된 가드레일

Dart의 사운드 null 안전성은 언어 계층 가드레일의 표본이다. 널이 될 수 있는 값과 없는 값을 타입 자체로 구분하고, 널 참조 가능성을 컴파일 시점에 원천 차단한다. 개발자가 런타임 검사를 성실하게 하기로 다짐하는 대신, 컴파일러가 대신 집행한다. 필자의 각색을 미리 밝히는데, 이것은 미니 정리라 부를 만하다. `String?` 타입은 "이 값은 없을 수 있다"는 명제고, 컴파일러는 그 명제를 다루는 코드마다 널이 아님을 증명할 것을 요구한다. 증명이 안 되면 컴파일이 막는다. Lean 커널이 증명에 실패한 행동의 실행을 막는 것과 같은 이진 구조다. 규칙이 문서에 있느냐, 집행기 안에 있느냐의 차이가 두 세계를 잇는 축이다.

그렇다면 AI가 이 언어들로 코드를 쓰는 시대에는 어떤가. MobileDev-Bench가 그 질문에 숫자로 답한다. 이 벤치마크는 실제 서비스 중인 모바일 앱 18개에서 실제 이슈 해결 과제 384개를 수집했다. 안드로이드 네이티브 307개, Flutter 63개, React Native 14개다. 네 개의 최신 코드 모델을 풀어 보니 종합 해결률이 3.39퍼센트에서 5.21퍼센트 사이에 불과했다. 한 자릿수의 한가운데다, 어려운 과제에서는 0퍼센트에서 1.6퍼센트로 사실상 무너졌다. 원인도 명확하다. 모바일 앱의 수정은 평균 12.5개 파일, 325줄에 이르고, 소스코드 외에 설정·리소스·매니페스트 같은 서로 다른 종류의 파일을 함께 건드려야 한다. 모델은 고쳐야 할 파일을 찾는 단계에서 이미 무너졌다. 파일 수준 재현율이 13.8퍼센트에서 19.5퍼센트 사이였다.

원본 논문의 승인 루프를 떠올려 보자. 에이전트의 행동을 중간에서 가로채 증명을 요구하고, 통과하면 실행한다. 해결률이 5퍼센트인 생성기가 있다면, 문제는 생성기의 능력만이 아니라 그 출력을 어디서 걸러내는가다. 빌드가 곧 검증이고 테스트 통과가 곧 증명인 Flutter·React Native 프로젝트에서, 이 게이트를 지우면 AI가 쓴 코드가 곧장 사용자의 화면으로 간다. UI 코드를 기계가 쓰는 시대에 검증 게이트는 사치가 아니라 전제다.

### 결정론적으로 검사할 수 있는 UI 규제

접근성은 UI 규제가 결정론적 검사와 만나는 지점이다. 밀라노 대학교 연구진은 iOS와 안드로이드의 스크린리더 API를 체계적으로 분석해 25개의 기능을 목록으로 만들었다. 그중 14개는 두 플랫폼에 기능적으로 동등하게 존재했다. 이론상 크로스플랫폼 프레임워크는 14개를 모두 하나의 API로 감쌀 수 있었다. 실제로는 React Native가 8개, Xamarin이 5개를 감쌌을 뿐이다. 가장 기본적인 8개 기능조차 React Native는 6개, Xamarin은 5개만 노출했다. 감싸지 않은 API를 쓰려면 개발자가 네이티브 언어로 플랫폼별 코드를 따로 작성해야 한다. 연구진의 실험에서는 이런 우회 구현에 며칠에서 수 주가 걸렸고, 결국 크로스플랫폼의 이점을 갉아먹었다. 추상화가 규제 준수를 누수시키는 사례다.

접근성 규칙의 성질에 주목하자. 이미지에 대체 텍스트가 있는지, 포커스 순서가 논리적인지, 레이블이 붙었는지 — 이런 규칙은 해석의 여지가 좁고 기계가 판정할 수 있다. 웹 접근성 표준의 자동 검증 도구가 그 증거다. 자연어로 쓰인 규제를 기계가 판정하는 형태로 옮기는 작업, 원본 논문이 자동 형식화라 부른 그 일의 UI판인 셈이다. 규모는 작아도 구조는 같다.

### UI 계층의 가드레일 사다리

이 장의 재료를 한 계단식으로 세워 보자. 린트가 흔한 실수를 걸러내고, 타입 검사가 명제를 강제하고, 빌드와 테스트가 합쳐지지 않은 코드를 막고, 디자인 토큰이 색과 간격의 값을 단일 출처로 묶고, 접근성 검사기가 규제 준수를 점점한다. 각 계단은 위로 갈수록 더 깊은 성질을, 더 결정론적으로 검사한다. 다음 표는 이 대응을 정리한 것이다. 이 표와 아래 해석은 필자의 각색이다.

| UI 계층의 도구 | 하는 일 | 원본 논문의 개념 |
|---|---|---|
| 린터 | 흔한 실수·스타일 위반을 걸러냄 | 구문 수준 검증 |
| 타입 검사기 | 타입 명제를 컴파일 시점에 강제 | 축소된 증명 |
| Dart의 사운드 null 안전성 | 널 참조를 원천 차단하는 이진 판정 | 커널의 허가·차단 |
| 빌드·테스트 게이트 | 증명 없는 병합을 막음 | 승인 루프 |
| 디자인 토큰 | 값을 불변의 단일 출처에 둠 | 정책 환경 |
| 접근성 검사기 | 검사 가능한 UI 규제를 자동 판정 | 자동 형식화된 규제 |

사다리를 다 오르면 어디에 닿는가. 원본 논문이 놓인 자리다. 이 장의 도구들은 규칙을 코드와 설정에 심지만, 그 규칙은 아직 언어가 정의한 명제 안에 머문다. 원본 논문은 사업의 규정 자체를 증명의 대상으로 만든다. 타입 검사가 축소된 증명이라는 문장은, 반대로 읽으면 증명까지 오르는 길이 이미 우리 발밑에 시작되어 있다는 뜻이다.
